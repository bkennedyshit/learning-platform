# 09.1 — Setup, Build Systems & Toolchain

> *"The tools we use have a profound (and devious!) influence on our thinking habits, and, therefore, on our thinking abilities."* — Edsger W. Dijkstra

Unlike Python's `pip install && python main.py`, C++ requires you to understand the compilation pipeline. This isn't a weakness — it's what gives you control over every byte your program produces. This chapter gets you from zero to a fully configured, IDE-quality development environment.

---

## 🎯 Learning Objectives

By the end of this chapter you will be able to:

1. Install and configure a modern C++ compiler (Clang, GCC, or MSVC).
2. Write `CMakeLists.txt` files for multi-target projects with dependencies.
3. Manage third-party libraries with vcpkg or Conan.
4. Configure clangd for IDE-quality code intelligence in VS Code.
5. Debug C++ programs with LLDB (or the VS debugger on Windows).
6. Understand the compilation pipeline: preprocessor → compiler → linker.

## 📚 1. Concepts & Definitions

### Definition 09.1.1 — The Compilation Pipeline

Unlike Python (interpreted), C++ is **compiled ahead of time**. Your source code goes through four stages:

```
Source (.cpp/.h) → Preprocessor → Compiler → Assembler → Linker → Executable
```

| Stage | Input | Output | What It Does |
|-------|-------|--------|-------------|
| **Preprocessor** | `.cpp` + `.h` | Translation unit | Expands `#include`, `#define`, `#ifdef` |
| **Compiler** | Translation unit | Object file (`.o`/`.obj`) | Parses C++, generates machine code |
| **Linker** | Object files + libraries | Executable/library | Resolves symbols across files |

**Python equivalent:** `import` + bytecode compilation + interpreter — but all happening at build time, not runtime.

### Definition 09.1.2 — Translation Unit

A **translation unit** is a single `.cpp` file after all `#include` directives have been expanded. Each translation unit is compiled independently. This is why you can have the same function name in two `.cpp` files (with `static` or anonymous namespace) without conflict.

### Definition 09.1.3 — CMake

**CMake** is a meta-build system — it doesn't build your code directly. Instead, it generates build files for your platform's native build tool (Ninja, Make, MSBuild). Think of it as a cross-platform `Makefile` generator.

### Definition 09.1.4 — Package Manager (vcpkg / Conan)

C++ has no built-in package manager like `pip`. **vcpkg** (Microsoft) and **Conan** (JFrog) fill this gap:

| Feature | vcpkg | Conan |
|---------|-------|-------|
| Integration | CMake-native (toolchain file) | CMake generators |
| Registry | Central GitHub repo | Remote + local recipes |
| Binary caching | Yes (GitHub Actions, NuGet) | Yes (Artifactory, local) |
| Best for | Quick start, Windows-heavy | Complex dependency graphs, CI |

### Definition 09.1.5 — clangd (Language Server)

**clangd** is an LSP (Language Server Protocol) implementation for C/C++. It provides:
- Real-time error diagnostics
- Code completion with semantic awareness
- Go-to-definition, find-references
- Automatic `#include` insertion
- Inlay hints (parameter names, deduced types)

It reads your `compile_commands.json` (generated by CMake) to understand your project's build configuration.

## 🧩 2. Mental Models

### Model 2.1.1 — "CMake is Your Project's Constitution"

Think of `CMakeLists.txt` as the single source of truth for:
- What files to compile
- What libraries to link
- What compiler flags to use
- What the output artifacts are

Every tool in your chain (compiler, IDE, debugger, package manager) reads from CMake. If CMake is wrong, everything downstream breaks.

### Model 2.1.2 — "Headers Are Copy-Paste, Sources Are Compilation Units"

```
#include "player.h"   // Literally pastes the entire file here
```

This is why you need **include guards** or `#pragma once` — without them, the same header pasted twice causes redefinition errors. This is fundamentally different from Python's `import` (which executes once and caches the module).

### Model 2.1.3 — "Linking Is Connecting the Dots"

The compiler produces object files with "holes" (undefined symbols). The linker fills those holes by connecting function calls to their definitions across object files and libraries. Common linker errors:

| Error | Meaning | Fix |
|-------|---------|-----|
| `undefined reference to X` | You declared X but never defined it | Add the `.cpp` file or link the library |
| `multiple definition of X` | X is defined in two translation units | Use `inline`, move to `.cpp`, or use anonymous namespace |
| `cannot find -lX` | Library X not found | Install it or fix library search path |

### 3.1 — Installing the Compiler

**Windows (recommended: MSVC + Clang):**
```powershell

# Option B: LLVM/Clang (standalone)

# Verify

```

**Linux (Ubuntu/Debian):**
```bash
sudo apt update
sudo apt install build-essential clang-17 lldb-17 cmake ninja-build
```

**macOS:**
```bash
xcode-select --install   # Apple Clang
brew install llvm cmake ninja
```

### 3.2 — CMake Fundamentals

**Minimal project structure:**
```
my_project/
├── CMakeLists.txt
├── src/
│   ├── main.cpp
│   └── engine.cpp
├── include/
│   └── engine.h
└── build/          ← generated, gitignored
```

**CMakeLists.txt — starter template:**
```cmake
cmake_minimum_required(VERSION 3.25)
project(MyGame
    VERSION 1.0.0
    LANGUAGES CXX
)

# Enforce modern C++
set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# Export compile_commands.json for clangd
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

# Define the executable
add_executable(my_game
    src/main.cpp
    src/engine.cpp
)

# Include directories
target_include_directories(my_game PRIVATE include)

# Compiler warnings (treat warnings as errors in CI)
target_compile_options(my_game PRIVATE
    $<$<CXX_COMPILER_ID:MSVC>:/W4 /permissive->
    $<$<NOT:$<CXX_COMPILER_ID:MSVC>>:-Wall -Wextra -Wpedantic>
)
```

**Build commands:**
```bash
# Configure (generate build files)
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug

# Build
cmake --build build

# Run
./build/my_game      # Linux/macOS
.\build\my_game.exe  # Windows
```

### 3.3 — vcpkg Integration

```bash
# Clone vcpkg (one-time setup)
git clone https://github.com/microsoft/vcpkg.git
cd vcpkg && ./bootstrap-vcpkg.sh  # or bootstrap-vcpkg.bat on Windows

# Install a library
./vcpkg install fmt spdlog glm

# Use with CMake (toolchain file approach)
cmake -B build -G Ninja \
    -DCMAKE_TOOLCHAIN_FILE=/path/to/vcpkg/scripts/buildsystems/vcpkg.cmake
```

**Using vcpkg packages in CMakeLists.txt:**
```cmake
find_package(fmt CONFIG REQUIRED)
find_package(spdlog CONFIG REQUIRED)

target_link_libraries(my_game PRIVATE fmt::fmt spdlog::spdlog)
```

**vcpkg.json (manifest mode — recommended):**
```json
{
    "name": "my-game",
    "version": "1.0.0",
    "dependencies": [
        "fmt",
        "spdlog",
        "glm",
        { "name": "sdl2", "features": ["vulkan"] }
    ]
}
```

### 3.4 — Conan Integration (Alternative)

```bash
pip install conan  # Yes, Conan is a Python package

# Create conanfile.txt
cat > conanfile.txt << 'EOF'

fmt/10.2.1

[generators]

# Configure CMake with Conan toolchain
cmake -B build -G Ninja \
    -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake
```

```json
        "--background-index",
        "--clang-tidy",
        "--header-insertion=iwyu",
        "--completion-style=detailed"

```

### 3.6 — Debugging with LLDB

```bash
# Build with debug symbols
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build

# Launch LLDB
lldb ./build/my_game
```

**Essential LLDB commands:**
```
(lldb) breakpoint set --file main.cpp --line 42    # Set breakpoint
(lldb) b main.cpp:42                                # Shorthand
(lldb) run                                          # Start execution
(lldb) next                                         # Step over
(lldb) step                                         # Step into
(lldb) continue                                     # Resume
(lldb) frame variable                               # Show local variables
(lldb) print my_var                                 # Evaluate expression
(lldb) bt                                           # Backtrace (call stack)
(lldb) watchpoint set variable x                    # Break when x changes
```

**VS Code launch.json (CodeLLDB extension):**
```json
{
    "version": "0.2.0",
    "configurations": [{
        "name": "Debug My Game",
        "type": "lldb",
        "request": "launch",
        "program": "${workspaceFolder}/build/my_game",
        "args": [],
        "cwd": "${workspaceFolder}",
        "preLaunchTask": "cmake-build"
    }]
}
```

### 3.7 — Multi-Target CMake (Libraries + Executables)

```cmake
cmake_minimum_required(VERSION 3.25)
project(GameEngine VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

# --- Engine library ---
add_library(engine STATIC
    src/engine/renderer.cpp
    src/engine/physics.cpp
    src/engine/audio.cpp
)
target_include_directories(engine PUBLIC include)

# --- Game executable ---
add_executable(game src/main.cpp)
target_link_libraries(game PRIVATE engine)

# --- Tests ---
enable_testing()
find_package(GTest CONFIG REQUIRED)

add_executable(engine_tests
    tests/renderer_test.cpp
    tests/physics_test.cpp
)
target_link_libraries(engine_tests PRIVATE engine GTest::gtest_main)

include(GoogleTest)
gtest_discover_tests(engine_tests)
```

### Example 09.1.2 — Diagnosing a Linker Error

<details>
<summary>You have a header declaring a function, but get "undefined reference" — fix it</summary>

**The error:**
```
/usr/bin/ld: CMakeFiles/game.dir/src/main.cpp.o: undefined reference to `Engine::init()'
```

**The problem:** You declared `Engine::init()` in `engine.h` but either:
1. Forgot to implement it in `engine.cpp`, or
2. Forgot to add `engine.cpp` to your CMake target

**Fix (if implementation exists but isn't compiled):**
```cmake
# WRONG — missing engine.cpp
add_executable(game src/main.cpp)

# RIGHT — include all source files
add_executable(game
    src/main.cpp
    src/engine.cpp  # ← This was missing
)
```

**Fix (if implementation is missing):**
```cpp
// engine.cpp
#include "engine.h"

void Engine::init() {
    // Implementation here
}
```

</details>

### Example 09.1.3 — Setting Up Sanitizers for Development

<details>
<summary>Configure AddressSanitizer to catch memory bugs at runtime</summary>

**Add to CMakeLists.txt:**
```cmake
# Only enable sanitizers in Debug builds
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    target_compile_options(my_game PRIVATE -fsanitize=address,undefined -fno-omit-frame-pointer)
    target_link_options(my_game PRIVATE -fsanitize=address,undefined)
endif()
```

**Or via CMake preset (CMakePresets.json):**
```json
{
    "version": 6,
    "configurePresets": [
        {
            "name": "debug-asan",
            "displayName": "Debug + ASan",
            "generator": "Ninja",
            "binaryDir": "${sourceDir}/build-asan",
            "cacheVariables": {
                "CMAKE_BUILD_TYPE": "Debug",
                "CMAKE_CXX_FLAGS": "-fsanitize=address,undefined -fno-omit-frame-pointer"
            }
        }
    ]
}
```

**Usage:**
```bash
cmake --preset debug-asan
cmake --build build-asan
./build-asan/my_game  # ASan will report any memory errors with full stack traces
```

**Example ASan output:**
```
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
READ of size 4 at 0x... thread T0
    #0 0x... in main src/main.cpp:15
    #1 0x... in __libc_start_main
```

</details>

### Pattern 2.1.2 — Header/Source Split Convention

```cpp
// include/engine/renderer.h — DECLARATION (interface)
#pragma once

#include <cstdint>
#include <string_view>

namespace engine {

class Renderer {
public:
    Renderer(uint32_t width, uint32_t height);
    ~Renderer();

    // Non-copyable, movable
    Renderer(const Renderer&) = delete;
    Renderer& operator=(const Renderer&) = delete;
    Renderer(Renderer&&) noexcept;
    Renderer& operator=(Renderer&&) noexcept;

    void clear(float r, float g, float b, float a = 1.0f);
    void present();
    void set_title(std::string_view title);

private:
    struct Impl;              // Forward declaration (Pimpl idiom)
    std::unique_ptr<Impl> impl_;
};

} // namespace engine
```

```cpp
// src/engine/renderer.cpp — DEFINITION (implementation)
#include "engine/renderer.h"
#include <SDL2/SDL.h>
#include <fmt/core.h>

namespace engine {

struct Renderer::Impl {
    SDL_Window* window = nullptr;
    SDL_Renderer* renderer = nullptr;
    uint32_t width, height;
};

Renderer::Renderer(uint32_t width, uint32_t height)
    : impl_(std::make_unique<Impl>()) {
    impl_->width = width;
    impl_->height = height;
    // SDL initialization...
    fmt::print("Renderer created: {}x{}\n", width, height);
}

Renderer::~Renderer() = default;  // unique_ptr handles cleanup
Renderer::Renderer(Renderer&&) noexcept = default;
Renderer& Renderer::operator=(Renderer&&) noexcept = default;

void Renderer::clear(float r, float g, float b, float a) {
    SDL_SetRenderDrawColor(impl_->renderer,
        static_cast<uint8_t>(r * 255),
        static_cast<uint8_t>(g * 255),
        static_cast<uint8_t>(b * 255),
        static_cast<uint8_t>(a * 255));
    SDL_RenderClear(impl_->renderer);
}

void Renderer::present() {
    SDL_RenderPresent(impl_->renderer);
}

} // namespace engine
```

## ⚠️ 6. Gotchas & Anti-Patterns

### Gotcha 2.1.1 — Forgetting `CMAKE_EXPORT_COMPILE_COMMANDS`

Without this, clangd has no idea how your project is configured. You'll get false errors for every `#include` and every compiler flag.

```cmake
# ALWAYS set this
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

Then symlink it to your project root (clangd looks there):
```bash
ln -s build/compile_commands.json .  # Linux/macOS
# Windows: copy or use clangd --compile-commands-dir=build
```

### Gotcha 2.1.2 — Mixing Compiler Versions

If you build a library with GCC 12 and link it with GCC 14, you may get ABI incompatibilities. The C++ ABI is not stable across major compiler versions (unlike C).

**Rule:** Build everything with the same compiler and version.

### Gotcha 2.1.3 — `#include` Order Matters

```cpp
// BAD: Your header might depend on something included before it
#include <vector>
#include "my_class.h"  // If this uses vector but doesn't include it, it works by accident

// GOOD: Include your own headers first to catch missing includes
#include "my_class.h"  // Forces this header to be self-contained
#include <vector>
#include <string>
```

### Gotcha 2.1.4 — Windows Path Length Limits

vcpkg + CMake on Windows can generate deeply nested paths that exceed the 260-character limit. Fix:

```powershell
# Enable long paths (requires admin)
New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem" `
    -Name "LongPathsEnabled" -Value 1 -PropertyType DWORD -Force
```

Or set `VCPKG_ROOT` to a short path like `C:\vcpkg`.

### Gotcha 2.1.5 — Debug vs Release Performance

Debug builds disable optimizations (`-O0`) and add debug symbols. Code can be **10–100x slower** in Debug mode. Always benchmark with Release builds:

```bash
cmake -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-release
```

## 🧠 8. Extended Worked Examples & Deep Dives

### Example 8.1 — CMake `target_link_libraries`: PUBLIC vs PRIVATE vs INTERFACE

**Problem:** You have a math library that uses Eigen internally and exposes Eigen types in its public headers. A rendering library uses your math library but doesn't expose Eigen to its own consumers. Configure the dependency graph correctly.

<details>
<summary>🔍 Full step-by-step solution</summary>

```cmake
cmake_minimum_required(VERSION 3.25)
project(DependencyGraph LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

find_package(Eigen3 CONFIG REQUIRED)
find_package(fmt CONFIG REQUIRED)
find_package(SDL2 CONFIG REQUIRED)

# --- Math library ---
# Eigen appears in math_lib's PUBLIC headers (e.g., Vector3 is Eigen::Vector3f)
add_library(math_lib STATIC
    src/math/transform.cpp
    src/math/quaternion.cpp
)
target_include_directories(math_lib PUBLIC include/math)

# PUBLIC: Eigen propagates to anything that links math_lib
# because math_lib's headers #include <Eigen/Dense>
target_link_libraries(math_lib PUBLIC Eigen3::Eigen)

# PRIVATE: fmt is only used inside .cpp files, not in headers
target_link_libraries(math_lib PRIVATE fmt::fmt)

# --- Physics library ---
# Uses math_lib internally but does NOT expose Eigen in its own headers
add_library(physics_lib STATIC
    src/physics/rigidbody.cpp
    src/physics/collision.cpp
)
target_include_directories(physics_lib PUBLIC include/physics)

# PRIVATE: physics_lib uses math_lib internally but its public API
# uses its own types (PhysVec3), not Eigen directly
target_link_libraries(physics_lib PRIVATE math_lib)

# --- Header-only utility library ---
add_library(utils INTERFACE)
target_include_directories(utils INTERFACE include/utils)
# INTERFACE: utils has no .cpp files, only headers
# Consumers get the include path; utils itself doesn't compile anything
target_link_libraries(utils INTERFACE fmt::fmt)

# --- Game executable ---
add_executable(game src/main.cpp)
target_link_libraries(game PRIVATE physics_lib utils SDL2::SDL2)
# game gets:
#   - physics_lib's headers (PUBLIC include dir)
#   - NOT Eigen (because physics_lib linked math_lib as PRIVATE)
#   - fmt (via utils INTERFACE)
#   - SDL2
```

**The propagation rules:**

| Keyword | Consumer gets include dirs? | Consumer gets link deps? | Used when |
|---------|---------------------------|-------------------------|-----------|
| `PUBLIC` | ✅ Yes | ✅ Yes | Dependency appears in YOUR public headers |
| `PRIVATE` | ❌ No | ❌ No | Dependency only used in YOUR .cpp files |
| `INTERFACE` | ✅ Yes | ✅ Yes | Header-only lib (no .cpp files of its own) |

**Verification — check what propagates:**
```bash
# See all properties of a target (including transitive deps)
cmake --build build --target math_lib -- -n  # dry run
# Or use cmake --graphviz=deps.dot build/ to visualize
cmake -B build -G Ninja
cmake --graphviz=deps.dot build/
dot -Tpng deps.dot -o dependency_graph.png
```

**Common mistake:** Using `PUBLIC` everywhere "just to be safe." This causes:
1. Longer compile times (every consumer recompiles when Eigen updates)
2. Include pollution (consumers see headers they shouldn't)
3. ODR violations if two libraries expose conflicting versions

</details>

### Example 8.2 — Conan 09.0 Integration with CMake

**Problem:** Set up a project using Conan 09.0 as the package manager with the `CMakeDeps` and `CMakeToolchain` generators, managing fmt, spdlog, and glm as dependencies.

<details>
<summary>🔍 Full step-by-step solution</summary>

**Step 1: Create `conanfile.py` (preferred over conanfile.txt in Conan 09.0)**
```python
# conanfile.py
from conan import ConanFile
from conan.tools.cmake import cmake_layout, CMakeToolchain, CMakeDeps

class GameEngineRecipe(ConanFile):
    name = "game_engine"
    version = "0.1.0"
    settings = "os", "compiler", "build_type", "arch"

    # Dependencies
    requires = (
        "fmt/10.2.1",
        "spdlog/1.13.0",
        "glm/cci.20230113",
    )

    build_requires = (
        "gtest/1.14.0",
    )

    def layout(self):
        cmake_layout(self)  # Sets standard build folder structure

    def generate(self):
        # CMakeToolchain: generates conan_toolchain.cmake
        tc = CMakeToolchain(self)
        tc.variables["MY_CUSTOM_VAR"] = "hello"
        tc.generate()

        # CMakeDeps: generates Find<Pkg>.cmake or <pkg>Config.cmake
        deps = CMakeDeps(self)
        deps.generate()
```

```bash

# %APPDATA%\ccache\ccache.conf (Windows)

max_size = 20G
compression = true
compression_level = 6
hash_dir = false
# Sloppiness: trade correctness for speed (safe for most projects)
slop = include_file_mtime,include_file_ctime,time_macros,pch_defines
```

```bash

# benchmark_ccache.sh — Run from project root

echo "=== Benchmark: ccache effectiveness ==="
echo ""

# Clear ccache stats
ccache --zero-stats

# 1. Cold build (empty cache)
echo "--- Cold build (no cache) ---"
ccache --clear
rm -rf build && cmake -B build -G Ninja -DCMAKE_CXX_COMPILER_LAUNCHER=ccache

echo ""
ccache --show-stats | grep -E "hit|miss"

# 2. Full rebuild (warm cache)
echo ""
echo "--- Full rebuild (warm cache) ---"
rm -rf build && cmake -B build -G Ninja -DCMAKE_CXX_COMPILER_LAUNCHER=ccache
time cmake --build build -j$(nproc)
echo ""
ccache --show-stats | grep -E "hit|miss"

```

| Build Type | Without ccache | With ccache | Speedup |
|-----------|---------------|-------------|---------|
| Cold (first build) | 45s | 47s | 0.96x (slight overhead) |
| Full rebuild (warm cache) | 45s | 4.2s | **10.7x** |
| After `git checkout` different branch | 45s | 6.1s | **7.4x** |
| Incremental (1 file) | 3.1s | 3.0s | 1.0x (no benefit) |

```bash
# Run IWYU using the compilation database
iwyu_tool.py -p build/ -- -Xiwyu --mapping_file=iwyu.imp > iwyu_output.txt 2>&1

# Apply fixes automatically
fix_includes.py < iwyu_output.txt
```

**Step 3: Create IWYU mapping file for project-specific rules**
```
# iwyu.imp — Tell IWYU about your project's conventions
[
    # fmt: include fmt/core.h instead of individual headers
    { include: ["<fmt/format.h>", "private", "<fmt/core.h>", "public"] },

    # Our engine: engine.h is the umbrella header
    { include: ["\"engine/renderer_impl.h\"", "private", "\"engine/renderer.h\"", "public"] },

    # System headers that IWYU gets wrong
    { include: ["<bits/types/struct_tm.h>", "private", "<ctime>", "public"] },
]
```

**Step 4: Integrate into CMake as a custom target**
```cmake
find_program(IWYU_PROGRAM NAMES include-what-you-use iwyu)
if(IWYU_PROGRAM)
    # Option A: Run on every compile (slow but thorough)
    set(CMAKE_CXX_INCLUDE_WHAT_YOU_USE
        ${IWYU_PROGRAM};-Xiwyu;--mapping_file=${CMAKE_SOURCE_DIR}/iwyu.imp)

    # Option B: Custom target (run on demand)
    add_custom_target(iwyu
        COMMAND iwyu_tool.py -p ${CMAKE_BINARY_DIR}
            -- -Xiwyu --mapping_file=${CMAKE_SOURCE_DIR}/iwyu.imp
        WORKING_DIRECTORY ${CMAKE_SOURCE_DIR}
        COMMENT "Running include-what-you-use..."
    )
endif()
```

```
  - Full rebuild time: 92s
  - Incremental (touch 1 header): 34s (recompiles 45 files)

After IWYU:
  - Average includes per .cpp: 9
  - Full rebuild time: 61s (34% faster)
  - Incremental (touch 1 header): 8s (recompiles 12 files)
```

### 9.1 FetchContent vs find_package() vs add_subdirectory — Complete Tradeoff Analysis

**The three mechanisms for consuming external code in CMake serve fundamentally different use cases.** Understanding when to use each prevents the most common CMake architecture mistakes.

#### `find_package()` — System/Pre-installed Libraries

```cmake
find_package(OpenSSL REQUIRED)
target_link_libraries(myapp PRIVATE OpenSSL::SSL OpenSSL::Crypto)
```

**How it works:** CMake searches for `FindOpenSSL.cmake` (Module mode) or `OpenSSLConfig.cmake` (Config mode) in standard system paths, `CMAKE_PREFIX_PATH`, and package registry locations.

**Advantages:**
- Fastest configure time (no downloading, no building)
- Respects system package manager (apt, brew, vcpkg)
- Shared libraries reduce binary size
- Security patches applied system-wide

**Disadvantages:**
- Version mismatch between dev machines ("works on my machine")
- Requires pre-installation step (CI must install deps first)
- Config-mode files vary wildly in quality between packages

**Best for:** System libraries (OpenSSL, zlib, CUDA), large frameworks (Qt, Boost), anything managed by vcpkg/Conan.

#### `FetchContent` — Download at Configure Time

```cmake
include(FetchContent)
FetchContent_Declare(
    json
    GIT_REPOSITORY https://github.com/nlohmann/json.git
    GIT_TAG        v3.11.3
    GIT_SHALLOW    TRUE
)
FetchContent_MakeAvailable(json)
target_link_libraries(myapp PRIVATE nlohmann_json::nlohmann_json)
```

**How it works:** During `cmake -B build` (configure step), CMake clones the repo into `_deps/` inside your build directory, then calls `add_subdirectory()` on it.

**Advantages:**
- Reproducible (pinned to exact git tag/commit)
- No pre-installation required (works on fresh clone)
- Source available for debugging
- Single CMake invocation handles everything

**Disadvantages:**
- Slow first configure (downloads + builds all deps)
- Pollutes your build namespace (dep's targets visible globally)
- Can conflict if two deps fetch different versions of the same library
- `_deps/` folder can grow to gigabytes

**Best for:** Small-to-medium libraries (json, catch2, doctest), header-only libraries, projects where reproducibility > build speed.

#### `add_subdirectory()` — Vendored/Submodule Code

```cmake
# Assumes third_party/imgui/ exists (git submodule or copied)
add_subdirectory(third_party/imgui)
target_link_libraries(myapp PRIVATE imgui)
```

**How it works:** Treats the subdirectory as part of your project. Its `CMakeLists.txt` is processed in your build.

**Advantages:**
- Full control (you can patch the code)
- Works offline
- Fastest iteration (no network, no package manager)

**Disadvantages:**
- Bloats your repository
- Manual updates (must pull new versions yourself)
- Git submodules are notoriously confusing for teams

**Best for:** Forked/patched libraries, internal shared code, monorepo architectures.

#### Decision Matrix

| Factor | `find_package` | `FetchContent` | `add_subdirectory` |
|--------|---------------|----------------|-------------------|
| Configure speed | ⚡ Fast | 🐌 Slow (first time) | ⚡ Fast |
| Reproducibility | ❌ System-dependent | ✅ Pinned version | ✅ Vendored |
| Offline builds | ✅ (if installed) | ❌ (needs network) | ✅ |
| Repo size | Small | Small | Large |
| Debugging deps | ❌ (no source) | ✅ (source in _deps) | ✅ (source in tree) |
| Version conflicts | Rare | Common | Rare |
| CI setup | Complex | Simple | Simple |

#### The Hybrid Pattern (Recommended)

```cmake
# Try system package first; fall back to FetchContent
find_package(spdlog 1.12 QUIET)
if(NOT spdlog_FOUND)
    message(STATUS "spdlog not found system-wide, fetching...")
    FetchContent_Declare(spdlog
        GIT_REPOSITORY https://github.com/gabime/spdlog.git
        GIT_TAG v1.13.0
    )
    FetchContent_MakeAvailable(spdlog)
endif()
```

This gives you the best of both worlds: fast builds when the package is installed (via vcpkg/Conan), automatic fallback for fresh environments.

### 9.2 The Compilation Model — Why C++ Builds Are Slow (And What To Do About It)

**C++ has the slowest compilation model of any mainstream language.** Understanding *why* is essential for optimizing build times.

#### The Textual Inclusion Model

Every `#include` literally copy-pastes the header file into your translation unit. A single `#include <iostream>` expands to ~27,000 lines of code. A typical game engine .cpp file with 15 includes can expand to 200,000+ lines that the compiler must parse, type-check, and optimize — *for every single .cpp file*.

```bash
# See how large your translation unit actually is:
g++ -E src/main.cpp | wc -l
# Output: 187,432 lines (from a 50-line source file!)
```

#### The Mitigation Stack (ordered by impact)

1. **Precompiled Headers (PCH)** — 20-40% speedup
```cmake
target_precompile_headers(game PRIVATE
    <vector>
    <string>
    <unordered_map>
    <memory>
    <fmt/core.h>
)
```
The compiler parses these once and reuses the AST for every .cpp file.

2. **Forward Declarations** — 10-30% speedup
```cpp
// BAD: includes entire Player definition
#include "player.h"
class GameWorld {
    std::vector<Player*> players_;  // Only needs pointer — forward decl suffices
};

// GOOD: forward declare
class Player;  // No #include needed for pointers/references
class GameWorld {
    std::vector<Player*> players_;
};
```

3. **Unity Builds (Jumbo Compilation)** — 30-60% speedup for clean builds
```cmake
set(CMAKE_UNITY_BUILD ON)
set(CMAKE_UNITY_BUILD_BATCH_SIZE 16)  # Combine 16 .cpp files into one TU
```
Reduces redundant header parsing but can cause ODR issues with `static` variables.

4. **C++20 Modules** — 50-80% speedup (when fully supported)
```cpp
// math.cppm — module interface
export module math;

export class Vector3 {
    float x, y, z;
public:
    Vector3(float x, float y, float z) : x(x), y(y), z(z) {}
    float length() const;
};
```
Modules are parsed once and imported as a binary AST — no textual inclusion.

5. **Distributed Compilation** — Linear speedup with machines
```bash
# distcc: distribute compilation across network
export CXX="distcc g++"
cmake -B build -DCMAKE_CXX_COMPILER_LAUNCHER=distcc

# icecream (icecc): smarter load balancing
export ICECC_VERSION=auto
cmake -B build -DCMAKE_CXX_COMPILER_LAUNCHER=icecc
```

#### Build Time Budget (Real-World Game Engine, 500 .cpp files)

| Optimization | Clean Build | Rebuild (1 file) |
|-------------|-------------|-------------------|
| Baseline | 180s | 12s |
| + Ninja (parallel) | 45s | 4s |
| + PCH | 32s | 3.5s |
| + ccache (warm) | 5s | 3.5s |
| + Unity build | 18s | 18s (rebuilds batch) |
| + Modules (future) | ~10s | ~2s |

### 9.3 vcpkg vs Conan vs Build2 — Package Manager Comparison

| Feature | vcpkg | Conan 09.0 | Build2 |
|---------|-------|-----------|--------|
| **Backing** | Microsoft | JFrog | Code Synthesis |
| **Package count** | 2,200+ | 1,800+ | 300+ |
| **Binary caching** | ✅ (GitHub/Azure) | ✅ (Artifactory/S3) | ✅ |
| **CMake integration** | Seamless (toolchain file) | Good (generators) | Own build system |
