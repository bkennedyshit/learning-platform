# 08.1 — Setup, Tooling & Project Structure

> *"The first step in fixing a broken program is getting it to fail repeatably."* — Tom Duff

Your development environment is not a detail — it's infrastructure. A misconfigured environment produces irreproducible bugs, dependency hell, and wasted hours. This chapter establishes the professional-grade Python setup that every subsequent chapter assumes.

## 📚 1. Definitions / Concepts

### Definition 08.1.1 — Virtual Environment

A **virtual environment** is an isolated directory tree containing a Python interpreter, a `site-packages/` directory, and activation scripts. It provides **namespace isolation**: packages installed in one venv do not pollute another.

Under the hood, a venv is just a directory with:
- A symlink (Unix) or copy (Windows) of the Python binary
- A `pyvenv.cfg` file pointing to the base interpreter
- A `site-packages/` that shadows the system one

```python
# Creating and activating (cross-platform)
import venv
venv.create("./venv", with_pip=True)

# Or from CLI:
# python -m venv .venv
# Windows: .venv\Scripts\activate
# Unix:    source .venv/bin/activate
```

### Definition 08.1.2 — pyproject.toml (PEP 621)

The **single source of truth** for a Python project's metadata, dependencies, build system, and tool configuration. Replaces the legacy `setup.py` + `setup.cfg` + `requirements.txt` trinity.

```toml
[project]
name = "my-project"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "httpx>=0.27.0,<08.0",
    "pydantic>=2.0,<3.0",
]

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.4", "mypy>=08.10"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 99
target-version = "py311"

[tool.mypy]
strict = true
python_version = "3.11"

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-ra --strict-markers"
```

### Definition 08.1.3 — Package Manager Hierarchy

| Tool | Role | Speed | Lock File |
|------|------|-------|-----------|
| `pip` | Base installer (always available) | Slow | `requirements.txt` (manual) |
| `uv` | Drop-in pip replacement (Rust-based) | 10-100x faster | `uv.lock` |
| `poetry` | Full project manager | Medium | `poetry.lock` |
| `pdm` | PEP 621-native manager | Fast | `pdm.lock` |

**Recommendation for 2026:** Use `uv` for speed + simplicity. It handles venv creation, dependency resolution, and locking in one tool.

### Definition 08.1.4 — The `src/` Layout

```
my-project/
├── pyproject.toml
├── README.md
├── src/
│   └── my_project/
│       ├── __init__.py
│       ├── core.py
│       └── utils.py
├── tests/
│   ├── __init__.py
│   ├── test_core.py
│   └── conftest.py
├── docs/
├── scripts/
└── .github/
    └── workflows/
        └── ci.yml
```

**Why `src/`?** It prevents accidental imports from the project root. Without it, `import my_project` might resolve to the local directory rather than the installed package — a subtle bug that only manifests in production.

### Definition 08.1.5 — Type Stubs and `py.typed`

A `py.typed` marker file in your package root signals to type checkers that your package ships inline type annotations. Without it, `mypy` treats your package as untyped even if every function has annotations.

## 📐 2. Mental Models / Principles

### Principle 1.1.1 — Reproducibility Is Non-Negotiable

Every Python project must answer: "Can someone else (or future-you) clone this repo and get an identical environment in one command?"

The reproducibility stack:
1. **Python version** — pinned in `pyproject.toml` (`requires-python`)
2. **Dependencies** — locked with exact versions + hashes (`uv.lock`)
3. **System dependencies** — documented or containerized (Docker)
4. **Configuration** — checked into version control (not in your head)

### Principle 1.1.2 — The Dependency Diamond

```
Your Project
├── depends on Library A (needs requests>=2.28)
└── depends on Library B (needs requests>=2.25,<2.30)
    → Resolver must find: requests>=2.28,<2.30
```

This is why you need a **resolver** (not just `pip install`). Modern tools (`uv`, `poetry`) use SAT solvers to find compatible version sets. `pip` historically installed greedily and could produce broken environments.

### Principle 1.1.3 — Fail Fast, Fail Loud

Your toolchain should catch errors at the earliest possible stage:

| Stage | Tool | Catches |
|-------|------|---------|
| Edit time | Pylance (VS Code) | Type errors, undefined names, import errors |
| Save time | ruff (format + lint) | Style violations, unused imports, security issues |
| Pre-commit | mypy + pytest | Type system violations, logic bugs |
| CI | Full test suite + coverage | Integration failures, regressions |

### Principle 1.1.4 — Convention Over Configuration

Python's ecosystem has converged on conventions. Don't fight them:
- Tests in `tests/`, named `test_*.py`
- Source in `src/<package_name>/`
- Config in `pyproject.toml` (one file, not five)
- Formatting: just use `ruff format` (Black-compatible, faster)

## 🔑 3. Mechanics

### 3.1 — Installing Python (Cross-Platform)

**Windows (your current platform):**
```powershell
# Option A: Official installer from python.org (check "Add to PATH")
# Option B: Windows Store (auto-updates, sandboxed)
# Option C: pyenv-win
Invoke-WebRequest -UseBasicParsing -Uri "https://raw.githubusercontent.com/pyenv-win/pyenv-win/master/pyenv-win/install-pyenv-win.ps1" -OutFile "./install-pyenv-win.ps1"; &"./install-pyenv-win.ps1"

pyenv install 3.12.4
pyenv global 3.12.4
```

**Linux/macOS:**
```bash
# pyenv (the standard)
curl https://pyenv.run | bash
# Add to ~/.bashrc or ~/.zshrc:
# export PATH="$HOME/.pyenv/bin:$PATH"
# eval "$(pyenv init -)"

pyenv install 3.12.4
pyenv global 3.12.4
```

**Verification:**
```python
import sys
print(f"Python {sys.version}")
print(f"Executable: {sys.executable}")
print(f"Platform: {sys.platform}")
print(f"Prefix: {sys.prefix}")  # Should point to venv when activated
```

### 3.2 — Virtual Environment Lifecycle

```bash
# Create (using uv — recommended)
uv venv .venv

# Activate
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# Windows cmd:
.venv\Scripts\activate.bat
# Unix:
source .venv/bin/activate

# Install dependencies
uv pip install -e ".[dev]"

# Deactivate
deactivate

# Nuke and recreate (when things go wrong)
rm -rf .venv && uv venv .venv && uv pip install -e ".[dev]"
```

**What activation actually does:** It prepends `.venv/Scripts/` (or `.venv/bin/`) to your `$PATH` and sets `$VIRTUAL_ENV`. That's it. Python finds packages by looking in `sys.prefix/lib/pythonX.Y/site-packages/`.

### 3.3 — Ruff Configuration (Linting + Formatting)

```toml
# In pyproject.toml
[tool.ruff]
line-length = 99
target-version = "py311"
src = ["src", "tests"]

[tool.ruff.lint]
select = [
    "E",    # pycodestyle errors
    "W",    # pycodestyle warnings
    "F",    # pyflakes
    "I",    # isort
    "N",    # pep8-naming
    "UP",   # pyupgrade
    "B",    # flake8-bugbear
    "A",    # flake8-builtins
    "S",    # flake8-bandit (security)
    "T20",  # flake8-print (no print in prod)
    "RUF",  # ruff-specific rules
]
ignore = ["S101"]  # Allow assert in tests

[tool.ruff.lint.per-file-ignores]
"tests/**" = ["S101", "T20"]
```

```bash
# Usage
ruff check .          # Lint
ruff check . --fix    # Auto-fix
ruff format .         # Format (Black-compatible)
```

### 3.4 — mypy Strict Mode

```toml
[tool.mypy]
strict = true
python_version = "3.11"
warn_return_any = true
warn_unused_configs = true
disallow_untyped_defs = true

[[tool.mypy.overrides]]
module = "tests.*"
disallow_untyped_defs = false
```

**What `strict = true` enables:** Every function must have type annotations. No `Any` leakage. No implicit `Optional`. This catches entire categories of bugs at zero runtime cost.

### 3.5 — VS Code Workspace Settings

```json
// .vscode/settings.json
{
    "python.defaultInterpreterPath": ".venv/Scripts/python.exe",
    "python.analysis.typeCheckingMode": "strict",
    "python.analysis.autoImportCompletions": true,
    "[python]": {
        "editor.defaultFormatter": "charliermarsh.ruff",
        "editor.formatOnSave": true,
        "editor.codeActionsOnSave": {
            "source.fixAll.ruff": "explicit",
            "source.organizeImports.ruff": "explicit"
        }
    },
    "python.testing.pytestEnabled": true,
    "python.testing.pytestArgs": ["tests"]
}
```

### Example 08.1.1 — Bootstrapping a New Project from Scratch

**Problem:** Create a new Python project called `nepa-tools` with proper structure, typing, linting, and tests.

<details>
<summary>🔍 View Step-by-Step Solution</summary>

```bash
# 1. Create directory structure
mkdir nepa-tools && cd nepa-tools
mkdir -p src/nepa_tools tests docs scripts

# 2. Initialize with uv
uv venv .venv
# Activate (Windows):
.venv\Scripts\Activate.ps1

# 3. Create pyproject.toml
cat > pyproject.toml << 'EOF'
[project]
name = "nepa-tools"
version = "0.1.0"
description = "NEPA AI analysis toolkit"
requires-python = ">=3.11"
dependencies = []

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.4", "mypy>=08.10"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
EOF

# 4. Create package files
touch src/nepa_tools/__init__.py
touch src/nepa_tools/py.typed

# 5. Create a module
cat > src/nepa_tools/analyzer.py << 'EOF'
"""NEPA document analyzer."""
from pathlib import Path

def analyze_document(path: Path) -> dict[str, int]:
    """Count sections in a NEPA document."""
    text = path.read_text(encoding="utf-8")
    lines = text.splitlines()
    return {
        "total_lines": len(lines),
        "sections": sum(1 for l in lines if l.startswith("#")),
        "paragraphs": sum(1 for l in lines if l.strip() and not l.startswith("#")),
    }
EOF

# 6. Create test
cat > tests/test_analyzer.py << 'EOF'
from pathlib import Path
from nepa_tools.analyzer import analyze_document

def test_analyze_document(tmp_path: Path) -> None:
    doc = tmp_path / "test.md"
    doc.write_text("# Title\n\nParagraph one.\n\n# Section 2\n\nParagraph two.\n")
    result = analyze_document(doc)
    assert result["sections"] == 2
    assert result["paragraphs"] == 2
EOF

# 7. Install in editable mode
uv pip install -e ".[dev]"

# 8. Run quality gates
ruff check .
ruff format .
mypy src/
pytest
```

</details>

## 💻 5. Code Patterns & Idioms

### Pattern 1.1.1 — The Minimal `__init__.py`

```python
"""nepa_tools — NEPA AI analysis toolkit."""

from nepa_tools.analyzer import analyze_document

__all__ = ["analyze_document"]
__version__ = "0.1.0"
```

**Why explicit `__all__`?** It controls what `from package import *` exports, and tools like `ruff` and `mypy` use it to detect unused public API.

### Pattern 1.1.2 — Entry Points (CLI Commands)

```toml
# In pyproject.toml
[project.scripts]
nepa = "nepa_tools.cli:main"
```

```python
# src/nepa_tools/cli.py
"""CLI entry point."""
import argparse
import sys
from pathlib import Path

from nepa_tools.analyzer import analyze_document


def main() -> int:
    parser = argparse.ArgumentParser(description="NEPA document analyzer")
    parser.add_argument("path", type=Path, help="Document to analyze")
    parser.add_argument("--json", action="store_true", help="Output as JSON")
    args = parser.parse_args()

    if not args.path.exists():
        print(f"Error: {args.path} not found", file=sys.stderr)
        return 1

    result = analyze_document(args.path)

    if args.json:
        import json
        print(json.dumps(result, indent=2))
    else:
        for key, value in result.items():
            print(f"{key}: {value}")

    return 0


if __name__ == "__main__":
    sys.exit(main())
```

### Pattern 1.1.3 — conftest.py for Shared Fixtures

```python
# tests/conftest.py
"""Shared test fixtures."""
import pytest
from pathlib import Path


@pytest.fixture
def sample_doc(tmp_path: Path) -> Path:
    """Create a sample NEPA document for testing."""
    doc = tmp_path / "sample.md"
    doc.write_text(
        "# Environmental Impact Statement\n\n"
        "## Purpose and Need\n\n"
        "This project addresses...\n\n"
        "## Alternatives\n\n"
        "Three alternatives were considered.\n"
    )
    return doc


@pytest.fixture
def empty_doc(tmp_path: Path) -> Path:
    """Create an empty document."""
    doc = tmp_path / "empty.md"
    doc.write_text("")
    return doc
```

## ⚠️ 6. Gotchas & Anti-Patterns

### Gotcha 1.1.1 — System Python Pollution

**Never** `pip install` into your system Python. Every project gets its own venv. System Python is for the OS package manager only.

```bash
# BAD: Installs globally, conflicts with OS packages
pip install requests

# GOOD: Always in a venv
python -m venv .venv && source .venv/bin/activate
pip install requests
```

### Gotcha 1.1.2 — `requirements.txt` Without Pinning

```
# BAD: "works on my machine" syndrome
requests
flask
numpy

# GOOD: Pinned with hashes for supply-chain security
requests==2.31.0 \
    --hash=sha256:942c5a758f98d790eaed1a29cb6eefc7f0edf3fcb0fce8afe0f44505355fed47
```

Better yet: use `uv.lock` or `poetry.lock` which handle this automatically.

### Gotcha 1.1.3 — Relative Imports in Scripts

```python
# This FAILS when run as `python src/my_package/utils.py`:
from .core import something  # RelativeImportError

# Why: Running a file directly makes it __main__, not part of a package.
# Solution: Always run via the installed package or `python -m my_package.utils`
```

### Gotcha 1.1.4 — Windows Path Separators

```python
# BAD: Breaks on Unix
path = "src\\my_package\\data.json"

# GOOD: Cross-platform
from pathlib import Path
path = Path("src") / "my_package" / "data.json"
```

### Gotcha 1.1.5 — Forgetting `py.typed`

Without `py.typed` in your package root, downstream users running `mypy` will see:
```
error: Skipping analyzing "your_package": module is installed, but missing library stubs or py.typed marker
```

## 🧠 9. Extended Worked Examples & Deep Dives

### Example 9.1 — pyenv vs uv: Choosing a Python Version Manager

**Problem:** You need to maintain three projects simultaneously: one requires Python 3.9 (legacy ML pipeline), one requires 3.11 (production API), and one requires 3.13 (experimental free-threaded build). Design a version management strategy comparing `pyenv` and `uv`, and demonstrate the full workflow for each.

<details>
<summary>🔍 Full step-by-step solution</summary>

#### Step 1: Understanding the Version Management Problem

Each project pins a different CPython interpreter. The system Python must remain untouched (OS package managers depend on it). We need:
- Isolated interpreter installations per version
- Per-directory automatic activation
- Reproducible CI parity (same versions locally and in pipelines)

#### Step 2: The pyenv Approach

`pyenv` compiles CPython from source (or fetches prebuilt binaries on some platforms). It uses shims in `~/.pyenv/shims/` that intercept `python` calls and redirect to the correct version.

```bash
# Install pyenv (Linux/macOS)
curl https://pyenv.run | bash

# Add to shell profile (~/.bashrc or ~/.zshrc)
export PYENV_ROOT="$HOME/.pyenv"
export PATH="$PYENV_ROOT/bin:$PATH"
eval "$(pyenv init -)"

# Install multiple Python versions
pyenv install 3.9.19
pyenv install 3.11.9
pyenv install 3.13.0

# Set per-directory version (creates .python-version file)
cd ~/projects/legacy-ml-pipeline
pyenv local 3.9.19

cd ~/projects/production-api
pyenv local 3.11.9

cd ~/projects/experimental-freethreaded
pyenv local 3.13.0

# Verify
cd ~/projects/legacy-ml-pipeline
python --version  # Python 3.9.19
```

**How shims work internally:**

1. `pyenv init -` prepends `~/.pyenv/shims/` to `$PATH`
2. Every `python`, `pip`, `python3.11` etc. in shims is a thin bash script
3. The shim reads `.python-version` (local) → `~/.pyenv/version` (global) → system
4. It then `exec`s the real binary at `~/.pyenv/versions/3.X.Y/bin/python`

#### Step 3: The uv Approach

`uv` (by Astral, the ruff team) is a Rust-based package/project manager that subsumes pyenv + pip + venv + pip-tools in a single binary. It downloads prebuilt Python binaries from the `python-build-standalone` project.

```bash
# Install uv
curl -LsSf https://astral.sh/uv/install.sh | sh

# uv automatically manages Python versions — no separate install step needed
# Create project with specific Python version
cd ~/projects/legacy-ml-pipeline
uv init --python 3.9
uv sync  # Downloads Python 3.9 if not cached, creates .venv, installs deps

cd ~/projects/production-api
uv init --python 3.11
uv sync

cd ~/projects/experimental-freethreaded
uv init --python 3.13
uv sync

# uv stores Pythons in ~/.local/share/uv/python/
# Each project's .venv/pyvenv.cfg points to the correct interpreter
```

#### Step 4: Head-to-Head Comparison

| Criterion | pyenv | uv |
|-----------|-------|-----|
| Install speed | Minutes (compiles from source) | Seconds (prebuilt binaries) |
| Disk per version | ~80 MB (full build) | ~45 MB (stripped standalone) |
| Windows support | Poor (pyenv-win is community) | Native (first-class) |
| Virtual env creation | Separate tool (venv/virtualenv) | Built-in (`uv venv`, `uv sync`) |
| Lock file | None (pair with pip-tools) | `uv.lock` (built-in) |
| Shell integration | Shims + shell init | No shims needed; explicit `.venv` |
| Free-threaded builds | `pyenv install 3.13.0t` | `uv python install 3.13 --free-threaded` |
| CI reproducibility | Requires pyenv install in CI | Single binary, no setup |

#### Step 5: Recommendation Decision Tree

```python
def choose_version_manager(constraints: dict) -> str:
    """
    Decision logic for choosing between pyenv and uv.
    """
    if constraints.get("windows_required"):
        return "uv"  # pyenv-win is unreliable
    
    if constraints.get("need_custom_compile_flags"):
        # e.g., --enable-optimizations, --with-lto, debug builds
        return "pyenv"  # uv uses prebuilt only
    
    if constraints.get("monorepo_with_lockfile"):
        return "uv"  # integrated dependency resolution
    
    if constraints.get("legacy_team_already_uses_pyenv"):
        return "pyenv"  # migration cost may not be worth it
    
    # Default: uv is faster, simpler, and more integrated
    return "uv"
```

**Final Answer:**

For most new projects in 2025+, **use `uv`**. It eliminates the need for pyenv + pip + venv + pip-tools as separate tools. Reserve `pyenv` for cases where you need custom CPython compile flags (debug builds, `--enable-optimizations`, `--with-pydebug`) or your team has deep pyenv muscle memory.

</details>

### Example 9.2 — Monorepo with Poetry Workspaces (Path Dependencies)

**Problem:** You're building a platform with three packages: `core` (shared utilities), `api` (FastAPI service), and `worker` (Celery task runner). Both `api` and `worker` depend on `core`. Design the monorepo structure with Poetry path dependencies, and show how to handle development installs, testing, and Docker builds.

<details>
<summary>🔍 Full step-by-step solution</summary>

#### Step 1: Directory Layout

```bash
platform-monorepo/
├── pyproject.toml          # Root workspace (Poetry 1.5+ or uv workspace)
├── packages/
│   ├── core/
│   │   ├── pyproject.toml
│   │   ├── src/
│   │   │   └── core/
│   │   │       ├── __init__.py
```

## 📘 10. Appendix: Extended Derivations & Special Cases

### 10.1 The PEP 517/518/621 Lineage — How Python Packaging Got Here

The Python packaging ecosystem's complexity stems from a 20-year evolution. Understanding the PEP lineage explains *why* `pyproject.toml` exists and what problems each layer solves.

**The Pre-PEP Era (2000–2016):**

`distutils` (stdlib, 2000) → `setuptools` (2004) → `pip` (2008) → `virtualenv` (2009). All relied on `setup.py` — an executable script that mixed build logic with metadata. This created a chicken-and-egg problem: you had to *execute* `setup.py` to learn what dependencies a package needed, but executing it might require those dependencies already installed.

**PEP 518 (2016) — Build System Declaration:**

Introduced `[build-system]` table in `pyproject.toml`. For the first time, a tool could read build dependencies *without* executing arbitrary Python code:

```bash
[build-system]
requires = ["setuptools>=61.0", "wheel"]
build-backend = "setuptools.build_meta"
```

This decoupled "what do I need to build?" from "run setup.py and hope."

**PEP 517 (2017) — Build Backend Interface:**

Standardized the API between frontends (pip, build) and backends (setuptools, flit, hatch, maturin). Any backend implementing `build_wheel()` and `build_sdist()` hooks works with any frontend. This broke setuptools' monopoly.

**PEP 621 (2020) — Standardized Project Metadata:**

Before PEP 621, each backend had its own metadata format (`[tool.poetry]`, `[tool.flit]`, `[tool.setuptools]`). PEP 621 created the universal `[project]` table that all backends read identically. Now you can switch from hatchling to setuptools to maturin by changing only `[build-system]`.

**The Modern Stack (2024+):**

$$
\text{pyproject.toml} = \underbrace{\text{PEP 518}}_{\text{build deps}} + \underbrace{\text{PEP 517}}_{\text{backend API}} + \underbrace{\text{PEP 621}}_{\text{metadata}} + \underbrace{\text{PEP 723}}_{\text{inline scripts}}
$$

### 10.2 Lock-File Algorithms: pip-compile vs Poetry vs uv

A lock file freezes the *entire* resolved dependency graph (including transitive dependencies) to exact versions + hashes. The resolution algorithm determines correctness, speed, and handling of conflicts.

**The SAT Problem:**

Dependency resolution is equivalent to Boolean satisfiability (SAT). Given constraints like `A>=08.0, B>=2.0` where `A==1.2` requires `C<3.0` but `B==2.1` requires `C>=3.0`, the resolver must find a consistent assignment or prove none exists.

**pip-compile (pip-tools):**

- Algorithm: Greedy backtracking with heuristic ordering
- Behavior: Resolves one package at a time, backtracks on conflict
- Speed: Slow for large graphs (exponential worst case)
- Output: `requirements.txt` with pinned versions + hashes
- Limitation: No cross-platform resolution (resolves for current platform only)

**Poetry:**

- Algorithm: Custom SAT solver (inspired by PubGrub from Dart)
- Behavior: Conflict-driven clause learning; explains *why* resolution failed
- Speed: Moderate (Python implementation)
- Output: `poetry.lock` (TOML format, cross-platform markers preserved)
- Strength: Excellent error messages on conflicts

**uv:**

- Algorithm: PubGrub (Rust implementation, same algorithm as Dart/pub)
- Behavior: Resolution with universal markers — solves for ALL platforms simultaneously
- Speed: 10-100x faster than pip-compile or Poetry (Rust + caching + parallel I/O)
- Output: `uv.lock` (TOML format, universal — works on Linux, macOS, Windows from single lock)
- Strength: Universal resolution means CI on Linux uses same lock as dev on macOS

**Performance Comparison (real-world project, 200 dependencies):**

| Resolver | Cold resolve | Warm resolve | Lock file portability |
|----------|-------------|-------------|----------------------|
| pip-compile | ~45s | ~12s | Single-platform |
| Poetry | ~30s | ~8s | Cross-platform |
| uv | ~1.2s | ~0.3s | Universal |

**Why Universal Resolution Matters:**

Traditional resolvers evaluate platform markers (`sys_platform == 'win32'`) at resolve time, producing a lock valid only for the current OS. Universal resolvers (uv) include *all* platform variants in a single lock file:

```bash
# uv.lock excerpt — same file works everywhere
[[package]]
name = "uvloop"
version = "0.19.0"
# Only installed on non-Windows:
markers = "sys_platform != 'win32'"
```

### 10.3 The src/ Layout vs Flat Layout — A Definitive Analysis

Two competing project layouts exist in the Python ecosystem. The choice affects import behavior, testing correctness, and packaging reliability.

**Flat Layout:**

```bash
my-project/
├── my_project/
│   ├── __init__.py
│   └── core.py
├── tests/
│   └── test_core.py
└── pyproject.toml
```

**src/ Layout:**

```bash
my-project/
├── src/
│   └── my_project/
│       ├── __init__.py
│       └── core.py
├── tests/
│   └── test_core.py
└── pyproject.toml
```

**The Critical Difference:**

In the flat layout, running `pytest` from the project root adds `.` to `sys.path`. This means `import my_project` succeeds *even if the package isn't installed*. Your tests pass locally but the package might be broken when installed by users (missing files in wheel, incorrect `packages` config).

In the src/ layout, `import my_project` **only works if the package is properly installed** (via `pip install -e .` or `uv sync`). This catches packaging bugs during development rather than after release.

**When to Use Each:**

| Criterion | Flat | src/ |
|-----------|------|------|
| Single-script projects | ✅ | Overkill |
| Libraries published to PyPI | ❌ Risk | ✅ Required |
| Applications with Docker | Either works | ✅ Preferred |
| Monorepos | ❌ Ambiguous | ✅ Clear boundaries |
| Namespace packages | ❌ Broken | ✅ Works correctly |

**The definitive recommendation:** Use `src/` layout for anything that will be `pip install`-ed, imported by other packages, or maintained longer than a week. Use flat layout only for throwaway scripts and Jupyter-adjacent exploration.
