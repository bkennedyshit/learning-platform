# 08.4 — Concurrency: asyncio, threading, multiprocessing & the GIL

> *"Concurrency is not parallelism."* — Rob Pike

Python offers three concurrency models, each suited to different workloads. The Global Interpreter Lock (GIL) is the elephant in the room — understanding it is the difference between writing fast concurrent Python and writing slow concurrent Python that *looks* like it should be fast.

---

## 🎯 Learning Objectives

By the end of this chapter you will be able to:

1. Explain the GIL: what it protects, when it releases, and why it exists.
2. Write `async/await` code with `asyncio` for I/O-bound concurrency.
3. Use `threading` correctly (and know when it helps vs. hurts).
4. Use `multiprocessing` for true CPU parallelism.
5. Choose the right concurrency model for a given workload.
6. Avoid common pitfalls: race conditions, deadlocks, and shared mutable state.

## 📚 1. Definitions / Concepts

### Definition 08.4.1 — The Global Interpreter Lock (GIL)

The **GIL** is a mutex in CPython that allows only one thread to execute Python bytecode at a time. It exists to protect CPython's reference-counting garbage collector from race conditions.

**Key facts:**
- The GIL is released during I/O operations (network, disk, sleep)
- The GIL is released by C extensions that don't touch Python objects (NumPy, BLAS)
- The GIL is NOT released during pure Python computation
- Python 3.13+ has experimental free-threaded mode (`--disable-gil`)

### Definition 08.4.2 — Coroutine

A **coroutine** is a function defined with `async def` that can suspend execution at `await` points, allowing other coroutines to run. Coroutines are the building blocks of `asyncio`.

```python
async def fetch(url: str) -> str:
    async with httpx.AsyncClient() as client:
        response = await client.get(url)  # Suspends here
        return response.text
```

### Definition 08.4.3 — Event Loop

The **event loop** is the scheduler that runs coroutines. It maintains a queue of ready tasks and advances them when their awaited I/O completes. There is one event loop per thread.

### Definition 08.4.4 — Concurrency vs. Parallelism

- **Concurrency**: Multiple tasks make progress (possibly interleaved on one core)
- **Parallelism**: Multiple tasks execute simultaneously (requires multiple cores)

`asyncio` and `threading` provide concurrency. `multiprocessing` provides parallelism.

## 📐 2. Mental Models / Principles

### Principle 1.4.1 — The Decision Matrix

| Workload | Model | Why |
|----------|-------|-----|
| Many network requests | `asyncio` | Thousands of concurrent connections, single thread |
| File I/O with legacy sync libs | `threading` | GIL releases during I/O; simpler than rewriting |
| CPU-bound (pure Python) | `multiprocessing` | Bypasses GIL with separate processes |
| CPU-bound (NumPy/BLAS) | `threading` works! | C extensions release the GIL |
| GPU compute | `asyncio` + process pool | Async dispatch, parallel GPU kernels |

### Principle 1.4.2 — Structured Concurrency

Modern async code uses **TaskGroups** (Python 3.11+) for structured concurrency — all tasks in a group must complete (or be cancelled) before the group exits:

```python
async with asyncio.TaskGroup() as tg:
    task1 = tg.create_task(fetch("https://api.example.com/a"))
    task2 = tg.create_task(fetch("https://api.example.com/b"))
# Both tasks guaranteed complete here. Exceptions propagate.
```

### Principle 1.4.3 — Share Nothing (Multiprocessing)

Processes don't share memory by default. Communication happens via:
- `Queue` / `Pipe` (message passing)
- `shared_memory` (explicit shared buffers)
- `Manager` (proxy objects — slow, avoid in hot paths)

This eliminates race conditions by design but adds serialization overhead.

## 🔑 3. Mechanics

### 3.1 — asyncio Fundamentals

```python
import asyncio
import httpx

async def fetch_all(urls: list[str]) -> list[str]:
    """Fetch multiple URLs concurrently."""
    async with httpx.AsyncClient() as client:
        async with asyncio.TaskGroup() as tg:
            tasks = [tg.create_task(client.get(url)) for url in urls]
    return [t.result().text for t in tasks]

# Entry point
results = asyncio.run(fetch_all(["https://example.com"] * 10))
```

**Key asyncio patterns:**
```python
# Timeout
async with asyncio.timeout(5.0):
    data = await slow_operation()

# Semaphore (limit concurrency)
sem = asyncio.Semaphore(10)
async def limited_fetch(url):
    async with sem:
        return await client.get(url)

# Queue (producer-consumer)
queue: asyncio.Queue[str] = asyncio.Queue(maxsize=100)
async def producer():
    await queue.put("item")
async def consumer():
    item = await queue.get()
```

### 3.2 — Threading (When You Need It)

```python
import threading
from concurrent.futures import ThreadPoolExecutor

def download(url: str) -> bytes:
    """Sync function — GIL released during network I/O."""
    import urllib.request
    return urllib.request.urlopen(url).read()

# ThreadPoolExecutor: the modern way
with ThreadPoolExecutor(max_workers=10) as pool:
    futures = [pool.submit(download, url) for url in urls]
    results = [f.result() for f in futures]

# Thread-safe data structures
import queue
q: queue.Queue[str] = queue.Queue()  # Thread-safe FIFO
```

### 3.3 — Multiprocessing (True Parallelism)

```python
from multiprocessing import Pool, cpu_count
import numpy as np

def heavy_compute(chunk: np.ndarray) -> float:
    """CPU-bound work — benefits from multiprocessing."""
    return float(np.linalg.det(chunk @ chunk.T))

data = [np.random.randn(100, 100) for _ in range(cpu_count())]

with Pool(processes=cpu_count()) as pool:
    results = pool.map(heavy_compute, data)
```

### 3.4 — ProcessPoolExecutor with asyncio

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor

async def hybrid_pipeline():
    """Async I/O + CPU parallelism."""
    loop = asyncio.get_running_loop()
    executor = ProcessPoolExecutor(max_workers=4)

    # Offload CPU work to process pool
    result = await loop.run_in_executor(executor, heavy_compute, data)
    return result
```

### Example 08.4.2 — Producer-Consumer with Backpressure

<summary>🔍 View Step-by-Step Solution</summary>

```python
import asyncio
from typing import AsyncIterator

async def producer(queue: asyncio.Queue[int], n: int) -> None:
    for i in range(n):
        await queue.put(i)  # Blocks if queue full (backpressure!)
        print(f"Produced {i}")
    await queue.put(-1)  # Sentinel

async def consumer(queue: asyncio.Queue[int], name: str) -> int:
    total = 0
    while True:
        item = await queue.get()
        if item == -1:
            await queue.put(-1)  # Pass sentinel to next consumer
            break
        await asyncio.sleep(0.01)  # Simulate processing
        total += item
        print(f"{name} consumed {item}")
    return total

async def main():
    queue: asyncio.Queue[int] = asyncio.Queue(maxsize=10)  # Backpressure at 10
    async with asyncio.TaskGroup() as tg:
        tg.create_task(producer(queue, 100))
        c1 = tg.create_task(consumer(queue, "C1"))
        c2 = tg.create_task(consumer(queue, "C2"))
    print(f"Totals: {c1.result()}, {c2.result()}")

asyncio.run(main())
```

### Example 08.4.3 — GIL Release Demonstration

<details>
<summary>🔍 View Step-by-Step Solution</summary>

```python
import threading
import time
import numpy as np

def python_cpu_work(n: int) -> float:
    """Pure Python — GIL held the entire time."""
    total = 0.0
    for i in range(n):
        total += i ** 0.5
    return total

def numpy_cpu_work(n: int) -> float:
    """NumPy — GIL released during C computation."""
    arr = np.arange(n, dtype=np.float64)
    return float(np.sqrt(arr).sum())

def benchmark(func, n, num_threads):
    threads = [threading.Thread(target=func, args=(n,)) for _ in range(num_threads)]
    start = time.perf_counter()
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return time.perf_counter() - start

n = 10_000_000
# Pure Python: threading SLOWER than sequential (GIL contention)
print(f"Python sequential: {benchmark(python_cpu_work, n, 1):.3f}s")
print(f"Python 4 threads:  {benchmark(python_cpu_work, n, 4):.3f}s")  # ~Same or worse!

# NumPy: threading gives real speedup (GIL released)
print(f"NumPy sequential:  {benchmark(numpy_cpu_work, n, 1):.3f}s")
print(f"NumPy 4 threads:   {benchmark(numpy_cpu_work, n, 4):.3f}s")  # ~4x faster!
```

## 💻 5. Code Patterns & Idioms

### Pattern 1.4.1 — Async Context Manager

```python
from contextlib import asynccontextmanager
from typing import AsyncIterator

@asynccontextmanager
async def managed_connection(url: str) -> AsyncIterator["Connection"]:
    conn = await connect(url)
    try:
        yield conn
    finally:
        await conn.close()

async def main():
    async with managed_connection("redis://localhost") as conn:
        await conn.set("key", "value")
```

### Pattern 1.4.2 — Thread-Safe Singleton with Lock

```python
import threading

class ThreadSafeDB:
    _instance: "ThreadSafeDB | None" = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:
            with cls._lock:
                if cls._instance is None:  # Double-check
                    cls._instance = super().__new__(cls)
        return cls._instance
```

## ⚠️ 6. Gotchas & Anti-Patterns

### Gotcha 1.4.1 — Blocking in async Code

```python
# BAD: Blocks the entire event loop!
async def bad():
    time.sleep(5)  # Synchronous sleep — freezes all tasks
    data = requests.get(url)  # Synchronous HTTP — freezes all tasks

# GOOD: Use async equivalents
async def good():
    await asyncio.sleep(5)
    async with httpx.AsyncClient() as client:
        data = await client.get(url)
```

### Gotcha 1.4.2 — Race Conditions with Shared State

```python
# BAD: Race condition even with GIL (bytecode interleaving)
counter = 0
def increment():
    global counter
    for _ in range(1_000_000):
        counter += 1  # NOT atomic! (LOAD, ADD, STORE = 3 bytecodes)

# GOOD: Use a Lock
lock = threading.Lock()
def safe_increment():
    global counter
    for _ in range(1_000_000):
        with lock:
            counter += 1
```

### Example 9.1 — asyncio.gather vs asyncio.TaskGroup: Migration Guide

**Problem:** `asyncio.gather()` has been the standard way to run concurrent coroutines since Python 3.4. Python 3.11 introduced `asyncio.TaskGroup` (from the Trio nursery concept) with structured concurrency guarantees. Demonstrate the behavioral differences, show a migration path, and explain when each is appropriate.

<details>
<summary>🔍 Full step-by-step solution</summary>

#### Step 1: The Fundamental Difference

`asyncio.gather()` is **unstructured** — if one task fails, other tasks may continue running (depending on `return_exceptions`). `TaskGroup` is **structured** — if any task raises, ALL other tasks in the group are cancelled, and the exception propagates after all tasks finish.

```python
import asyncio
import random

async def flaky_api_call(name: str, fail_chance: float = 0.3) -> str:
    """Simulates an API call that might fail."""
    await asyncio.sleep(random.uniform(0.1, 0.5))
    if random.random() < fail_chance:
        raise ConnectionError(f"{name}: connection refused")
    return f"{name}: success"
```

#### Step 2: The gather() Approach (Old Way)

```python
async def fetch_all_gather(endpoints: list[str]) -> list[str]:
    """
    Problem with gather + return_exceptions=False (default):
    - First exception cancels gather, but other tasks may have side effects
    - No guarantee all tasks are cleaned up
    
    Problem with gather + return_exceptions=True:
    - Exceptions are silently mixed into results
    - Caller must manually check each result's type
    """
    # Approach A: return_exceptions=False (default)
    # Raises on first failure, but other tasks keep running briefly
    try:
        results = await asyncio.gather(
            *[flaky_api_call(ep) for ep in endpoints]
        )
        return results
    except ConnectionError as e:
        print(f"One failed: {e}")
        # Other tasks may still be running! No cleanup guarantee.
        return []

    # Approach B: return_exceptions=True
    # results = await asyncio.gather(
    #     *[flaky_api_call(ep) for ep in endpoints],
    #     return_exceptions=True
    # )
    # # results is a mix of strings and exceptions — ugly to handle
    # successes = [r for r in results if isinstance(r, str)]
    # failures = [r for r in results if isinstance(r, Exception)]
```

#### Step 3: The TaskGroup Approach (Python 3.11+)

```python
async def fetch_all_taskgroup(endpoints: list[str]) -> list[str]:
    """
    Structured concurrency with TaskGroup:
    - If ANY task fails, ALL others are cancelled
    - ExceptionGroup collects ALL exceptions (not just the first)
    - Guaranteed: no orphaned tasks after the `async with` block
    """
    results: list[str] = []

    try:
        async with asyncio.TaskGroup() as tg:
            tasks = [
                tg.create_task(flaky_api_call(ep))
                for ep in endpoints
            ]
        # If we reach here, ALL tasks succeeded
        results = [t.result() for t in tasks]

    except* ConnectionError as eg:
        # ExceptionGroup handling (PEP 654, Python 3.11)
        # `eg` contains ALL ConnectionErrors from failed tasks
        print(f"{len(eg.exceptions)} endpoints failed:")
        for exc in eg.exceptions:
            print(f"  - {exc}")
        # All other tasks were already cancelled — no orphans

    return results
```

#### Step 4: Key Behavioral Differences

```python
async def demonstrate_cancellation():
    """Show that TaskGroup cancels siblings on failure."""

    async def slow_task(name: str) -> str:
        try:
            await asyncio.sleep(10)  # Long-running
            return f"{name} done"
        except asyncio.CancelledError:
            print(f"  {name} was CANCELLED (cleanup happening)")
            raise  # Must re-raise CancelledError

    async def fast_failure() -> str:
        await asyncio.sleep(0.1)
        raise ValueError("fast failure!")

    print("=== TaskGroup: sibling cancellation ===")
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(slow_task("worker-1"))
            tg.create_task(slow_task("worker-2"))
            tg.create_task(fast_failure())  # Fails after 0.1s
    except* ValueError:
        print("  All tasks cleaned up, group exited")
    # Output:
    #   worker-1 was CANCELLED (cleanup happening)
    #   worker-2 was CANCELLED (cleanup happening)
    #   All tasks cleaned up, group exited

asyncio.run(demonstrate_cancellation())
```

#### Step 5: Migration Decision Matrix

| Scenario | Use `gather()` | Use `TaskGroup` |
|----------|---------------|-----------------|
| All tasks must succeed or all fail | ❌ | ✅ |
| Partial results acceptable | ✅ (`return_exceptions=True`) | ❌ |
| Need to handle multiple exception types | ❌ (only first) | ✅ (`except*`) |
| Python < 3.11 | ✅ (only option) | ❌ |
| Fire-and-forget background tasks | ✅ | ❌ (all must complete) |
| Resource cleanup guaranteed | ❌ | ✅ |

**Final Answer:**

```python
# Migration rule of thumb:
# - New code (Python 3.11+): Always prefer TaskGroup
# - Existing gather() code: Migrate when you need:
#   1. Guaranteed cancellation of siblings on failure
#   2. ExceptionGroup for multi-error handling
#   3. No orphaned tasks (structured concurrency)
# - Keep gather() when you need partial results or fire-and-forget semantics
```

### Example 9.2 — multiprocessing.Manager: Shared State Across Processes

**Problem:** You need to share a dictionary and a counter across 8 worker processes that are processing items from a queue. Demonstrate `multiprocessing.Manager` for shared state, compare with `multiprocessing.Value`/`Array`, and show the performance implications.

<details>
<summary>🔍 Full step-by-step solution</summary>

#### Step 1: The Problem with Shared State

```python
import multiprocessing as mp
from multiprocessing import Manager, Process, Value, Lock
import time
from typing import Any

# Processes have SEPARATE memory spaces (unlike threads).
# A regular dict in the parent is NOT visible to children.
# Three approaches to share state:
# 1. Manager (proxy objects over IPC) — flexible but slow
# 2. Value/Array (shared memory) — fast but limited types
# 3. SharedMemory (Python 3.8+) — fastest, raw bytes
```

#### Step 2: Manager Approach (Flexible)

```python
def worker_with_manager(
    worker_id: int,
    shared_dict: dict,
    shared_counter: Any,  # Manager.Value
    items: list[int],
    lock: Any,
):
    """Process items and update shared state via Manager proxies."""
    local_count = 0
    for item in items:
        # Simulate processing
        result = item ** 2
        
        # Update shared dict (each operation is an IPC call!)
        shared_dict[f"worker_{worker_id}_item_{item}"] = result
        local_count += 1

    # Update shared counter atomically
    with lock:
        shared_counter.value += local_count


def run_manager_approach(data: list[int], num_workers: int = 8):
    """Coordinate workers with Manager-based shared state."""
    chunk_size = len(data) // num_workers

    with Manager() as manager:
        shared_dict = manager.dict()      # Proxy dict (IPC per operation)
        shared_counter = manager.Value("i", 0)  # Proxy int
        lock = manager.Lock()

        processes = []
        for i in range(num_workers):
            chunk = data[i * chunk_size : (i + 1) * chunk_size]
            p = Process(
                target=worker_with_manager,
                args=(i, shared_dict, shared_counter, chunk, lock),
            )
            processes.append(p)
            p.start()

        for p in processes:
            p.join()

        print(f"Manager approach: {shared_counter.value} items processed")
        print(f"Dict size: {len(shared_dict)}")
        return dict(shared_dict)  # Convert proxy to regular dict
```

#### Step 3: Value/Array Approach (Fast, Limited)

```python
def worker_with_value(
    worker_id: int,
    counter: Value,
    results_array: mp.Array,
    items: list[int],
    offset: int,
):
    """Use shared memory directly — much faster than Manager."""
    for i, item in enumerate(items):
        result = item ** 2
        results_array[offset + i] = result  # Direct shared memory write

    # Atomic increment (Value has built-in lock)
    with counter.get_lock():
        counter.value += len(items)


def run_value_approach(data: list[int], num_workers: int = 8):
    """Coordinate workers with shared memory Value/Array."""
    chunk_size = len(data) // num_workers

    counter = Value("i", 0)  # Shared int in shared memory
    results = mp.Array("i", len(data))  # Shared int array

    processes = []
    for i in range(num_workers):
        chunk = data[i * chunk_size : (i + 1) * chunk_size]
        p = Process(
            target=worker_with_value,
            args=(i, counter, results, chunk, i * chunk_size),
        )
        processes.append(p)
        p.start()

    for p in processes:
        p.join()

    print(f"Value/Array approach: {counter.value} items processed")
    return list(results)
```

#### Step 4: Performance Comparison

```python
def benchmark():
    data = list(range(100_000))

    start = time.perf_counter()
    run_manager_approach(data)
    manager_time = time.perf_counter() - start

    start = time.perf_counter()
    run_value_approach(data)
    value_time = time.perf_counter() - start

    print(f"\nManager: {manager_time:.3f}s")
    print(f"Value/Array: {value_time:.3f}s")
    print(f"Speedup: {manager_time / value_time:.1f}x")
    # Typical result: Value/Array is 10-50x faster than Manager
    # Because Manager uses IPC (socket) for EVERY dict operation

# benchmark()
```

#### Step 5: When to Use Each

| Approach | Speed | Flexibility | Use Case |
|----------|-------|-------------|----------|
| `Manager.dict()` | Slow (IPC per op) | Any Python object | Complex shared state, infrequent updates |
| `Value`/`Array` | Fast (shared mem) | C types only (int, float, char) | Counters, fixed-size numeric arrays |
| `SharedMemory` | Fastest (raw) | Raw bytes (manual serialization) | Large arrays, NumPy interop |
| `Queue`/`Pipe` | Medium | Any picklable | Message passing (preferred pattern) |

**Final Answer:**

```python
# Prefer message passing (Queue/Pipe) over shared state.
# If you must share state:
#   - Few updates, complex types → Manager
#   - Many updates, numeric types → Value/Array
#   - Large numeric arrays → SharedMemory + numpy
# Always protect shared state with locks for read-modify-write operations.
```

### Example 9.3 — The GIL Deep Dive: When It Helps, When It Hurts, and How to Work Around It

**Problem:** Explain the Global Interpreter Lock (GIL) at the C level, demonstrate exactly when it releases, benchmark CPU-bound vs I/O-bound threading, and show the three escape hatches (multiprocessing, C extensions, subinterpreters).

<details>
<summary>🔍 Full step-by-step solution</summary>

#### Step 1: What the GIL Actually Is

```python
# The GIL is a mutex (mutual exclusion lock) in CPython that protects
# access to Python objects. Only ONE thread can execute Python bytecode
# at any time, even on a 64-core machine.

# WHY it exists:
# 1. CPython uses reference counting for GC. Without the GIL, every
#    Py_INCREF/Py_DECREF would need atomic operations (expensive).
# 2. Many C extension modules assume single-threaded access to Python objects.
# 3. It simplifies the CPython implementation enormously.

# The GIL is NOT:
# - A per-object lock (it's global)
# - Present in all Python implementations (Jython, IronPython don't have it)
# - A language feature (it's a CPython implementation detail)
```

#### Step 2: When the GIL Releases

```python
import threading
import time
import hashlib

# The GIL releases during:
# 1. I/O operations (file read/write, network, sleep)
# 2. Certain C extension calls (numpy operations, hashlib, regex)
# 3. Every N bytecode instructions (sys.getswitchinterval(), default 5ms)

def io_bound_task(n: int) -> None:
    """GIL released during sleep — threads run truly concurrently."""
    for _ in range(n):
        time.sleep(0.001)  # GIL released here

def cpu_bound_task(n: int) -> int:
    """GIL held during pure Python computation — threads serialize."""
    total = 0
    for i in range(n):
        total += i * i  # Pure Python bytecode — GIL held
    return total

def c_extension_task(n: int) -> None:
    """GIL released during C extension work (hashlib)."""
    data = b"x" * 10_000_000
    for _ in range(n):
        hashlib.sha256(data)  # GIL released during C computation


def benchmark_threading(task, args, num_threads=4, label=""):
    """Run task in threads and measure wall-clock time."""
    start = time.perf_counter()
    threads = [threading.Thread(target=task, args=args) for _ in range(num_threads)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    elapsed = time.perf_counter() - start
    print(f"{label:30s}: {elapsed:.3f}s ({num_threads} threads)")


def benchmark_sequential(task, args, num_threads=4, label=""):
    """Run task sequentially for comparison."""
    start = time.perf_counter()
    for _ in range(num_threads):
        task(*args)
    elapsed = time.perf_counter() - start
    print(f"{label:30s}: {elapsed:.3f}s (sequential)")


# Results (typical, 4-core machine):
# I/O-bound (sleep):
#   Sequential: 4.0s | Threaded: 1.0s → 4x speedup ✅
# CPU-bound (pure Python):
#   Sequential: 2.0s | Threaded: 2.5s → SLOWER (GIL contention) ❌
# C-extension (hashlib):
#   Sequential: 3.0s | Threaded: 0.8s → 3.7x speedup ✅
```

#### Step 3: Escape Hatch 1 — multiprocessing

```python

    """Each process has its own GIL — true parallelism."""
    return sum(i * i for i in range(n))

def parallel_cpu_work():
    """Use process pool for CPU-bound work."""
    with Pool(processes=4) as pool:
        # Each worker is a separate process with its own GIL
        results = pool.map(cpu_intensive, [10_000_000] * 4)
    return results
    # True 4x speedup on 4 cores (minus IPC overhead)
```

## 📘 10. Appendix: Extended Derivations & Special Cases

### 10.1 PEP 703 (No-GIL / Free-Threaded Python) — Status and Implications

PEP 703, authored by Sam Gross, proposes making the GIL optional in CPython. After years of development, Python 3.13 (October 2024) shipped the first experimental free-threaded build (`python3.13t`). Here's what changed and what it means.

**The Technical Challenge:**

Removing the GIL requires replacing reference counting with thread-safe alternatives. PEP 703's approach:

1. **Biased reference counting:** Objects are "owned" by the thread that created them. The owning thread uses fast, non-atomic increments/decrements. Other threads use atomic operations. When the owning thread's count reaches zero, it checks if other threads hold references.

2. **Deferred reference counting:** Certain high-frequency objects (module globals, type objects) use deferred counting — their refcount is only checked during GC pauses, not on every access.

3. **Immortalization:** Objects that live forever (`None`, `True`, small ints) have a special refcount that's never modified — eliminating all contention for the most-accessed objects.

4. **Per-object locks:** Instead of one global lock, fine-grained locking protects individual objects. CPython 3.13t uses a combination of:
   - Critical sections (lightweight, non-recursive locks)
   - `dict` and `list` have their own internal locks
   - The GC uses stop-the-world pauses (rare, short)

**Performance Impact (Python 3.13t benchmarks):**

| Workload | GIL build | Free-threaded (1 thread) | Free-threaded (4 threads) |
|----------|-----------|--------------------------|---------------------------|
| Single-threaded Python | 1.00x | 0.90-0.95x (5-10% slower) | N/A |
| CPU-bound, 4 threads | 1.00x (serialized) | N/A | 3.2-3.8x speedup |
| I/O-bound, 4 threads | ~4x (already parallel) | ~4x | ~4x |

The single-threaded regression comes from: atomic operations on refcounts, per-object lock acquisition, and disabled specializing adaptive interpreter optimizations.

**What Breaks:**

- C extensions using `Py_INCREF`/`Py_DECREF` without holding the GIL → crash
- Code relying on the GIL for thread safety (common in older C extensions)
- `ctypes` callbacks that assume single-threaded execution

**Timeline:**

- Python 3.13 (2024): Experimental `--disable-gil` build flag
- Python 3.14 (2025): Improved stability, more C extensions compatible
- Python 3.15+ (2026+): Potential default (if ecosystem ready)

**Practical Advice:**

```python
import sys

def check_free_threaded():
    """Check if running on free-threaded build."""
    # Python 3.13+
    if hasattr(sys, "_is_gil_enabled"):
        gil_enabled = sys._is_gil_enabled()
        print(f"GIL enabled: {gil_enabled}")
        if not gil_enabled:
            print("Running FREE-THREADED Python!")
    else:
        print("Python < 3.13 — GIL always enabled")
```

### 10.2 The CPython Subinterpreter Model (PEP 684)

Subinterpreters provide isolated Python execution environments within a single process. Each subinterpreter has its own:
- Module namespace (`sys.modules`)
- Import state
- GIL (since Python 3.12, per-interpreter GIL via PEP 684)

**How They Differ from Threads and Processes:**

| Property | Thread | Subinterpreter | Process |
|----------|--------|----------------|---------|
| Memory space | Shared | Shared (with restrictions) | Separate |
| GIL | Shared (one GIL) | Separate (per-interp GIL) | Separate |
| Communication | Direct object sharing | Channels (copy semantics) | IPC (pickle) |
| Startup cost | ~100μs | ~1ms | ~50ms |
| Memory overhead | ~8KB stack | ~2MB (module state) | ~30MB (full process) |

**The Communication Challenge:**

Subinterpreters cannot share Python objects directly (each has its own object space). Communication uses channels that copy data:

```python
# Conceptual API (Python 3.13+):
# import interpreters
# 
# interp = interpreters.create()
# 
# # Send data via channel (serialized, not shared)
# channel = interpreters.create_channel()
# channel.send(b"hello")  # bytes, int, float, str, None only
# 
# interp.exec("""
# import interpreters
# data = channel.recv()  # Receives copy
# result = process(data)
# channel.send(result)
# """)
```

**Use Cases:**

1. **Plugin isolation:** Run untrusted plugins in subinterpreters — they can't corrupt the main interpreter's state
2. **Per-request isolation:** Web servers can use one subinterpreter per request (like PHP's process-per-request model, but lighter)
3. **True parallelism without multiprocessing:** Each subinterpreter has its own GIL, so CPU-bound work in different subinterpreters runs in parallel on different cores

**Current Limitations (Python 3.13):**

- Many C extensions don't support subinterpreters (they use global state)
- NumPy, most of the scientific stack: NOT compatible yet
- The API is still evolving and considered experimental
- Only basic types can cross interpreter boundaries

**Future Vision:**

The long-term plan is for subinterpreters to replace multiprocessing for many use cases — providing process-like isolation with thread-like performance. Combined with PEP 703 (no-GIL), Python's concurrency story will eventually offer: threads (shared memory, no GIL), subinterpreters (isolated memory, parallel), and processes (maximum isolation, maximum overhead).
