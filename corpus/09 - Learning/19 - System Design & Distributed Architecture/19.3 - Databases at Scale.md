# 19.3 — Databases at Scale

> *"A modern Postgres on a single big box handles 100 k QPS for almost everyone. The mistake is sharding before you've actually filled the box."*

By 2026 the default playbook is: **scale up Postgres** → **add a read replica** → **add a cache** → **(only then) shard or pick a NewSQL system**. This chapter teaches the whole staircase and the *exits* off it (vector DBs for embeddings, OLAP warehouses for analytics, time-series DBs for metrics).

---

## 🎯 Learning Objectives

1. Differentiate **OLTP**, **OLAP**, **HTAP** workloads and pick the right system.
2. Use **read replicas** safely (replica lag, read-your-writes pitfalls).
3. Choose between **range**, **hash**, and **directory-based** sharding with their failure modes.
4. Compare **NewSQL** systems: CockroachDB, YugabyteDB, TiDB, Spanner — and know when *none* is the answer.
5. Pick a **vector database** (pgvector, Pinecone, Qdrant, Weaviate, Milvus, Chroma) for a given workload.
6. Pick a **time-series** database (TimescaleDB, InfluxDB, ClickHouse, Prometheus) for metrics, IoT, or finance.
7. Recognize when the answer is "stay in Postgres" vs "leave Postgres".

## 📚 1. OLTP vs OLAP vs HTAP

| Workload | Pattern | Typical store |
|---|---|---|
| **OLTP** (transactions) | Many small reads/writes; row-oriented; latency-sensitive | Postgres, MySQL, CockroachDB, Yugabyte, TiDB OLTP path |
| **OLAP** (analytics) | Few large scans; column-oriented; throughput-sensitive | Snowflake, BigQuery, Redshift, ClickHouse, DuckDB |
| **HTAP** (hybrid) | Both, on the same data, no ETL | TiDB (TiKV + TiFlash), SingleStore, recent Postgres + Citus + Hydra |

**Default rule:** OLTP in Postgres; OLAP in BigQuery or DuckDB or ClickHouse; HTAP only when you genuinely cannot ETL.

## 📚 2. Replication

### Leader–follower (single-leader)
One node accepts writes; followers replicate asynchronously (default Postgres) or synchronously. Reads can go to followers (eventually consistent) or leader (linearizable on the leader).

**Pitfall — read-your-writes:** a user writes, then reads from a follower lagging by 200 ms, sees old data. Fix: route same-user reads to leader for N seconds after a write, or use **logical replication slots** + **bounded staleness**.

### Multi-leader
Each region accepts writes; conflicts must be resolved (last-writer-wins, CRDTs, application logic). Used in geo-distributed setups.

### Leaderless (Dynamo-style)
Cassandra, Riak, DynamoDB. Quorum reads/writes (R + W > N → strong-ish). Application gets to feel the trade-offs directly.

## 📚 3. Sharding (a.k.a. Horizontal Partitioning)

| Strategy | How keys map to shards | Strength | Weakness |
|---|---|---|---|
| **Range** | `[a-f] → s0`, `[g-m] → s1` | Range scans cheap | Hot ranges (recent dates!) |
| **Hash** | `hash(key) mod N` | Even distribution | Range scans expensive; resharding hard |
| **Consistent hash** | hash → ring; nodes own arcs | Resharding minimally moves data | More complex |
| **Directory** | Lookup table key → shard | Maximum flexibility | Lookup table itself must scale |
| **Geo** | Shard by region | Locality | Cross-region queries painful |

**The first rule of sharding:** *don't*. The second rule: **shard on a key the application already filters on** — otherwise every query becomes a scatter-gather.

## 📚 4. NewSQL — Distributed SQL in 2026

> CockroachDB offers the best PostgreSQL wire compatibility and a mature self-hosted path; Spanner delivers unmatched global consistency via TrueTime but is GCP-only and expensive at scale; YugabyteDB also runs on the Postgres wire and competes on operational simplicity. — paraphrased from [jusdb — CockroachDB vs Spanner vs YugabyteDB](https://www.jusdb.com/blog/cockroachdb-vs-spanner-vs-yugabytedb-newsql). Content rephrased for compliance.

> Choose TiDB if you are MySQL-first and need scale-out writes/storage without app-owned sharding, with optional HTAP via TiKV + TiFlash; choose CockroachDB if you are Postgres-first and prioritize multi-region locality. — paraphrased from [pingcap — CockroachDB vs TiDB](https://pingcap.com/compare/cockroachdb-vs-tidb). Content rephrased for compliance.

| System | Wire protocol | Consensus | Strengths |
|---|---|---|---|
| **CockroachDB** | Postgres | Raft (per range) | Postgres-compat, multi-region locality, self-hostable |
| **YugabyteDB** | Postgres + Cassandra | Raft | Lower CPU overhead, simpler operator |
| **TiDB** | MySQL | Raft (TiKV) + columnar TiFlash | HTAP, MySQL ecosystem |
| **Google Spanner** | Custom + Postgres dialect | TrueTime + Paxos | Unmatched global consistency; GCP-only |
| **Amazon Aurora** | Postgres / MySQL | Custom storage layer; not a true distributed SQL | Best for AWS single-region scale |
| **Azure Cosmos DB** | Many | Multi-model | Azure-tied; tunable consistency |

**The honest 2026 default:** start in Postgres; only graduate to NewSQL when you hit a wall the cache + replicas + sharding can't fix, **or** when you actually need active-active across regions.

## 📚 5. Vector Databases

> Pinecone (managed leader), Qdrant (Rust-based open-source speed leader), Weaviate (hybrid + GraphQL), Milvus (large-scale), Chroma (developer-experience leader), pgvector (Postgres-integrated default), plus Vertex Vector and Vespa for hyperscale. — paraphrased from [digitalapplied — Vector DBs 2026](https://www.digitalapplied.com/blog/vector-databases-for-ai-agents-pinecone-qdrant-2026). Content rephrased for compliance.

| Pick | When |
|---|---|
| **pgvector** | You're already on Postgres and have under ~10 M vectors — keep it simple |
| **Qdrant** | Self-hosted, lowest-latency, Rust-native |
| **Pinecone** | Fully managed, scale, willing to pay per dimension stored |
| **Weaviate** | Hybrid keyword + vector search; multi-modal |
| **Milvus** | You crossed the billion-vector mark |
| **Chroma** | Best DX for prototyping, especially with LangChain |
| **Vespa** | Hybrid at hyperscale (Yahoo / Spotify lineage) |

> Practical rule: pgvector under 10 M; Qdrant for self-hosted speed; Pinecone for managed scale; Weaviate for hybrid; Milvus past a billion. — paraphrased from [singhajit — Vector DB deep dive](https://singhajit.com/vector-database-deep-dive/) and [jusdb — pgvector vs Pinecone vs Weaviate](https://www.jusdb.com/blog/vector-databases-comparison-pgvector-pinecone-weaviate). Content rephrased for compliance.

Cross-link: vector DBs are central to RAG and embeddings; see [[../23 - AI & Machine Learning Systems/Subject_Plan]] for the upstream training and embedding pipelines that feed them.

## 📚 6. Time-Series & Append-Only Workloads

| System | Strengths |
|---|---|
| **TimescaleDB** | Postgres extension; SQL + hypertables + continuous aggregates |
| **InfluxDB** | Purpose-built TSDB; Flux query language |
| **ClickHouse** | Column-store; absurd scan speed; analytics + time series |
| **Prometheus** | Metrics + service discovery; not a long-term store |
| **VictoriaMetrics** | Prometheus-compatible long-term store |
| **QuestDB** | Low-latency time series with SQL |

For most engineering metrics: **Prometheus + Grafana + VictoriaMetrics for retention**. For business time-series and IoT: **TimescaleDB or ClickHouse**.

## 🛠️ 7. Worked Example — From Single Postgres to Multi-Region

A SaaS hits 50 M users in one region; expansion to EU + APAC requires sub-100 ms latency for writes everywhere.

**Step 0:** Confirm caching ([[19.2 - Caching, CDNs & Edge|19.2]]) is exhausted. It is.

**Step 1 — Read scaling:** add Postgres read replicas in each region. Application routes reads to nearest replica; writes still go to primary in us-east-1.
- *Cost*: writes from EU still pay 100 ms RTT.
- *Win*: most reads now <30 ms.

**Step 2 — Decision point:**
- **Path A (cheap):** stay on Postgres + region-local read replicas; accept write latency for non-EU users. Many companies do this until they're told no.
- **Path B (NewSQL):** migrate to **CockroachDB** with **regional-by-row** tables — each row's leaseholder lives in the user's home region. p99 writes drop to ~5 ms in-region.
- **Path C (sharded):** application-level region sharding — each region has its own Postgres; cross-region queries via federated views or async replication. Cheaper than CockroachDB but uglier.

**Step 3 — Vector workload:** the SaaS adds RAG. Embeddings live in **pgvector** while small (<10 M); migrate to **Qdrant** when latency budget tightens.

**Step 4 — Analytics:** stop running BI queries on the OLTP store. Pipe CDC (Debezium → Kafka) into **ClickHouse** or **BigQuery** for analyst self-service.

The lesson: **don't pick the shiny database first**. Identify the bottleneck, exhaust the cheap fix, and only then pay the migration cost.

## ⚠️ 9. Common Misconceptions

- **"NoSQL is faster than SQL."** Apples and onions. Modern Postgres beats most NoSQL for OLTP under 100 k QPS.
- **"Sharding is a scaling solution."** Sharding is a *cost* you pay to keep scaling; it doesn't make a query plan faster — it just lets you have more copies of the box.
- **"Distributed SQL = free scale."** It costs latency on every write (consensus) and complicates schema migrations and backups.
- **"Vector DB = required for RAG."** pgvector inside Postgres is enough until ~10 M vectors. Don't add a system you don't need.
- **"Eventual consistency is bad."** It's *appropriate* for analytics, recommendations, and most read paths. Strong consistency is the exception, not the default.
