# 19.8 — Capacity Planning & Back-of-Envelope Math

> *"Without numbers, every architecture argument is theology. With numbers, even the wrong answer is useful — you can refute it."*

This chapter is the math behind every claim in the previous seven. **Little's Law** for throughput vs concurrency. **Percentiles** because the average lies. The **Universal Scalability Law** because doubling the cluster does not double the capacity. And the load-testing tools (**k6, Locust, Gatling, vegeta, JMeter**) you use to find the truth before users do.

---

## 🎯 Learning Objectives

1. Apply **Little's Law** to relate throughput, concurrency, and latency.
2. Read **p50 / p95 / p99 / p999** latency curves and explain why averages are dangerous.
3. State the **Universal Scalability Law (USL)** and identify the contention vs coherence terms.
4. Pick a load-testing tool: **k6**, **Locust**, **Gatling**, **vegeta**, or **JMeter**, by team and workload.
5. Build a **growth model** — back-of-envelope for 10×, 100×, 1000× traffic scenarios.
6. Establish **SLOs** (objectives), **SLIs** (indicators), and **error budgets** for a service.

## 📚 1. Little's Law

For any stable system in steady state:

$$
L = \lambda \cdot W
$$

- **L** = average number of items in the system (concurrency).
- **λ** (lambda) = average arrival rate (throughput, RPS).
- **W** = average time an item spends in the system (latency).

**Consequence:** if your service handles 1000 RPS with average latency 200 ms, average concurrency is `1000 × 0.2 = 200` requests in flight. To handle 10× the RPS at the same latency you need to support 10× concurrency — i.e. 10× threads / file descriptors / DB connections. **This is why connection pooling matters more than CPU.**

## 📚 2. Percentiles — Why Averages Lie

> Slapping "99.9% availability" and "sub-200 ms p99 latency" in a contract sounds great until someone asks for the numbers. Load testing gives you that proof before your users do it for you. — paraphrased from [bitslovers — Load testing on AWS](https://www.bitslovers.com/load-testing-aws-k6-locust-guide/). Content rephrased for compliance.

> Look at p50/p95/p99 latency, error rate, and throughput together — never just an average. The framework gives you the metrics surface; the test is your responsibility. — paraphrased from [gofr.dev — Load testing](https://gofr.dev/docs/guides/load-testing). Content rephrased for compliance.

| Percentile | What it means | Why it matters |
|---|---|---|
| **p50** | Median; half users faster, half slower | Typical-case feel |
| **p95** | 5% of users see worse | "Good days" experience |
| **p99** | 1% of users see worse | What you ship in SLOs |
| **p999** | 1 in 1000 | Why a hot key kills retention |
| **p9999** | 1 in 10 000 | Where head-of-line blocking lives |

A p50 of 50 ms and p99 of 5 s means **1 in 100 requests is 100× slower than typical**. If a session makes 100 requests, almost every session sees that slowness somewhere. **Tail latency is the user experience.**

**Coordinated omission** is the most-ignored measurement bug: when a load generator slows down because the server is slow, it stops *recording* the slowness. Use **HdrHistogram**-aware tools (k6, vegeta, wrk2, Gatling) that don't omit.

## 📚 3. Universal Scalability Law (USL)

Neil Gunther's USL models capacity vs concurrency:

$$
C(N) = \frac{N}{1 + \alpha (N-1) + \beta N (N-1)}
$$

- **N** = number of concurrent workers (or nodes).
- **α** (alpha) = **contention** — serialized portions (locks, single leader).
- **β** (beta) = **coherence** — cross-node coordination cost (consensus, cache coherence).

| Term | Behavior |
|---|---|
| α only (β=0) | Amdahl's Law — ceiling at `1/α` |
| α + β > 0 | **Capacity peaks then drops** as you add nodes |

The USL explains why doubling the cluster sometimes makes things worse — coherence cost outpaces contention reduction. Measure α and β by load testing across cluster sizes; the fit tells you whether to throw nodes at the problem or fix the lock.

## 📚 4. The 2026 Load Testing Toolset

> Top picks for 2026: TestSprite, Apache JMeter, k6, Gatling, Locust. — paraphrased from [testsprite — Best load testing tools 2026](https://testsprite.com/use-cases/en/the-best-load-testing-tools). Content rephrased for compliance.

> Choosing a performance testing tool is mostly a choice about how much complexity you take on; some tools generate enormous distributed load but demand real expertise; others are simple to start with but cap out early. — paraphrased from [apidog — Software performance testing tools](https://apidog.com/blog/software-performance-testing-tool/). Content rephrased for compliance.

| Tool | Language | Strengths | Trade-offs |
|---|---|---|---|
| **k6** (Grafana) | Go core, JS scripts | Modern DX, CI-friendly, great percentile reporting, Cloud-native | Single-binary by default; cluster mode is paid Cloud or k6-operator |
| **Locust** | Python | Code-first, distributed mode, easy to integrate with custom auth | Single-CPU per worker (use distributed mode for scale) |
| **Gatling** | Scala / Java DSL | Excellent reports, scenario chaining, recent JS DSL | JVM warm-up; steeper learning curve |
| **vegeta** | Go | Tiny, scriptable, great HdrHistogram output | HTTP only; no UI |
| **Apache JMeter** | Java GUI | Mature, plugin ecosystem, distributed | GUI-heavy; not CI-native |
| **wrk / wrk2** | C | Fastest single-machine load gen; wrk2 fixes coordinated omission | Plain HTTP only |
| **k6 LLM extensions / FutureAGI / Apidog** | Various | Token-aware load testing for LLM APIs | Niche but vital in 2026 |

**2026 default:** **k6** for most teams — the JS scripting + Grafana reporting + CI-friendly binary is the right developer experience. Locust if your team is Python-native and needs custom logic. Gatling for high-end perf engineering shops.

## 📚 5. Growth Modelling — The 10× / 100× / 1000× Spreadsheet

For each major component, fill:

| Component | Today (1×) | 10× (1 yr) | 100× (3 yr) | 1000× (5 yr) |
|---|---|---|---|---|
| RPS peak | 1 k | 10 k | 100 k | 1 M |
| DB QPS | 5 k | 50 k | 500 k | 5 M |
| Cache QPS | 30 k | 300 k | 3 M | 30 M |
| Storage | 100 GB | 1 TB | 10 TB | 100 TB |
| Bandwidth out | 10 MB/s | 100 MB/s | 1 GB/s | 10 GB/s |
| Strategy | single Postgres | + read replicas | + sharding or NewSQL | + region-local writes |

The point of the spreadsheet is not accuracy — it's **forcing the conversation** about which choice fails first. Usually the DB at 100×, the cache at 1000×.

## 📚 6. SLOs / SLIs / Error Budgets

| Term | Meaning |
|---|---|
| **SLI** (Service Level Indicator) | A measured value (e.g. "% of requests with latency < 200 ms") |
| **SLO** (Service Level Objective) | The target on the SLI (e.g. "99.9% of requests under 200 ms over 30 days") |
| **SLA** (Service Level Agreement) | A *contract* with consequences attached to a missed SLO |
| **Error budget** | `1 - SLO` — how much unreliability you can spend before frozen deploys |

Error budgets translate reliability into a *currency* product and engineering can spend together: each minute of downtime debits the budget; if it goes negative, ship fewer risky changes until it recovers.

## 🛠️ 7. Worked Example — Sizing for Launch

**Scenario:** launching a new collaborative SaaS. Marketing predicts 10 k DAU at launch, 100 k DAU within 6 months.

**Step 1 — Per-user load.**
- Avg session: 30 min/day; 60 actions / session; 2 KB / action.
- Peak factor: 5× of avg (lunchtime + evening clusters).

**Step 2 — Throughput math.**
- Daily actions = `100 k × 60 = 6 M`.
- Avg RPS = `6 M / 86400 ≈ 70`.
- Peak RPS = `70 × 5 = 350`.
- Plus real-time updates: assume 10× the action rate as awareness/presence updates → ~3500 small messages/s peak.

**Step 3 — DB load.**
- ~3 DB writes per action → `350 × 3 = 1050` peak DB writes/s. Trivial.
- ~10 DB reads per action with 80% cached → `350 × 10 × 0.2 = 700` peak DB reads/s. Trivial.

**Step 4 — Connection math (Little's Law).**
- WebSocket: 100 k DAU × 20% concurrent = 20 k open connections. Each ~50 KB RAM → 1 GB. One Hocuspocus pod with 4 vCPU + 4 GB.
- HTTP: avg 350 RPS × 100 ms = 35 in flight. Tiny.

**Step 5 — Storage.**
- 100 k users × 5 MB content avg = 500 GB. Postgres on a single 1 TB SSD is fine.

**Step 6 — Verify with k6.**
```js
import http from 'k6/http';
import { sleep, check } from 'k6';
export const options = {
  scenarios: {
    ramp: {
      executor: 'ramping-vus',
      stages: [
        { duration: '2m', target: 50 },   // warm
        { duration: '5m', target: 350 },  // peak
        { duration: '2m', target: 0 },    // cool
      ],
    },
  },
  thresholds: {
    http_req_duration: ['p(99)<500', 'p(95)<200'],
    http_req_failed:   ['rate<0.001'],
  },
};
export default function () {
  const res = http.get('https://staging.example.com/api/feed');
  check(res, { '200': r => r.status === 200 });
  sleep(1);
}
```

Run, watch p99, fix what breaks, repeat at 10×.

## ⚠️ 9. Common Misconceptions

- **"Average latency tells me how fast it is."** No. p99 tells you how fast it is for everyone. Averages hide the bad days.
- **"More machines = more throughput."** Until coherence cost dominates and the USL curve **bends downward**. Measure, don't assume.
- **"I'll load-test before launch."** Load-test in CI on every PR, not just before launch. The bug you find on launch day costs 100× more.
- **"100% reliability is the goal."** No — `1 - SLO` is the *budget* you spend on shipping change. 100% means you stopped shipping.
- **"Bandwidth is free."** Egress on AWS is roughly $0.09/GB. At a large enough scale, bandwidth is your biggest line item; design accordingly.
