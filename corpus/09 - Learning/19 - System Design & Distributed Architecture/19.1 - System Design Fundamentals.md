# 19.1 — System Design Fundamentals

> *"The network is not reliable. Latency is not zero. Bandwidth is not infinite. The network is not secure. Topology doesn't change. There is one administrator. Transport cost is zero. The network is homogeneous."*
> — The **8 Fallacies of Distributed Computing**, Peter Deutsch & James Gosling. Every system design begins by violating exactly one of these and ends by violating most.

This chapter is the **universal layer** under everything that follows — caches ([[19.2 - Caching, CDNs & Edge|19.2]]), databases ([[19.3 - Databases at Scale|19.3]]), queues ([[19.4 - Message Queues & Event-Driven Architecture|19.4]]), APIs ([[19.5 - API Design|19.5]]), microservices ([[19.6 - Microservices & Service Mesh|19.6]]), real-time ([[19.7 - Real-Time Systems|19.7]]), and capacity reasoning ([[19.8 - Capacity Planning & Back-of-Envelope Math|19.8]]). Once these primitives are second nature, every later choice is a small derivation.

---

## 🎯 Learning Objectives

By the end of this chapter you will be able to:

1. State the **CAP theorem** precisely and explain why "pick two" is misleading.
2. State the **PACELC theorem** and place common databases on it (Spanner, DynamoDB, Cassandra, etcd, MongoDB, CockroachDB).
3. Distinguish four consistency models: **linearizable**, **sequential**, **causal**, **eventual**.
4. Recall the **latency numbers** every dev should know — from L1 cache (~0.5 ns) to inter-continental RTT (~150 ms) — within an order of magnitude.
5. Run a **requirements-gathering interview** for a system-design problem (functional / non-functional / constraints / SLOs).
6. Sketch a **back-of-envelope** capacity model for any "design X" prompt in under 10 minutes.

## 📚 1. CAP Theorem

### Definition 19.1.1 — CAP

In a distributed data store, no system can simultaneously provide all three of:

- **C — Consistency**: every read returns the most recent write (linearizable).
- **A — Availability**: every request to a non-failed node returns a non-error response.
- **P — Partition tolerance**: the system continues to operate despite arbitrary message loss between nodes.

> The CAP theorem applies to a distributed data store; it states that under network partitioning, the system must choose between consistency and availability. Linearizability is the strongest consistency model — every read reflects the most recent write, or returns an error. — paraphrased from [kindatechnical — CAP & PACELC](https://kindatechnical.com/database/cap-theorem-pacelc.html). Content was rephrased for compliance with licensing restrictions.

### Why "pick two" is misleading

Network partitions **happen** — switches die, links flap, kernels drop packets. **P is not optional** in any system that crosses machines. So in practice CAP forces a choice between **CP** (consistent but unavailable during partition) and **AP** (available but possibly stale). "CA" is a pre-distribution mythology — a single-machine database.

| System | Reality under partition |
|---|---|
| **etcd**, **ZooKeeper**, **Spanner**, **CockroachDB** | CP — refuse writes on the minority side |
| **DynamoDB**, **Cassandra**, **Riak** | AP — accept writes anywhere; resolve later |
| **MongoDB (default)** | CP — primary-only writes; replica failover |

## 📚 2. PACELC — CAP Refined

CAP describes only the **partitioned** state. Most of the time the network is fine — and a system still has a knob between latency and consistency. **PACELC** extends CAP:

> If there is a partition (P), choose between availability (A) and consistency (C) — else (E), even with no partition, choose between latency (L) and consistency (C). — paraphrased from [Wikipedia — PACELC design principle](https://en.wikipedia.org/wiki/PACELC_design_principle), [thecoder.cafe — PACELC](https://www.thecoder.cafe/p/pacelc), [numberanalytics — Mastering PACELC](https://www.numberanalytics.com/blog/mastering-pacelc-theorem-distributed-systems). Content was rephrased for compliance with licensing restrictions.

| System | PACELC class | Reading |
|---|---|---|
| **Google Spanner** | **PC/EC** | Even normally, prefer consistency (TrueTime cost) |
| **CockroachDB**, **YugabyteDB** | **PC/EC** | Postgres-compatible, multi-region, consistency-first |
| **DynamoDB** (default) | **PA/EL** | Even normally, prefer latency over strong consistency |
| **Cassandra** | **PA/EL** | Tunable, but commonly latency-first |
| **MongoDB** (default) | **PA/EC** | Stale reads from secondaries unless `readConcern: majority` |
| **Riak** | **PA/EL** | Pure Dynamo lineage |
| **VoltDB** | **PC/EC** | In-memory, single-leader-shard |

The honest interview answer is **always "PACELC"**, not just "CAP", because most production traffic is *not* during a partition.

## 📚 3. Four Consistency Models

| Model | Guarantee | Typical workload |
|---|---|---|
| **Linearizable** | Every operation appears to take effect at a single point between its invocation and response, in real-time order | Bank ledgers, leader election, locks |
| **Sequential** | All processes see operations in *some* total order, consistent with each process's own program order | Some replicated state machines |
| **Causal** | Operations causally related (one observed before another) appear in that order; concurrent operations may differ | Group chat, social feeds |
| **Eventual** | Without further updates, all replicas eventually converge — but no order guarantee in the meantime | DNS, Cassandra default, Dynamo |

**Read-your-writes**, **monotonic reads**, and **bounded staleness** are *session* guarantees that sit between linearizable and eventual — see DDIA Ch. 5 for the full taxonomy.

## 📚 4. The Latency Numbers Table

Every dev should know these within an order of magnitude. They drive **every** capacity decision.

| Operation | ~Time | What it implies |
|---|---|---|
| L1 cache reference | 0.5 ns | Single instruction territory |
| Branch mispredict | 5 ns | ~10 instructions wasted |
| L2 cache reference | 7 ns | One CPU bus hop |
| Mutex lock/unlock (uncontended) | 25 ns | Cheap; contention is what costs |
| Main memory reference | 100 ns | 200× L1 |
| Compress 1 KB with Snappy | ~3 µs | Rough — varies |
| Read 1 MB sequentially from RAM | ~250 µs | Bandwidth-bound |
| SSD random read | 150 µs | 1500× RAM |
| Round-trip within data center | 500 µs | The cost of leaving a machine |
| Read 1 MB sequentially from SSD | ~1 ms | 4× sequential RAM read |
| HDD seek | 10 ms | Why HDDs lost OLTP |
| Read 1 MB sequentially from HDD | ~20 ms | Streaming media is fine; OLTP is not |
| Round-trip CA → Netherlands | ~150 ms | Speed of light × geography |

> Source: paraphrased and shortened from [Latency Numbers Every Programmer Should Know](https://gist.github.com/jboner/2841832) (Jeff Dean / jboner gist). Content rephrased for compliance.

**Rule of thumb:** memory is ~100× faster than network-local; network-local is ~100× faster than spinning disk; intercontinental is ~300× a data-center RTT. Most "performance issues" are crossings of one of those boundaries unnecessarily.

## 📚 5. Requirements Gathering — The 4-Box Method

Before any architecture, fill in four boxes with the user / interviewer:

```
┌──────────────────┬──────────────────┐
│ FUNCTIONAL       │ NON-FUNCTIONAL   │
│ - what user does │ - SLOs (p99, %)  │
│ - core entities  │ - read/write mix │
│ - core flows     │ - durability     │
├──────────────────┼──────────────────┤
│ CONSTRAINTS      │ TRAFFIC PROFILE  │
│ - team size      │ - DAU, RPS peak  │
│ - existing tech  │ - data per user  │
│ - cost ceiling   │ - growth trend   │
└──────────────────┴──────────────────┘
```

If you cannot fill **traffic profile** + **SLOs**, you cannot do back-of-envelope, and your design is a guess.

## 🛠️ 6. Worked Example — "Design a URL Shortener"

A canonical interview prompt — minimal but exercises every primitive.

### Step 1 — Requirements
- **Functional:** create short URL from long URL; redirect short → long; analytics (click count).
- **Non-functional:** 99.99% availability for redirects; p99 < 50 ms; 7-day click-count freshness OK.
- **Traffic:** 100 M new URLs/year; 10× reads:writes; peak 10 k RPS reads.
- **Constraints:** small team; AWS preferred.

### Step 2 — Back-of-envelope
- 100 M / year ≈ 3.2 / sec writes (peak ~30/s) — trivial.
- 10× reads → 32/s avg, 10 k peak.
- 100 M URLs × ~500 bytes ≈ 50 GB / year — trivial in Postgres.
- 10 k RPS reads × ~0.5 KB response ≈ 5 MB/s out — trivial.

This is **not a sharding problem**. It's a single-Postgres + cache + CDN problem. Most "system design" failures are **over-architecture**.

### Step 3 — Architecture
1. Single Postgres (with a read replica) — primary holds `(short_id PK, long_url, created_at, owner_id)`.
2. Redis in front of Postgres for hot redirects (cache-aside, TTL = 1 day; see [[19.2 - Caching, CDNs & Edge|19.2]]).
3. Cloudflare in front of the redirect endpoint — most reads never hit your origin.
4. Click counts: fire-and-forget event to a Kafka topic (or SQS); aggregate in a batch job (see [[19.4 - Message Queues & Event-Driven Architecture|19.4]]). 7-day staleness is fine.
5. Short ID generation: base62 of an auto-increment ID, or a Snowflake ID, depending on cross-region needs.

### Step 4 — Where could it fail?
- **Cache stampede on a viral short URL** → request coalescing + TTL jitter (next chapter).
- **Hot key in Redis** → consistent hashing is the wrong fix; **replicate the hot key** across replicas.
- **Postgres write hot row** for a single popular owner → that's a counter, push to Redis or async aggregator.

This is the **CP/EL** flavour for writes (we want consistent short_id allocation) and **AP/EL** for reads (a stale long_url for one second is fine). PACELC tells you the answer is *split*.

## ⚠️ 8. Common Misconceptions

- **"CAP says pick two."** No — *P is forced* by reality, so it's CP-or-AP.
- **"Eventual consistency means weak."** Causal + read-your-writes is more nuanced and often what users actually need.
- **"My system is consistent because I use Postgres."** Single-master Postgres is linearizable on the master; **a read replica is not**.
- **"Latency is bandwidth divided by something."** Latency and bandwidth are independent; high-bandwidth + high-latency satellite links exist and ruin assumptions.
- **"99.99% means 99.99% of users are happy."** It's a measurement of the median across a sample. Tail latency (p99/p999) is what users *feel* on bad days — see [[19.8 - Capacity Planning & Back-of-Envelope Math|19.8]].
