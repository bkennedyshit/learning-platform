# 10.6 — Unity Specifics: MonoBehaviour, Coroutines, ScriptableObjects, ECS

> *"Unity is not a game engine that happens to support C#. It's a C# framework that happens to render games."* — Code Monkey

You'll learn the MonoBehaviour lifecycle that governs every script, coroutines for time-based logic, ScriptableObjects for data-driven design, and DOTS/ECS for when you need 10,000 entities running at 60fps.

## 📚 1. Concepts

### Concept 3.6.1 — MonoBehaviour Lifecycle (Complete)

Every script inheriting `MonoBehaviour` follows this execution order within a frame:

```
┌─── INITIALIZATION (once) ───────────────────────────────────┐
│  Awake()          → Object loaded. Self-init. Runs even if disabled.  │
│  OnEnable()       → Object activated. Subscribe to events here.       │
│  Start()          → Before first Update. Cross-references safe.       │
└─────────────────────────────────────────────────────────────┘

┌─── PHYSICS LOOP (0+ times per frame) ──────────────────────┐
│  FixedUpdate()    → Fixed timestep (default 50Hz).                    │
│                     Physics, forces, raycasts.                         │
│  OnTriggerXxx()   → Trigger callbacks.                                │
│  OnCollisionXxx() → Collision callbacks.                              │
└─────────────────────────────────────────────────────────────┘

┌─── GAME LOGIC (once per frame) ────────────────────────────┐
│  Update()         → Input, game logic, AI decisions.                  │
│  LateUpdate()     → After ALL Updates. Camera follow, IK.            │
└─────────────────────────────────────────────────────────────┘

┌─── RENDERING ──────────────────────────────────────────────┐
│  OnBecameVisible/Invisible()                                          │
│  OnRenderObject()                                                     │
│  OnGUI()          → Legacy UI (avoid, use UI Toolkit/UGUI).          │
└─────────────────────────────────────────────────────────────┘

┌─── TEARDOWN ───────────────────────────────────────────────┐
│  OnDisable()      → Object deactivated. Unsubscribe events.          │
│  OnDestroy()      → Object destroyed. Final cleanup.                  │
└─────────────────────────────────────────────────────────────┘
```

**Critical rules:**
- `Awake()` runs before `Start()` across ALL objects (use for self-init).
- `Start()` runs after all `Awake()` calls (safe for cross-references).
- `FixedUpdate()` may run 0, 1, or multiple times per frame (catching up to real time).
- `LateUpdate()` always runs after ALL `Update()` calls in the frame.
- Execution order between scripts is undefined unless set in Project Settings.

### Concept 3.6.2 — Awake vs Start vs OnEnable

```csharp
public class CropPlot : MonoBehaviour
{
    private SpriteRenderer _renderer;
    private CropSystem _cropSystem;

    void Awake()
    {
        // ✓ Self-references (guaranteed to exist)
        _renderer = GetComponent<SpriteRenderer>();
    }

    void OnEnable()
    {
        // ✓ Subscribe to events (called every time object is re-enabled)
        GameEvents.Instance.OnSeasonChanged += HandleSeasonChange;
    }

    void Start()
    {
        // ✓ Cross-references (other objects' Awake has run)
        _cropSystem = FindFirstObjectByType<CropSystem>();
        _cropSystem.Register(this);
    }

    void OnDisable()
    {
        // ✓ Unsubscribe (mirrors OnEnable)
        GameEvents.Instance.OnSeasonChanged -= HandleSeasonChange;
    }

    void OnDestroy()
    {
        // ✓ Final cleanup (unregister from systems)
        _cropSystem?.Unregister(this);
    }
}
```

### Concept 3.6.3 — Update vs FixedUpdate vs LateUpdate

| Method | When | Use For | Time Variable |
|--------|------|---------|---------------|
| `FixedUpdate()` | Fixed interval (0.02s default) | Physics, forces, Rigidbody | `Time.fixedDeltaTime` |
| `Update()` | Once per frame (variable rate) | Input, game logic, animation | `Time.deltaTime` |
| `LateUpdate()` | After all Updates | Camera, post-processing | `Time.deltaTime` |

```csharp
public class PlayerController : MonoBehaviour
{
    [SerializeField] private float moveSpeed = 5f;
    private Rigidbody2D _rb;
    private Vector2 _input;

    void Awake() => _rb = GetComponent<Rigidbody2D>();

    void Update()
    {
        // Input polling (frame-rate dependent, must be in Update)
        _input = new Vector2(
            Input.GetAxisRaw("Horizontal"),
            Input.GetAxisRaw("Vertical")
        ).normalized;
    }

    void FixedUpdate()
    {
        // Physics movement (fixed timestep, deterministic)
        _rb.MovePosition(_rb.position + _input * moveSpeed * Time.fixedDeltaTime);
    }
}

public class CameraFollow : MonoBehaviour
{
    [SerializeField] private Transform target;
    [SerializeField] private float smoothTime = 0.3f;
    private Vector3 _velocity;

    void LateUpdate()
    {
        // Camera follows AFTER player has moved (no jitter)
        var targetPos = new Vector3(target.position.x, target.position.y, -10f);
        transform.position = Vector3.SmoothDamp(
            transform.position, targetPos, ref _velocity, smoothTime);
    }
}
```

## 🔑 2. Mechanics — Coroutines

### 2.1 — Coroutine Fundamentals

Coroutines are Unity's legacy async mechanism — cooperative multitasking on the main thread using C#'s `IEnumerator` and `yield return`:

```csharp
// Python comparison: generators with yield
// def countdown():
//     for i in range(3, 0, -1):
//         yield i
//         time.sleep(1)

public class DayNightCycle : MonoBehaviour
{
    [SerializeField] private float dayDuration = 120f;  // seconds

    private IEnumerator Start()
    {
        while (true)
        {
            yield return RunDay();
            yield return RunNight();
        }
    }

    private IEnumerator RunDay()
    {
        Debug.Log("Day begins");
        float elapsed = 0f;

        while (elapsed < dayDuration)
        {
            float t = elapsed / dayDuration;
            UpdateLighting(t);  // Gradually change lighting
            elapsed += Time.deltaTime;
            yield return null;  // Wait one frame
        }
    }

    private IEnumerator RunNight()
    {
        Debug.Log("Night begins");
        yield return new WaitForSeconds(dayDuration * 0.5f);  // Night is shorter
    }
}
```

### 2.2 — Yield Instructions

```csharp
yield return null;                              // Wait one frame
yield return new WaitForSeconds(2f);            // Wait 2 seconds (scaled time)
yield return new WaitForSecondsRealtime(2f);    // Wait 2 seconds (unscaled)
yield return new WaitForFixedUpdate();          // Wait for next FixedUpdate
yield return new WaitForEndOfFrame();           // Wait until rendering done
yield return new WaitUntil(() => isReady);      // Wait until condition true
yield return new WaitWhile(() => isLoading);    // Wait while condition true
yield return StartCoroutine(OtherCoroutine());  // Wait for another coroutine
yield return SceneManager.LoadSceneAsync("Farm"); // Wait for async operation
```

### 2.3 — Coroutine Patterns for Games

```csharp
// Pattern: Tween/Animation
public IEnumerator FadeOut(SpriteRenderer sr, float duration)
{
    Color start = sr.color;
    Color end = new Color(start.r, start.g, start.b, 0f);
    float elapsed = 0f;

    while (elapsed < duration)
    {
        sr.color = Color.Lerp(start, end, elapsed / duration);
        elapsed += Time.deltaTime;
        yield return null;
    }
    sr.color = end;
}

// Pattern: Spread heavy work across frames
public IEnumerator GenerateWorld(int width, int height)
{
    for (int x = 0; x < width; x++)
    {
        for (int y = 0; y < height; y++)
        {
            GenerateTile(x, y);
        }
        // Process one column per frame to avoid freezing
        yield return null;
    }
    Debug.Log("World generation complete");
}

// Pattern: Cooldown
private bool _canAttack = true;

public void TryAttack()
{
    if (!_canAttack) return;
    PerformAttack();
    StartCoroutine(AttackCooldown());
}

private IEnumerator AttackCooldown()
{
    _canAttack = false;
    yield return new WaitForSeconds(0.5f);
    _canAttack = true;
}

// Stopping coroutines
private Coroutine _currentRoutine;

void StartNewRoutine()
{
    if (_currentRoutine != null)
        StopCoroutine(_currentRoutine);  // Stop previous
    _currentRoutine = StartCoroutine(MyRoutine());
}
```

### 2.4 — Coroutines vs async/await (UniTask)

| Feature | Coroutines | UniTask |
|---------|-----------|---------|
| Allocation | WaitForSeconds allocates | Zero-allocation |
| Return values | No (IEnumerator) | Yes (`UniTask<T>`) |
| Exception handling | Swallowed silently | try/catch works |
| Cancellation | StopCoroutine (manual) | CancellationToken |
| Requires MonoBehaviour | Yes | No |
| Debugging | Hard (no stack trace) | Normal async debugging |

**Recommendation:** Use UniTask for new projects. Use coroutines only when interfacing with legacy Unity APIs that return `IEnumerator`.

## 🔑 3. Mechanics — ScriptableObjects

### 10.1 — What Are ScriptableObjects?

ScriptableObjects are **data containers** that live as assets in your project. They're NOT attached to GameObjects — they exist independently and can be shared across scenes.

```csharp
[CreateAssetMenu(fileName = "New Crop", menuName = "Farm/Crop Definition")]
public class CropDefinition : ScriptableObject
{
    [Header("Identity")]
    public string cropName;
    public Sprite[] growthSprites;  // One per growth stage

    [Header("Growth")]
    public int daysToGrow;
    public Season[] validSeasons;
    public bool needsWatering;

    [Header("Harvest")]
    public int minYield = 1;
    public int maxYield = 3;
    public int sellPrice;
    public ItemDefinition harvestedItem;

    [Header("Visual")]
    public Color mapColor = Color.green;

    // ScriptableObjects can have methods too
    public Sprite GetSpriteForDay(int day)
    {
        int stage = Mathf.FloorToInt((float)day / daysToGrow * growthSprites.Length);
        return growthSprites[Mathf.Clamp(stage, 0, growthSprites.Length - 1)];
    }

    public int RollYield() => Random.Range(minYield, maxYield + 1);
}
```

### 10.2 — ScriptableObject Patterns

```csharp
// Pattern 1: Runtime data set (registry)
[CreateAssetMenu(menuName = "Farm/Crop Database")]
public class CropDatabase : ScriptableObject
{
    [SerializeField] private CropDefinition[] crops;
    private Dictionary<string, CropDefinition> _lookup;

    public void Initialize()
    {
        _lookup = crops.ToDictionary(c => c.cropName);
    }

    public CropDefinition Get(string name) => _lookup[name];
    public IEnumerable<CropDefinition> GetBySeason(Season s) =>
        crops.Where(c => c.validSeasons.Contains(s));
}

// Pattern 2: Event channel (decoupled communication)
[CreateAssetMenu(menuName = "Events/Void Event")]
public class VoidEventChannel : ScriptableObject
{
    private readonly HashSet<Action> _listeners = new();

    public void Register(Action listener) => _listeners.Add(listener);
    public void Unregister(Action listener) => _listeners.Remove(listener);

    public void Raise()
    {
        foreach (var listener in _listeners)
            listener.Invoke();
    }
}

[CreateAssetMenu(menuName = "Events/Int Event")]
public class IntEventChannel : ScriptableObject
{
    private readonly HashSet<Action<int>> _listeners = new();

    public void Register(Action<int> listener) => _listeners.Add(listener);
    public void Unregister(Action<int> listener) => _listeners.Remove(listener);
    public void Raise(int value)
    {
        foreach (var listener in _listeners)
            listener.Invoke(value);
    }
}

// Pattern 3: Runtime variable (shared state without singletons)
[CreateAssetMenu(menuName = "Variables/Float Variable")]
public class FloatVariable : ScriptableObject
{
    public float Value;
    public event Action<float>? OnChanged;

    public void Set(float value)
    {
        Value = value;
        OnChanged?.Invoke(value);
    }
}

// Usage: PlayerHealth (FloatVariable asset) referenced by both HealthSystem and HealthBar UI
// No direct coupling between them!
```

### 10.3 — Why ScriptableObjects for a Stardew-Like Game

| Use Case | Benefit |
|----------|---------|
| Crop definitions | Designers edit in Inspector, no code changes |
| Item database | Shared across inventory, shop, crafting systems |
| Dialogue trees | Data-driven conversations |
| Quest definitions | Add quests without touching code |
| Audio config | Volume curves, music playlists as assets |
| Event channels | Decouple systems without singletons |

## 🔑 4. Mechanics — DOTS / ECS

### 4.1 — Why ECS?

MonoBehaviour works great for hundreds of objects. But a Stardew-like farm with 5,000 crop tiles, 200 NPCs, and 1,000 particles needs something faster. ECS provides:

- **Cache-friendly memory**: Components stored in contiguous arrays
- **Automatic parallelism**: Systems run on multiple cores via Job System
- **Burst compilation**: C# compiled to SIMD-optimized native code
- **No GC pressure**: Components are structs, no heap allocation

### 4.2 — ECS Core Concepts

```csharp
using Unity.Entities;
using Unity.Mathematics;
using Unity.Transforms;

// COMPONENT: Pure data, no behavior (struct)
public struct CropGrowth : IComponentData
{
    public float GrowthProgress;    // 0.0 to 1.0
    public float GrowthRate;        // Per-second growth
    public int CurrentStage;
    public bool NeedsWater;
}

public struct Harvestable : IComponentData
{
    public int YieldMin;
    public int YieldMax;
    public int SellPrice;
}

// Tag component (zero-size, just marks entities)
public struct WateredToday : IComponentData { }

// SYSTEM: Logic that processes entities with specific components
public partial struct CropGrowthSystem : ISystem
{
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;

        // Process ALL entities with CropGrowth + WateredToday
        foreach (var (growth, entity) in
            SystemAPI.Query<RefRW<CropGrowth>>()
                .WithAll<WateredToday>()
                .WithEntityAccess())
        {
            growth.ValueRW.GrowthProgress += growth.ValueRO.GrowthRate * dt;

            if (growth.ValueRO.GrowthProgress >= 1.0f)
            {
                // Add Harvestable component when fully grown
                state.EntityManager.AddComponent<Harvestable>(entity);
            }
        }
    }
}
```

### 4.3 — Job System (Parallel Processing)

```csharp
using Unity.Jobs;
using Unity.Collections;
using Unity.Burst;

// Job: a unit of work that can run on any thread
[BurstCompile]
public struct GrowCropsJob : IJobParallelFor
{
    public float DeltaTime;
    public NativeArray<float> GrowthProgress;
    [ReadOnly] public NativeArray<float> GrowthRates;
    [ReadOnly] public NativeArray<bool> IsWatered;

    public void Execute(int index)
    {
        if (IsWatered[index])
        {
            GrowthProgress[index] += GrowthRates[index] * DeltaTime;
            GrowthProgress[index] = math.min(GrowthProgress[index], 1.0f);
        }
    }
}

// Scheduling the job
public class CropJobScheduler : MonoBehaviour
{
    private NativeArray<float> _progress;
    private NativeArray<float> _rates;
    private NativeArray<bool> _watered;

    void Update()
    {
        var job = new GrowCropsJob
        {
            DeltaTime = Time.deltaTime,
            GrowthProgress = _progress,
            GrowthRates = _rates,
            IsWatered = _watered
        };

        // Schedule across all worker threads, batches of 64
        JobHandle handle = job.Schedule(_progress.Length, 64);
        handle.Complete();  // Wait for completion (or chain with other jobs)
    }

    void OnDestroy()
    {
        // NativeArrays must be manually disposed!
        _progress.Dispose();
        _rates.Dispose();
        _watered.Dispose();
    }
}
```

### 4.4 — Burst Compiler

Burst compiles C# (a subset called HPC# — High Performance C#) to highly optimized native code with SIMD vectorization:

```csharp
[BurstCompile]
public struct DistanceCheckJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<float3> Positions;
    public float3 Center;
    public float RadiusSq;
    public NativeArray<bool> Results;

    public void Execute(int index)
    {
        float3 diff = Positions[index] - Center;
        Results[index] = math.lengthsq(diff) <= RadiusSq;
    }
}
// Burst auto-vectorizes this: processes 4-8 positions per CPU instruction (SIMD)
```

**Burst restrictions (HPC#):**
- No managed types (no `string`, `class`, `List<T>`)
- No `try/catch` (use error codes)
- No virtual calls or interfaces
- Only `NativeArray`, `NativeList`, etc. for collections
- Use `Unity.Mathematics` (`float3`, `math.sin`) instead of `UnityEngine` (`Vector3`, `Mathf.Sin`)

### 4.5 — When to Use What

| Scenario | Approach | Why |
|----------|----------|-----|
| Player controller, UI, menus | MonoBehaviour | Low entity count, needs Unity API |
| 100 NPCs with AI | MonoBehaviour + Jobs | AI on threads, results applied on main |
| 5,000 crop tiles growing | ECS + Burst | Massive parallelism, cache-friendly |
| 10,000 particles | ECS + Burst + Job System | Maximum throughput |
| Save/Load system | MonoBehaviour + async | I/O bound, not CPU bound |
| Networking | MonoBehaviour (Mirror/Netcode) | Framework requires it |

### 4.6 — Hybrid Approach (Recommended for Stardew-Like)

```csharp
// MonoBehaviour "bridge" that owns ECS world for farm simulation
public class FarmSimulation : MonoBehaviour
{
    private World _ecsWorld;
    private EntityManager _em;

    void Awake()
    {
        _ecsWorld = World.DefaultGameObjectConversionWorld;
        _em = _ecsWorld.EntityManager;
    }

    public void PlantCrop(Vector2Int tile, CropDefinition def)
    {
        // Create ECS entity for the crop (high-performance simulation)
        var entity = _em.CreateEntity();
        _em.AddComponentData(entity, new CropGrowth
        {
            GrowthProgress = 0f,
            GrowthRate = 1f / (def.daysToGrow * 60f),  // Convert days to seconds
            NeedsWater = def.needsWatering
        });
        _em.AddComponentData(entity, new LocalTransform
        {
            Position = new float3(tile.x, tile.y, 0)
        });

        // MonoBehaviour handles the visual (sprite, animation)
        var visual = Instantiate(cropVisualPrefab, (Vector3Int)tile, Quaternion.identity);
        visual.LinkToEntity(entity);
    }
}
```

## ⚠️ 5. Gotchas

### Gotcha 3.6.1 — Null Checks in Unity Are Expensive
```csharp
// Unity overrides == operator for UnityEngine.Object
// This checks BOTH C# null AND native-side destruction
if (gameObject == null) { }  // Calls Unity's custom == (slow!)

// ✓ For destroyed checks, use the Unity way:
if (!gameObject) { }  // Implicit bool conversion (same as == null but clearer intent)

// ✓ For pure C# null (never-assigned reference):
if (gameObject is null) { }  // Bypasses Unity's == override (faster, but won't catch Destroy'd)
```

### Gotcha 3.6.2 — GetComponent in Update
```csharp
// ❌ Searches component list every frame
void Update()
{
    var rb = GetComponent<Rigidbody2D>();  // ~0.02ms per call, adds up!
    rb.AddForce(Vector2.up);
}

// ✓ Cache in Awake
private Rigidbody2D _rb;
void Awake() => _rb = GetComponent<Rigidbody2D>();
void FixedUpdate() => _rb.AddForce(Vector2.up);
```

### Gotcha 3.6.3 — Coroutine Allocation
```csharp
// ❌ new WaitForSeconds allocates every time
IEnumerator Spawn()
{
    while (true)
    {
        SpawnEnemy();
        yield return new WaitForSeconds(2f);  // GC allocation!
    }
}

// ✓ Cache the yield instruction
private readonly WaitForSeconds _spawnDelay = new(2f);
IEnumerator Spawn()
{
    while (true)
    {
        SpawnEnemy();
        yield return _spawnDelay;  // Reused, no allocation
    }
}
```

### Gotcha 3.6.4 — ScriptableObject Runtime State
```csharp
// ❌ Modifying SO at runtime persists in Editor (but NOT in builds)
[CreateAssetMenu] public class PlayerStats : ScriptableObject
{
    public int health = 100;  // If you modify this at runtime in Editor, it SAVES!
}

// ✓ Use runtime copies or separate runtime state
public class PlayerHealth : MonoBehaviour
{
    [SerializeField] private PlayerStats baseStats;
    private int _currentHealth;  // Runtime state lives here, not in SO

    void Start() => _currentHealth = baseStats.health;
}
```

### Gotcha 3.6.5 — NativeArray Leaks
```csharp
// ❌ Forgetting to dispose NativeArrays = memory leak + error spam
var positions = new NativeArray<float3>(1000, Allocator.Persistent);
// ... use it ...
// Forgot to dispose! Unity will scream at you in the console.

// ✓ Always dispose, or use Allocator.Temp/TempJob for short-lived
void Update()
{
    var temp = new NativeArray<float3>(100, Allocator.Temp);  // Auto-disposed end of frame
    // ... use it ...
    // No need to manually dispose Allocator.Temp
}
```

### Gotcha 3.6.6 — Execution Order Between Scripts
```csharp
// ❌ Assuming your Manager.Awake() runs before Player.Awake()
// Unity does NOT guarantee order unless you set it!

// ✓ Set explicit order: Edit → Project Settings → Script Execution Order
// Or: Use [DefaultExecutionOrder(int)] attribute
[DefaultExecutionOrder(-100)]  // Runs before default (0)
public class GameManager : MonoBehaviour { }

[DefaultExecutionOrder(100)]   // Runs after default
public class UIManager : MonoBehaviour { }
```

## 🧠 8. Extended Worked Examples & Deep Dives

### Example 8.1 — ScriptableObject Architecture: Event Channels & Runtime Sets

**Problem:** Your Unity game has tightly coupled MonoBehaviours referencing each other via `GetComponent` and `FindObjectOfType`. Use ScriptableObject-based architecture for decoupled, testable, designer-friendly systems.

<details>
<summary>🔍 Full step-by-step solution</summary>

#### Event Channels (ScriptableObject Events)

```csharp
// ═══════════════════════════════════════════════════════════════
// GENERIC EVENT CHANNEL — Replaces direct references between systems
// ═══════════════════════════════════════════════════════════════

// Base: Void event (no payload)
[CreateAssetMenu(menuName = "Events/Void Event Channel")]
public class VoidEventChannel : ScriptableObject
{
    private readonly List<Action> _listeners = new();

    public void Raise()
    {
        // Iterate backwards to allow unsubscription during raise
        for (int i = _listeners.Count - 1; i >= 0; i--)
            _listeners[i]?.Invoke();
    }

    public void Subscribe(Action listener) => _listeners.Add(listener);
    public void Unsubscribe(Action listener) => _listeners.Remove(listener);
}

// Generic: Typed event (with payload)
public abstract class EventChannel<T> : ScriptableObject
{
    private readonly List<Action<T>> _listeners = new();

    public void Raise(T value)
    {
        for (int i = _listeners.Count - 1; i >= 0; i--)
            _listeners[i]?.Invoke(value);
    }

    public void Subscribe(Action<T> listener) => _listeners.Add(listener);
    public void Unsubscribe(Action<T> listener) => _listeners.Remove(listener);
}

// Concrete channels (needed because Unity can't serialize open generics)
[CreateAssetMenu(menuName = "Events/Int Event Channel")]
public class IntEventChannel : EventChannel<int> { }

[CreateAssetMenu(menuName = "Events/Float Event Channel")]
public class FloatEventChannel : EventChannel<float> { }

[CreateAssetMenu(menuName = "Events/String Event Channel")]
public class StringEventChannel : EventChannel<string> { }

[CreateAssetMenu(menuName = "Events/Vector3 Event Channel")]
public class Vector3EventChannel : EventChannel<Vector3> { }

// ═══════════════════════════════════════════════════════════════
// USAGE: Combat system raises damage event, UI and Audio listen
// ═══════════════════════════════════════════════════════════════

// Publisher (CombatSystem.cs)
public class CombatSystem : MonoBehaviour
{
    [SerializeField] private IntEventChannel _onDamageDealt;    // Drag SO in Inspector
    [SerializeField] private VoidEventChannel _onEnemyKilled;

    public void DealDamage(int amount)
    {
        // ... apply damage logic ...
        _onDamageDealt.Raise(amount);  // Fire-and-forget, no references needed
        
        if (targetDead)
            _onEnemyKilled.Raise();
    }
}

// Subscriber (DamageUI.cs) — completely decoupled from CombatSystem
public class DamageUI : MonoBehaviour
```

### Example 8.2 — MonoBehaviour vs ECS DOTS Migration

**Problem:** Your game has 10,000+ entities and MonoBehaviour-based architecture is hitting performance limits. Understand when and how to migrate to Unity's Data-Oriented Technology Stack (DOTS).

<details>
<summary>🔍 Full step-by-step solution</summary>

#### MonoBehaviour Approach (Object-Oriented)

```csharp
// Traditional: Each enemy is a GameObject with MonoBehaviours
public class EnemyMovement : MonoBehaviour
{
    [SerializeField] private float _speed = 3f;
    private Transform _target;

    private void Update()
    {
        if (_target == null) return;
        var direction = (_target.position - transform.position).normalized;
        transform.position += direction * _speed * Time.deltaTime;
    }
}
// Problem at scale:
// - 10,000 GameObjects = 10,000 Update() calls (virtual dispatch overhead)
// - Transform data scattered across heap (cache misses)
// - Each MonoBehaviour is a managed object (GC pressure)
// - ~2ms for 1,000 enemies, ~20ms for 10,000 (frame budget blown)
```

#### ECS DOTS Approach (Data-Oriented)

```csharp
using Unity.Entities;
using Unity.Mathematics;
using Unity.Transforms;
using Unity.Burst;

// COMPONENT: Pure data, no behavior (struct, no methods)
public struct MoveSpeed : IComponentData
{
    public float Value;
}

public struct TargetPosition : IComponentData
{
    public float3 Value;
}

// SYSTEM: Pure behavior, no data (processes components in bulk)
[BurstCompile]
public partial struct EnemyMovementSystem : ISystem
{
    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;

        // Processes ALL entities with (LocalTransform + MoveSpeed + TargetPosition)
        // in a tight, cache-friendly loop — Burst-compiled to SIMD
        foreach (var (transform, speed, target) in
            SystemAPI.Query<RefRW<LocalTransform>, RefRO<MoveSpeed>, RefRO<TargetPosition>>())
        {
            float3 direction = math.normalize(target.ValueRO.Value - transform.ValueRO.Position);
            transform.ValueRW.Position += direction * speed.ValueRO.Value * dt;
        }
    }
}

// Performance at 10,000 entities:
// MonoBehaviour: ~20ms (scattered memory, virtual calls, GC)
// ECS + Burst:   ~0.3ms (contiguous memory, SIMD, zero GC)
// Speedup: ~66x
```

#### Job System for Parallel Processing

```csharp
using Unity.Jobs;
using Unity.Collections;
using Unity.Burst;

[BurstCompile]
public partial struct EnemyMovementJobSystem : ISystem
{
    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;
        
        // Schedule parallel job across all worker threads
        new MoveTowardTargetJob { DeltaTime = dt }
            .ScheduleParallel();
    }
}

[BurstCompile]
partial struct MoveTowardTargetJob : IJobEntity
{
    public float DeltaTime;

    void Execute(ref LocalTransform transform, in MoveSpeed speed, in TargetPosition target)
    {
        float3 direction = math.normalize(target.Value - transform.Position);
        transform.Position += direction * speed.Value * DeltaTime;
    }
}
// This automatically splits work across all CPU cores
// 8-core CPU: ~8x additional speedup over single-threaded ECS
```

#### Migration Strategy (Incremental)

```csharp
// You DON'T have to convert everything at once.
// Hybrid approach: MonoBehaviours for complex logic, ECS for bulk processing

// Step 1: Identify hot paths (profiler shows what's slow)
// Step 2: Convert those specific systems to ECS
// Step 3: Keep UI, input, audio as MonoBehaviours (they're fine)

// Common migration targets:
// ✅ Bullet/projectile systems (thousands of simple entities)
// ✅ Particle-like effects (spawning, moving, despawning)
// ✅ AI pathfinding (parallel graph traversal)
// ✅ Spatial queries (nearest enemy, line of sight)
// ❌ Player controller (complex, one instance, not a bottleneck)
// ❌ UI system (event-driven, not performance-critical)
// ❌ Audio (Unity's audio system is already native)
```

### Example 8.3 — Burst Compiler Intrinsics

**Problem:** You need maximum performance for math-heavy game code (physics, pathfinding, procedural generation). Burst compiles C# to highly optimized native code with SIMD instructions.

<details>
<summary>🔍 Full step-by-step solution</summary>

```csharp
using Unity.Burst;
using Unity.Burst.Intrinsics;
using Unity.Mathematics;
using Unity.Collections;
using Unity.Jobs;

// ═══════════════════════════════════════════════════════════════
// BASIC BURST: Just add [BurstCompile] to Jobs/Systems
// ═══════════════════════════════════════════════════════════════

[BurstCompile(FloatPrecision.Standard, FloatMode.Fast)]
struct CalculateDistancesJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<float3> Positions;
    public float3 Origin;
    public NativeArray<float> Distances;

    public void Execute(int index)
    {
        // Burst auto-vectorizes this to SIMD (SSE/AVX on x86, NEON on ARM)
        Distances[index] = math.distance(Origin, Positions[index]);
    }
}

// ═══════════════════════════════════════════════════════════════
// BURST RESTRICTIONS (what you CAN'T do)
// ═══════════════════════════════════════════════════════════════

// ❌ No managed types (string, class, List<T>, delegates)
// ❌ No try/catch (exceptions not supported)
// ❌ No virtual calls (no interfaces in hot path)
// ❌ No LINQ
// ❌ No boxing
// ❌ No shared static mutable state (unless SharedStatic<T>)

// ✅ Allowed: structs, NativeArray, NativeHashMap, math.*, fixed arrays
// ✅ Allowed: Unity.Mathematics (float3, quaternion, etc.)
// ✅ Allowed: Function pointers (FunctionPointer<T>)

// ═══════════════════════════════════════════════════════════════
// ADVANCED: Manual SIMD with Burst intrinsics
// ═══════════════════════════════════════════════════════════════

[BurstCompile]
struct FrustumCullingJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<float4> FrustumPlanes; // 6 planes
    [ReadOnly] public NativeArray<float3> BoundsCenters;
    [ReadOnly] public NativeArray<float> BoundsRadii;
    public NativeArray<bool> IsVisible;

    public void Execute(int index)
    {
        float3 center = BoundsCenters[index];
        float radius = BoundsRadii[index];

        // Test against all 6 frustum planes
        for (int p = 0; p < 6; p++)
        {
            float4 plane = FrustumPlanes[p];
            float distance = math.dot(plane.xyz, center) + plane.w;
            if (distance < -radius)
            {
                IsVisible[index] = false;
                return; // Outside frustum
            }
        }
        IsVisible[index] = true;
    }
}
// Burst compiles this to ~4 SIMD instructions per plane test
// 100,000 objects culled in <0.5ms on modern CPU
```

### Example 8.4 — Job System Dependency Graph

<details>
<summary>🔍 Full step-by-step solution</summary>

```csharp
using Unity.Jobs;
using Unity.Collections;

// ═══════════════════════════════════════════════════════════════
// DEPENDENCY CHAINS: Jobs that depend on other jobs' output
// ═══════════════════════════════════════════════════════════════

public class GameSimulation : MonoBehaviour
{
    private NativeArray<float3> _positions;
    private NativeArray<float3> _velocities;
    private NativeArray<float> _health;
    private NativeArray<int> _aliveCount;

    void Update()
    {
        float dt = Time.deltaTime;

        // Job 1: Apply physics (reads velocities, writes positions)
        var physicsJob = new ApplyVelocityJob
        {
            Positions = _positions,
            Velocities = _velocities,
            DeltaTime = dt
        };
        JobHandle physicsHandle = physicsJob.Schedule(_positions.Length, 64);

        // Job 2: Apply damage over time (independent of physics)
        var damageJob = new ApplyDotJob
        {
            Health = _health,
            DamagePerSecond = 5f,
            DeltaTime = dt
        };
        JobHandle damageHandle = damageJob.Schedule(_health.Length, 64);

        // Job 3: Count alive entities (depends on BOTH physics and damage)
        var countJob = new CountAliveJob
        {
            Health = _health,
            AliveCount = _aliveCount
        };
        // CombineDependencies: waits for both to complete
        JobHandle combined = JobHandle.CombineDependencies(physicsHandle, damageHandle);
        JobHandle countHandle = countJob.Schedule(combined);

        // Job 4: Cleanup dead entities (depends on count)
        var cleanupJob = new CleanupDeadJob
        {
            Health = _health,
            Positions = _positions
        };
        JobHandle cleanupHandle = cleanupJob.Schedule(_health.Length, 64, countHandle);

        // Complete all work before end of frame
        cleanupHandle.Complete();

        // Read results on main thread
        Debug.Log($"Alive: {_aliveCount[0]}");
    }
}

// Execution timeline:
// Frame start ──┬── [Physics Job] ──────┐
//               │                        ├── [Count Job] ── [Cleanup Job] ── Frame end
//               └── [Damage Job] ────────┘
// Physics and Damage run IN PARALLEL on different cores
// Count waits for both, Cleanup waits for Count
```

### Appendix 9.1 — How Unity's Serialization Works

Unity's serialization system determines what shows up in the Inspector and what gets saved in scenes/prefabs. Understanding it prevents countless bugs.

#### Serialization Rules

```csharp
// SERIALIZED (shows in Inspector, saved in scenes):
[SerializeField] private int _health;           // ✅ Private + attribute
public float Speed;                              // ✅ Public field (auto-serialized)
[SerializeField] private List<string> _items;   // ✅ List<T> of serializable type
[SerializeField] private MyStruct _data;        // ✅ Serializable struct

// NOT SERIALIZED:
private int _cachedValue;                        // ❌ Private without attribute
public static int GlobalCount;                   // ❌ Static fields never serialized
[NonSerialized] public int TempValue;           // ❌ Explicitly excluded
public Dictionary<string, int> Map;             // ❌ Dictionary not serializable!
public Action OnEvent;                           // ❌ Delegates not serializable
public IMyInterface Reference;                   // ❌ Interfaces not serializable*

// *Unity 2023+: [SerializeReference] enables interface/abstract serialization
[SerializeReference] private IMyInterface _ref;  // ✅ Polymorphic serialization
```

### Appendix 9.2 — Addressables Internals

#### How Addressables Work Under the Hood

```
Build Time:
1. Assets marked as "Addressable" get a string address (e.g., "Enemies/Goblin")
2. Assets are packed into AssetBundles (compressed archives)
3. A catalog (JSON) maps addresses → bundle locations
4. Bundles can be local (in build) or remote (CDN)

Runtime:
1. Addressables.LoadAssetAsync("Enemies/Goblin")
2. System looks up address in catalog → finds bundle name + offset
3. Downloads bundle if remote (with caching)
4. Loads asset from bundle into memory
5. Returns typed handle (AsyncOperationHandle<T>)
6. YOU must release the handle when done (reference counting)
```

#### Memory Management with Addressables

```csharp
using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

public class AddressableLoader : MonoBehaviour
{
    private AsyncOperationHandle<GameObject> _prefabHandle;
    private List<AsyncOperationHandle> _loadedHandles = new();

    // Load and instantiate
    public async UniTask<GameObject> SpawnEnemyAsync(string address, CancellationToken ct)
    {
        _prefabHandle = Addressables.LoadAssetAsync<GameObject>(address);
        await _prefabHandle.WithCancellation(ct);
        
        if (_prefabHandle.Status == AsyncOperationStatus.Succeeded)
        {
            _loadedHandles.Add(_prefabHandle);
            return Instantiate(_prefabHandle.Result);
        }
        
        Debug.LogError($"Failed to load: {address}");
        return null;
    }

    // CRITICAL: Release handles to free memory
    private void OnDestroy()
    {
        foreach (var handle in _loadedHandles)
        {
            Addressables.Release(handle);
        }
        _loadedHandles.Clear();
    }
}

// Common mistake: Loading without releasing
// Each LoadAssetAsync increments a reference count on the bundle
// If you never Release, the bundle stays in memory FOREVER
// Unity Profiler → Memory → "Addressables Event Viewer" shows leaks
```
