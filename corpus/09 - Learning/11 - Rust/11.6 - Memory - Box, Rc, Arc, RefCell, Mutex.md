# 11.6 — Memory: Box, Rc, Arc, RefCell & Mutex

> *"Rust gives you the tools to express exactly the ownership pattern you need — from unique ownership to shared ownership to interior mutability — all checked at compile time or with minimal runtime cost."* — Niko Matsakis

In Python, every object lives on the heap and is reference-counted. You never think about it. In Rust, stack allocation is the default, and heap allocation is explicit. This chapter covers the smart pointer types that let you opt into heap allocation, shared ownership, and interior mutability — each with clear tradeoffs.

---

## 🎯 Learning Objectives

By the end of this chapter you will be able to:

1. Use `Box<T>` for heap allocation and recursive types.
2. Use `Rc<T>` for single-threaded shared ownership.
3. Use `Arc<T>` for multi-threaded shared ownership.
4. Use `RefCell<T>` for single-threaded interior mutability.
5. Use `Mutex<T>` and `RwLock<T>` for thread-safe interior mutability.
6. Choose the right pointer type for any given situation.

## 📚 1. Concepts

### Concept 14.6.1 — Stack vs Heap (The Performance Foundation)

```
Stack (fast, automatic):          Heap (flexible, manual):
┌─────────────────────┐          ┌─────────────────────────┐
│ Fixed size at compile│          │ Dynamic size at runtime  │
│ LIFO allocation     │          │ Allocator manages memory │
│ ~1 CPU cycle        │          │ ~100+ CPU cycles         │
│ Cache-friendly      │          │ Pointer indirection      │
│ Auto-freed on scope │          │ Freed when owner drops   │
└─────────────────────┘          └─────────────────────────┘
```

**Cache implications** (see [[08.12 - Computer Architecture - Performance Intuition]]):
- Stack data is contiguous → CPU cache prefetcher works well
- Heap data via pointers → cache misses on every dereference
- `Vec<T>` stores elements contiguously on heap → cache-friendly
- `Vec<Box<T>>` stores pointers → each element access is a cache miss

### Concept 14.6.2 — Box<T> (Heap Allocation)

`Box<T>` is the simplest smart pointer: it allocates `T` on the heap and owns it exclusively.

```rust
fn main() {
    // Stack allocation (default):
    let x: i32 = 42;  // 4 bytes on stack

    // Heap allocation (explicit):
    let y: Box<i32> = Box::new(42);  // 8-byte pointer on stack → 4 bytes on heap

    // Dereferences transparently:
    println!("{}", *y);  // Explicit deref
    println!("{y}");     // Auto-deref (Deref trait)
}
```

**When to use Box:**
1. **Recursive types** (size unknown at compile time)
2. **Large data** you don't want to copy on the stack
3. **Trait objects** (`Box<dyn Trait>`)
4. **Transferring ownership** of large data without copying

```rust
// Recursive type — won't compile without Box:
enum List {
    Cons(i32, Box<List>),  // Box breaks the infinite size recursion
    Nil,
}

// Without Box: compiler error "recursive type has infinite size"
// With Box: List is a known size (i32 + pointer)
```

### Concept 14.6.3 — Rc<T> (Reference Counting — Single Thread)

`Rc<T>` enables **multiple owners** of the same data (single-threaded only):

```rust
use std::rc::Rc;

fn main() {
    let data = Rc::new(vec![1, 2, 3]);

    let a = Rc::clone(&data);  // Increments reference count (cheap!)
    let b = Rc::clone(&data);  // Another clone

    println!("References: {}", Rc::strong_count(&data));  // 3
    println!("Data: {:?}", a);  // All point to same Vec

    // When all Rc's are dropped, the data is freed
    drop(a);
    println!("References: {}", Rc::strong_count(&data));  // 2
}
```

**Key facts:**
- `Rc::clone()` is cheap — just increments a counter (NOT a deep copy)
- Data is immutable through `Rc` (you get `&T`, not `&mut T`)
- NOT thread-safe (use `Arc` for threads)
- Can create reference cycles → memory leaks (use `Weak<T>` to break cycles)

### Concept 14.6.4 — Arc<T> (Atomic Reference Counting — Multi-Thread)

`Arc<T>` is `Rc<T>` but thread-safe (uses atomic operations for the counter):

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let data = Arc::new(vec![1, 2, 3, 4, 5]);
    let mut handles = vec![];

    for i in 0..3 {
        let data = Arc::clone(&data);  // Atomic increment
        handles.push(thread::spawn(move || {
            println!("Thread {i}: sum = {}", data.iter().sum::<i32>());
        }));
    }

    for handle in handles {
        handle.join().unwrap();
    }
}
```

**Arc vs Rc:**
- `Arc`: atomic counter (~5-10x slower than Rc, but thread-safe)
- `Rc`: non-atomic counter (faster, but single-thread only)
- Rule: Use `Rc` unless you need to share across threads

### Concept 14.6.5 — RefCell<T> (Interior Mutability — Single Thread)

`RefCell<T>` moves borrow checking from compile time to **runtime**:

```rust
use std::cell::RefCell;

fn main() {
    let data = RefCell::new(vec![1, 2, 3]);

    // Borrow rules enforced at RUNTIME (panics on violation):
    {
        let r1 = data.borrow();      // Immutable borrow (like &T)
        let r2 = data.borrow();      // Another immutable borrow — OK
        println!("{:?} {:?}", r1, r2);
    }  // r1, r2 dropped

    {
        let mut w = data.borrow_mut();  // Mutable borrow (like &mut T)
        w.push(4);
        // let r = data.borrow();  // PANIC! Can't borrow while mutably borrowed
    }

    println!("{:?}", data.borrow());  // [1, 2, 3, 4]
}
```

**When to use RefCell:**
- When you need to mutate data behind a shared reference (`&self`)
- Common pattern: `Rc<RefCell<T>>` — shared ownership + interior mutability
- NOT thread-safe (use `Mutex<T>` for threads)

### Concept 14.6.6 — Mutex<T> (Thread-Safe Interior Mutability)

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let data = Arc::new(Mutex::new(vec![1, 2, 3]));
    let mut handles = vec![];

    for i in 0..5 {
        let data = Arc::clone(&data);
        handles.push(thread::spawn(move || {
            let mut guard = data.lock().unwrap();  // Blocks until lock acquired
            guard.push(i);
            // Lock released when guard is dropped (RAII)
        }));
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("{:?}", data.lock().unwrap());  // [1, 2, 3, 0, 1, 2, 3, 4]
}
```

### Concept 14.6.7 — RwLock<T> (Multiple Readers OR One Writer)

```rust
use std::sync::{Arc, RwLock};
use std::thread;

fn main() {
    let config = Arc::new(RwLock::new(String::from("initial")));

    // Multiple readers can access simultaneously:
    let readers: Vec<_> = (0..5).map(|i| {
        let config = Arc::clone(&config);
        thread::spawn(move || {
            let guard = config.read().unwrap();  // Shared read lock
            println!("Reader {i}: {guard}");
        })
    }).collect();

    // Writer gets exclusive access:
    {
        let mut guard = config.write().unwrap();  // Exclusive write lock
        *guard = String::from("updated");
    }

    for r in readers { r.join().unwrap(); }
}
```

## 📐 2. Mental Models

### Model 14.6.1 — The Decision Matrix

| Need | Single-Thread | Multi-Thread |
|------|--------------|--------------|
| Unique ownership, heap | `Box<T>` | `Box<T>` |
| Shared ownership, immutable | `Rc<T>` | `Arc<T>` |
| Shared ownership, mutable | `Rc<RefCell<T>>` | `Arc<Mutex<T>>` |
| Shared ownership, read-heavy | `Rc<RefCell<T>>` | `Arc<RwLock<T>>` |
| Interior mutability (no sharing) | `Cell<T>` / `RefCell<T>` | `Mutex<T>` |

### Model 14.6.2 — Python Object Model as Rust Equivalent

Every Python object is essentially `Arc<RefCell<T>>`:
- Reference counted (Arc)
- Mutable through any reference (RefCell)
- Heap allocated (Box)

Rust makes you choose explicitly, gaining performance and safety:

```python
# Python: everything is Arc<RefCell<T>> implicitly
x = [1, 2, 3]  # Heap-allocated, ref-counted, mutable through any reference
y = x           # Shared reference (refcount++)
y.append(4)     # Mutates through shared reference (no compile-time check)
```

```rust
// Rust: you choose the exact semantics you need
let x = vec![1, 2, 3];           // Stack pointer to heap Vec (unique owner)
let y = x;                        // MOVED — x invalid (zero-cost, no refcount)

// If you NEED Python semantics:
let x = Rc::new(RefCell::new(vec![1, 2, 3]));
let y = Rc::clone(&x);
y.borrow_mut().push(4);          // Explicit mutation through shared reference
```

### Model 14.6.3 — Memory Layout Visualization

```
Box<Vec<i32>>:
Stack:  [ptr] ──→ Heap: [ptr, len, cap] ──→ Heap: [1, 2, 3, 4, ...]
         8B              24B                    N×4B

Rc<Vec<i32>>:
Stack:  [ptr] ──→ Heap: [strong_count, weak_count, ptr, len, cap] ──→ Heap: [1, 2, 3, ...]
         8B              8B + 8B + 24B = 40B                            N×4B

Arc<Mutex<Vec<i32>>>:
Stack:  [ptr] ──→ Heap: [atomic_strong, atomic_weak, poison_flag, lock_state, ptr, len, cap] ──→ Heap: [...]
         8B              ~64B (cache-line aligned)                                                  N×4B
```

Each layer of indirection costs cache performance. Use the simplest type that satisfies your requirements.

## 🔑 3. Mechanics

### 3.1 — Cell<T> (Copy Types Only, Zero Overhead)

```rust
use std::cell::Cell;

struct Counter {
    count: Cell<u32>,  // Can mutate even through &self
}

impl Counter {
    fn new() -> Self {
        Counter { count: Cell::new(0) }
    }

    fn increment(&self) {  // Note: &self, not &mut self!
        self.count.set(self.count.get() + 1);
    }

    fn get(&self) -> u32 {
        self.count.get()
    }
}

// Cell works by copying values in and out (only for Copy types)
// Zero runtime overhead — no borrow tracking
```

### 3.2 — Weak<T> (Breaking Reference Cycles)

```rust
use std::rc::{Rc, Weak};
use std::cell::RefCell;

// Tree with parent back-references (would leak with Rc for parent)
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,      // Weak: doesn't prevent deallocation
    children: RefCell<Vec<Rc<Node>>>,  // Strong: keeps children alive
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });

    let branch = Rc::new(Node {
        value: 5,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });

    // Set parent (weak reference — won't create cycle)
    *leaf.parent.borrow_mut() = Rc::downgrade(&branch);

    // Access parent (might be deallocated — returns Option)
    if let Some(parent) = leaf.parent.borrow().upgrade() {
        println!("Leaf's parent: {}", parent.value);
    }
}
```

### 3.3 — Cow<T> (Clone on Write)

```rust
use std::borrow::Cow;

// Cow<'a, T>: either borrows or owns data
// Avoids cloning until mutation is needed
fn process_name(name: &str) -> Cow<'_, str> {
    if name.contains(' ') {
        // Need to modify — clone into owned String
        Cow::Owned(name.replace(' ', "_"))
    } else {
        // No modification needed — just borrow
        Cow::Borrowed(name)
    }
}

fn main() {
    let name1 = process_name("hello");       // Borrowed (no allocation)
    let name2 = process_name("hello world"); // Owned (allocated)

    // Both can be used as &str:
    println!("{name1}, {name2}");
}
```

### 3.4 — Pin<T> (Preventing Moves)

```rust
use std::pin::Pin;
use std::marker::PhantomPinned;

// Pin prevents a value from being moved in memory
// Required for self-referential types (like async Futures)

struct SelfReferential {
    data: String,
    // ptr: *const String,  // Points to self.data — breaks if moved!
    _pin: PhantomPinned,
}

// In practice, you encounter Pin with:
// 1. async/await (Futures are self-referential)
// 2. Intrusive data structures
// 3. FFI with C libraries that store pointers

// Most common usage: Pin<Box<dyn Future>>
use std::future::Future;
fn returns_future() -> Pin<Box<dyn Future<Output = i32>>> {
    Box::pin(async { 42 })
}
```

### 3.5 — Performance Comparison

```rust
use std::time::Instant;

fn benchmark_allocations() {
    let n = 1_000_000;

    // Stack allocation (fastest)
    let start = Instant::now();
    for _ in 0..n {
        let _x: [u8; 64] = [0; 64];
    }
    println!("Stack: {:?}", start.elapsed());

    // Box (heap allocation)
    let start = Instant::now();
    for _ in 0..n {
        let _x = Box::new([0u8; 64]);
    }
    println!("Box: {:?}", start.elapsed());

    // Rc (heap + refcount)
    let start = Instant::now();
    for _ in 0..n {
        let _x = std::rc::Rc::new([0u8; 64]);
    }
    println!("Rc: {:?}", start.elapsed());

    // Arc (heap + atomic refcount)
    let start = Instant::now();
    for _ in 0..n {
        let _x = std::sync::Arc::new([0u8; 64]);
    }
    println!("Arc: {:?}", start.elapsed());
}

// Typical results:
// Stack: ~0ms (optimized away or near-zero)
// Box:   ~15ms
// Rc:    ~20ms
// Arc:   ~25ms
```

## 💡 4. Worked Examples

### Example 11.6.1 — Thread-Safe Cache

```rust
use std::collections::HashMap;
use std::sync::{Arc, RwLock};

#[derive(Clone)]
struct Cache<K, V> {
    store: Arc<RwLock<HashMap<K, V>>>,
}

impl<K: Eq + std::hash::Hash + Clone, V: Clone> Cache<K, V> {
    fn new() -> Self {
        Cache {
            store: Arc::new(RwLock::new(HashMap::new())),
        }
    }

    fn get(&self, key: &K) -> Option<V> {
        let guard = self.store.read().unwrap();
        guard.get(key).cloned()
    }

    fn set(&self, key: K, value: V) {
        let mut guard = self.store.write().unwrap();
        guard.insert(key, value);
    }

    fn get_or_insert_with<F>(&self, key: K, f: F) -> V
    where
        F: FnOnce() -> V,
    {
        // Try read first (fast path)
        {
            let guard = self.store.read().unwrap();
            if let Some(v) = guard.get(&key) {
                return v.clone();
            }
        }
        // Upgrade to write
        let mut guard = self.store.write().unwrap();
        // Double-check (another thread might have inserted)
        guard.entry(key).or_insert_with(f).clone()
    }
}
```

### Example 11.6.2 — Observer Pattern with Weak References

```rust
use std::rc::{Rc, Weak};
use std::cell::RefCell;

trait Observer {
    fn on_event(&self, event: &str);
}

struct EventBus {
    observers: RefCell<Vec<Weak<dyn Observer>>>,
}

impl EventBus {
    fn new() -> Self {
        EventBus { observers: RefCell::new(vec![]) }
    }

    fn subscribe(&self, observer: &Rc<dyn Observer>) {
        self.observers.borrow_mut().push(Rc::downgrade(observer));
    }

    fn emit(&self, event: &str) {
        let mut observers = self.observers.borrow_mut();
        // Remove dead observers and notify live ones
        observers.retain(|weak| {
            if let Some(observer) = weak.upgrade() {
                observer.on_event(event);
                true  // Keep
            } else {
                false  // Remove (observer was dropped)
            }
        });
    }
}

struct Logger;
impl Observer for Logger {
    fn on_event(&self, event: &str) {
        println!("[LOG] {event}");
    }
}
```

### Example 11.6.3 — ECS-Style Component Storage

```rust
use std::any::{Any, TypeId};
use std::collections::HashMap;

/// Type-erased component storage (simplified ECS)
struct ComponentStore {
    stores: HashMap<TypeId, Box<dyn Any>>,
}

impl ComponentStore {
    fn new() -> Self {
        ComponentStore { stores: HashMap::new() }
    }

    fn insert<T: 'static>(&mut self, entity_id: u64, component: T) {
        let type_id = TypeId::of::<T>();
        let store = self.stores
            .entry(type_id)
            .or_insert_with(|| Box::new(HashMap::<u64, T>::new()));

        store.downcast_mut::<HashMap<u64, T>>()
            .unwrap()
            .insert(entity_id, component);
    }

    fn get<T: 'static>(&self, entity_id: u64) -> Option<&T> {
        let type_id = TypeId::of::<T>();
        self.stores.get(&type_id)?
            .downcast_ref::<HashMap<u64, T>>()?
            .get(&entity_id)
    }

    fn get_mut<T: 'static>(&mut self, entity_id: u64) -> Option<&mut T> {
        let type_id = TypeId::of::<T>();
        self.stores.get_mut(&type_id)?
            .downcast_mut::<HashMap<u64, T>>()?
            .get_mut(&entity_id)
    }
}

#[derive(Debug)]
struct Position { x: f32, y: f32 }

#[derive(Debug)]
struct Velocity { dx: f32, dy: f32 }

fn main() {
    let mut world = ComponentStore::new();

    world.insert(0, Position { x: 0.0, y: 0.0 });
    world.insert(0, Velocity { dx: 1.0, dy: 0.5 });

    if let Some(pos) = world.get::<Position>(0) {
        println!("Entity 0 position: ({}, {})", pos.x, pos.y);
    }
}
```

## ⚠️ 5. Gotchas & Common Mistakes

### Gotcha 14.6.1 — Rc/RefCell Reference Cycles = Memory Leaks

```rust
use std::rc::Rc;
use std::cell::RefCell;

struct Node {
    next: RefCell<Option<Rc<Node>>>,
}

fn main() {
    let a = Rc::new(Node { next: RefCell::new(None) });
    let b = Rc::new(Node { next: RefCell::new(Some(Rc::clone(&a))) });

    // Create cycle: a → b → a
    *a.next.borrow_mut() = Some(Rc::clone(&b));

    // Memory leak! Neither a nor b will ever be freed.
    // Fix: Use Weak<T> for back-references
}
```

### Gotcha 14.6.2 — RefCell Panics at Runtime

```rust
use std::cell::RefCell;

let data = RefCell::new(42);
let r1 = data.borrow();      // Immutable borrow
// let w = data.borrow_mut(); // PANIC! Already borrowed immutably

// Use try_borrow/try_borrow_mut to avoid panics:
match data.try_borrow_mut() {
    Ok(mut w) => *w = 100,
    Err(_) => println!("Already borrowed — skipping"),
}
```

### Gotcha 14.6.3 — Arc<Mutex<T>> Contention

```rust
// If many threads contend on the same Mutex, performance degrades
// Solutions:
// 1. Reduce critical section size (hold lock briefly)
// 2. Use RwLock if reads >> writes
// 3. Shard the data (multiple mutexes for different partitions)
// 4. Use lock-free data structures (crossbeam, dashmap)

// BAD: holding lock during I/O
let guard = data.lock().unwrap();
expensive_network_call(&guard);  // Other threads blocked!
drop(guard);

// GOOD: copy data out, release lock, then do I/O
let snapshot = {
    let guard = data.lock().unwrap();
    guard.clone()  // Quick clone
};  // Lock released
expensive_network_call(&snapshot);  // Other threads unblocked
```

### Gotcha 14.6.4 — Box<dyn Trait> vs &dyn Trait

```rust
// Box<dyn Trait>: OWNS the trait object (heap allocated)
fn create_animal() -> Box<dyn Animal> {
    Box::new(Dog { name: "Rex".into() })  // Caller owns it
}

// &dyn Trait: BORROWS the trait object (no allocation)
fn describe_animal(animal: &dyn Animal) {
    println!("{}", animal.speak());  // Just borrows
}

// Rule: Use &dyn Trait for parameters, Box<dyn Trait> for return values and storage
```

## 🧠 8. Extended Worked Examples & Deep Dives

### Example 8.1 — Arc<Mutex<T>> Alternatives: RwLock, parking_lot, and DashMap

**Problem:** You have a shared cache accessed by 100 concurrent tasks. 95% of accesses are reads, 5% are writes. Compare `Arc<Mutex<T>>`, `Arc<RwLock<T>>`, `Arc<parking_lot::RwLock<T>>`, and `DashMap` for this workload.

<details>
<summary>🔍 Full step-by-step solution</summary>

```rust
use std::collections::HashMap;
use std::sync::{Arc, Mutex, RwLock};
use std::time::Instant;

// ============================================================
// APPROACH 1: Arc<Mutex<HashMap>> — simplest, worst for read-heavy
// ============================================================
// All access (read AND write) is serialized.
// Only ONE thread can access the map at a time.

async fn mutex_approach() {
    let cache: Arc<Mutex<HashMap<String, String>>> = 
        Arc::new(Mutex::new(HashMap::new()));
    
    let mut handles = vec![];
    for i in 0..100 {
        let cache = cache.clone();
        handles.push(tokio::spawn(async move {
            for j in 0..1000 {
                if j % 20 == 0 {
                    // Write (5%)
                    let mut guard = cache.lock().unwrap();
                    guard.insert(format!("key_{i}_{j}"), format!("value_{j}"));
                } else {
                    // Read (95%)
                    let guard = cache.lock().unwrap();
                    let _ = guard.get(&format!("key_{i}_0"));
                }
                // Lock released here (RAII)
            }
        }));
    }
    for h in handles { h.await.unwrap(); }
}

// ============================================================
// APPROACH 2: Arc<RwLock<HashMap>> — better for read-heavy
// ============================================================
// Multiple readers can access simultaneously.
// Writers get exclusive access (blocks all readers).
// std::sync::RwLock can have writer starvation on some platforms.

async fn rwlock_approach() {
    let cache: Arc<RwLock<HashMap<String, String>>> = 
        Arc::new(RwLock::new(HashMap::new()));
    
    let mut handles = vec![];
    for i in 0..100 {
        let cache = cache.clone();
        handles.push(tokio::spawn(async move {
            for j in 0..1000 {
                if j % 20 == 0 {
                    // Write — exclusive lock
                    let mut guard = cache.write().unwrap();
                    guard.insert(format!("key_{i}_{j}"), format!("value_{j}"));
                } else {
                    // Read — shared lock (many readers simultaneously)
                    let guard = cache.read().unwrap();
                    let _ = guard.get(&format!("key_{i}_0"));
                }
            }
        }));
    }
    for h in handles { h.await.unwrap(); }
}

// ============================================================
// APPROACH 3: parking_lot::RwLock — faster, no poisoning
// ============================================================
// Benefits over std::sync::RwLock:
// - No poisoning (no .unwrap() needed)
// - Smaller (1 word vs 2-3 words on std)
// - Faster (optimized spinning before syscall)
// - Fair scheduling (prevents writer starvation)
// - Upgradable read locks

fn parking_lot_approach() {
    use parking_lot::RwLock;
    
    let cache: Arc<RwLock<HashMap<String, String>>> = 
        Arc::new(RwLock::new(HashMap::new()));
    
    // Read lock (no .unwrap() needed — no poisoning!)
    {
        let guard = cache.read();  // Returns RwLockReadGuard directly
        let _ = guard.get("key");
    }
    
    // Write lock
    {
        let mut guard = cache.write();
        guard.insert("key".into(), "value".into());
    }
    
    // Upgradable read lock (read → write without releasing)
    {
        let guard = cache.upgradable_read();
        if guard.get("key").is_none() {
            // Upgrade to write lock atomically
            let mut write_guard = parking_lot::RwLockUpgradableReadGuard::upgrade(guard);
            write_guard.insert("key".into(), "value".into());
        }
    }
}

// ============================================================
// APPROACH 4: DashMap — concurrent HashMap (sharded internally)
// ============================================================
// DashMap shards the map into N segments, each with its own lock.
// Different keys can be accessed concurrently without contention.
// Best for high-concurrency scenarios.

async fn dashmap_approach() {
    use dashmap::DashMap;
    
    let cache: Arc<DashMap<String, String>> = Arc::new(DashMap::new());
    
    let mut handles = vec![];
    for i in 0..100 {
        let cache = cache.clone();
        handles.push(tokio::spawn(async move {
            for j in 0..1000 {
                if j % 20 == 0 {
                    // Write — only locks the shard containing this key
                    cache.insert(format!("key_{i}_{j}"), format!("value_{j}"));
                } else {
                    // Read — only locks the shard containing this key
                    let _ = cache.get(&format!("key_{i}_0"));
                }
            }
        }));
    }
    for h in handles { h.await.unwrap(); }
}

// ============================================================
// BENCHMARK COMPARISON (typical results, 100 tasks × 1000 ops)
// ============================================================
//
// Arc<Mutex<HashMap>>:           ~45ms  (all access serialized)
// Arc<RwLock<HashMap>>:          ~12ms  (readers parallel, writers exclusive)
// Arc<parking_lot::RwLock<..>>:  ~8ms   (faster lock implementation)
// DashMap:                       ~4ms   (sharded, minimal contention)
//
// DECISION GUIDE:
// - Simple, low contention: Mutex (simplest code)
// - Read-heavy, moderate contention: RwLock
// - Read-heavy, high contention: parking_lot::RwLock
// - High contention, many keys: DashMap
// - Single writer, many readers: watch channel (see 11.5)
```

### Example 8.3 — Arena Allocators with bumpalo

**Problem:** You're building a compiler that creates millions of short-lived AST nodes during parsing. Individual heap allocations (`Box::new()`) are too slow. Use an arena allocator for bulk allocation and instant deallocation.

<details>
<summary>🔍 Full step-by-step solution</summary>

```rust
use bumpalo::Bump;
use std::time::Instant;

// ============================================================
// WHY ARENAS: The allocation problem in compilers/parsers
// ============================================================
// 
// Standard allocation (Box/Vec):
//   - Each node: malloc() call (~50-100ns)
//   - Each deallocation: free() call (~50-100ns)
//   - 1M nodes: ~100ms just for allocation
//   - Memory fragmentation over time
//
// Arena allocation (bumpalo):
//   - Allocates from a contiguous buffer (bump pointer)
//   - Each allocation: increment pointer (~1-2ns)
//   - Deallocation: free entire arena at once (~1μs for any size)
//   - Zero fragmentation (contiguous memory = cache-friendly)

// ============================================================
// AST NODES allocated in an arena
// ============================================================

#[derive(Debug)]
enum Expr<'arena> {
    Number(f64),
    String(&'arena str),
    Ident(&'arena str),
    BinaryOp {
        op: BinOp,
        left: &'arena Expr<'arena>,
        right: &'arena Expr<'arena>,
    },
    Call {
        function: &'arena str,
        args: &'arena [&'arena Expr<'arena>],
    },
    If {
        condition: &'arena Expr<'arena>,
        then_branch: &'arena Expr<'arena>,
        else_branch: Option<&'arena Expr<'arena>>,
    },
}

#[derive(Debug, Clone, Copy)]
enum BinOp { Add, Sub, Mul, Div }

// ============================================================
// PARSER using arena allocation
// ============================================================

struct Parser<'arena> {
    arena: &'arena Bump,
    tokens: Vec<String>,
    pos: usize,
}

impl<'arena> Parser<'arena> {
    fn new(arena: &'arena Bump, tokens: Vec<String>) -> Self {
        Parser { arena, tokens, pos: 0 }
    }
    
    /// Allocate an expression in the arena (returns &'arena reference)
    fn alloc_expr(&self, expr: Expr<'arena>) -> &'arena Expr<'arena> {
        self.arena.alloc(expr)
    }
    
    /// Allocate a string in the arena
    fn alloc_str(&self, s: &str) -> &'arena str {
        self.arena.alloc_str(s)
    }
    
    /// Allocate a slice in the arena
    fn alloc_slice(&self, items: Vec<&'arena Expr<'arena>>) -> &'arena [&'arena Expr<'arena>] {
        self.arena.alloc_slice_copy(&items)
    }
    
    fn parse_expr(&mut self) -> &'arena Expr<'arena> {
        // Simplified parser for demonstration
        let left = self.parse_primary();
        
        if self.pos < self.tokens.len() && self.tokens[self.pos] == "+" {
            self.pos += 1;
            let right = self.parse_primary();
            self.alloc_expr(Expr::BinaryOp {
                op: BinOp::Add,
                left,
                right,
            })
        } else {
            left
        }
    }
    
    fn parse_primary(&mut self) -> &'arena Expr<'arena> {
        if self.pos >= self.tokens.len() {
            return self.alloc_expr(Expr::Number(0.0));
        }
        
        let token = &self.tokens[self.pos];
        self.pos += 1;
        
        if let Ok(n) = token.parse::<f64>() {
            self.alloc_expr(Expr::Number(n))
        } else {
            let name = self.alloc_str(token);
            self.alloc_expr(Expr::Ident(name))
        }
    }
}

// ============================================================
// BENCHMARK: Arena vs Box allocation
// ============================================================

fn benchmark_arena_vs_box() {
    let n = 1_000_000;
    
    // Arena allocation
    let start = Instant::now();
    let arena = Bump::new();
    for i in 0..n {
        let _: &Expr = arena.alloc(Expr::Number(i as f64));
    }
    let arena_time = start.elapsed();
    let arena_bytes = arena.allocated_bytes();
    drop(arena);  // Frees ALL allocations instantly
    println!("Arena: {:?} ({} bytes allocated)", arena_time, arena_bytes);
    
    // Box allocation
    let start = Instant::now();
    let mut nodes: Vec<Box<Expr>> = Vec::with_capacity(n);
    for i in 0..n {
        nodes.push(Box::new(Expr::Number(i as f64)));
    }
    let box_time = start.elapsed();
    drop(nodes);  // Frees each allocation individually
    println!("Box:   {:?}", box_time);
    
    // Typical results:
    // Arena: ~5ms (1M allocations)
    // Box:   ~45ms (1M allocations)
    // Arena is ~9x faster for bulk allocation
}

fn main() {
    // Create arena (lives for the duration of compilation)
    let arena = Bump::new();
    
    // Parse source code (all AST nodes live in the arena)
    let tokens = vec!["x".into(), "+".into(), "42".into()];
    let mut parser = Parser::new(&arena, tokens);
    let ast = parser.parse_expr();
    
    println!("AST: {ast:?}");
    // Expr::BinaryOp { op: Add, left: Ident("x"), right: Number(42.0) }
    
    // Process the AST...
    // ...
    
    // When arena is dropped, ALL AST nodes are freed at once
    // No individual destructors, no traversal needed
    drop(arena);
}
```

### 9.1 Atomics: Mara Bos's Mental Model for Memory Ordering

Atomic operations are the foundation of all lock-free programming. The key challenge is understanding **memory ordering** — the guarantees about when writes by one thread become visible to other threads.

**The mental model (from "Rust Atomics and Locks" by Mara Bos):**

Think of each thread as having its own **notebook** (local cache). When a thread writes to an atomic variable, it writes in its notebook. The question is: when does that write appear in other threads' notebooks?

**The five orderings (from weakest to strongest):**

```rust
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};

// Relaxed: No ordering guarantees between different variables.
// Only guarantees: atomic (no torn reads/writes) and total order per variable.
// Use for: counters, statistics, anything where you don't need synchronization.
static COUNTER: AtomicU64 = AtomicU64::new(0);
fn increment() {
    COUNTER.fetch_add(1, Ordering::Relaxed);
    // Other threads will EVENTUALLY see this, but no guarantee about
    // ordering relative to other memory operations.
}

// Acquire: When loading, ensures all writes that happened BEFORE the
// corresponding Release store are visible to this thread.
// Use for: the "reader" side of a lock or flag.

// Release: When storing, ensures all previous writes by this thread
// are visible to threads that do an Acquire load of this variable.
// Use for: the "writer" side of a lock or flag.

static FLAG: AtomicBool = AtomicBool::new(false);
static mut DATA: u64 = 0;  // Protected by FLAG

fn producer() {
    unsafe { DATA = 42; }  // Write data FIRST
    FLAG.store(true, Ordering::Release);  // Then signal (Release)
    // Release guarantees: DATA=42 is visible to anyone who sees FLAG=true
}

fn consumer() {
    while !FLAG.load(Ordering::Acquire) {}  // Wait for signal (Acquire)
    // Acquire guarantees: we see all writes before the Release store
    let value = unsafe { DATA };  // Guaranteed to see 42
    assert_eq!(value, 42);
}

// AcqRel: Both Acquire and Release (for read-modify-write operations).
// Use for: compare_exchange, fetch_add when the result is used for synchronization.

// SeqCst: Sequential Consistency — strongest ordering.
// All SeqCst operations appear in a single global total order.
// Use for: when you need a global ordering across multiple variables.
// (Rarely needed; usually Acquire/Release suffices.)
```

**Practical rules of thumb:**

1. **Counters/statistics**: Use `Relaxed` (no synchronization needed)
2. **Flags/signals**: Use `Release` for store, `Acquire` for load
3. **Locks**: Use `Acquire` for lock, `Release` for unlock
4. **When in doubt**: Use `SeqCst` (correct but potentially slower)
5. **compare_exchange**: Usually `AcqRel` for success, `Acquire` for failure

**Common patterns:**

```rust
use std::sync::atomic::{AtomicUsize, AtomicBool, Ordering};
use std::sync::Arc;

// Pattern 1: Spin lock (educational — use parking_lot in production)
struct SpinLock {
    locked: AtomicBool,
}

impl SpinLock {
    fn new() -> Self { SpinLock { locked: AtomicBool::new(false) } }
    
    fn lock(&self) {
        while self.locked.compare_exchange_weak(
            false, true, Ordering::Acquire, Ordering::Relaxed
        ).is_err() {
            std::hint::spin_loop();  // CPU hint: we're spinning
        }
    }
    
    fn unlock(&self) {
        self.locked.store(false, Ordering::Release);
    }
}

// Pattern 2: One-shot initialization (like std::sync::Once)
struct OnceCell {
    initialized: AtomicBool,
    // ... data ...
}

// Pattern 3: Reference counting (simplified Arc)
struct MyArc<T> {
    count: AtomicUsize,
    data: T,
}

impl<T> Clone for &MyArc<T> {
    fn clone(&self) -> Self {
        self.count.fetch_add(1, Ordering::Relaxed);
        // Relaxed is fine for increment — we don't need to synchronize
        // any data with the increment itself.
        *self
    }
}
// But drop needs Acquire/Release to ensure all accesses complete before free:
// count.fetch_sub(1, Ordering::Release) ... fence(Acquire) before dealloc
```

### 9.2 Lock-Free Queues: The ABA Problem and Solutions

Lock-free data structures avoid mutexes by using atomic compare-and-swap (CAS) operations. The most famous challenge is the **ABA problem**.

**The ABA problem explained:**

```
Thread 1: Reads pointer P = A (node at address 0x1000)
Thread 1: Gets preempted...

Thread 2: Pops A from the queue
Thread 2: Frees A's memory (address 0x1000 is now available)
Thread 2: Pushes B (allocator reuses address 0x1000!)
Thread 2: Now the queue head is at 0x1000 again, but it's B, not A

Thread 1: Resumes, does CAS(head, expected=0x1000, new=A.next)
Thread 1: CAS succeeds! (head IS 0x1000) — but it's the WRONG node!
Thread 1: Queue is now corrupted.
```

The pointer value is the same (A), but the data it points to has changed (B). CAS can't detect this.

**Solutions:**

1. **Tagged pointers**: Add a monotonically increasing counter to the pointer. CAS checks both pointer AND counter. Even if the address is reused, the counter will differ.

2. **Epoch-based reclamation (crossbeam)**: Don't free memory until all threads that might hold references have "moved on." This prevents address reuse during the critical window.

3. **Hazard pointers**: Each thread publishes which pointers it's currently accessing. Memory is only freed when no thread has it as a hazard pointer.

**crossbeam's approach (epoch-based):**

```rust
// crossbeam uses epochs (generations) to defer deallocation:
// 
// Global epoch: 0, 1, 2 (cycles)
// Each thread pins to the current epoch before accessing shared data.
// Memory freed in epoch N is only reclaimed when ALL threads have
// advanced past epoch N+2 (ensuring no thread can still hold a reference).
//
// This is why crossbeam::epoch::pin() exists — it tells the system
// "I'm about to access shared data, don't free anything I might see."
```

### 9.3 Interior Mutability: UnsafeCell and the Compiler's Aliasing Assumptions

All interior mutability in Rust ultimately goes through `UnsafeCell<T>` — it's the only primitive that allows mutation through a shared reference. Understanding why is key to understanding Rust's safety model.

**The aliasing assumption:**

The Rust compiler assumes that `&T` references are **immutable** — the data behind them won't change during the reference's lifetime. This enables powerful optimizations:

```rust
fn example(x: &i32, y: &i32) -> i32 {
    let a = *x;
    // The compiler can assume *x hasn't changed here
    // because no &mut i32 can exist while &i32 exists
    let b = *x;  // Compiler can optimize: b = a (no reload needed)
    a + b + *y
}
```

**UnsafeCell breaks this assumption (legally):**

```rust
use std::cell::UnsafeCell;

// UnsafeCell tells the compiler: "don't assume immutability here"
pub struct Cell<T> {
    value: UnsafeCell<T>,
}

impl<T: Copy> Cell<T> {
    pub fn get(&self) -> T {
        // SAFETY: Cell is !Sync, so only one thread accesses this.
        // We return a copy, so no aliasing issues.
        unsafe { *self.value.get() }
    }
    
    pub fn set(&self, val: T) {
        // SAFETY: Cell is !Sync, single-threaded access guaranteed.
        // T: Copy means no Drop to worry about.
        unsafe { *self.value.get() = val; }
    }
}

// RefCell uses UnsafeCell + runtime borrow tracking:
pub struct RefCell<T> {
    borrow_state: Cell<isize>,  // -1 = mut borrowed, 0 = free, >0 = shared borrows
    value: UnsafeCell<T>,
}

// Mutex uses UnsafeCell + OS synchronization:
pub struct Mutex<T> {
    lock: sys::Mutex,  // OS mutex primitive
    data: UnsafeCell<T>,
}
```

**The hierarchy of interior mutability:**

```
UnsafeCell<T>          — raw primitive, unsafe to use
    ├── Cell<T>        — Copy types only, zero overhead, !Sync
    ├── RefCell<T>     — any type, runtime borrow checking, !Sync
    ├── Mutex<T>       — any type, OS lock, Sync (thread-safe)
    ├── RwLock<T>      — any type, readers-writer lock, Sync
    ├── AtomicT        — primitive types, lock-free, Sync
    └── OnceCell<T>    — write-once, then immutable, Sync
```

**Why Cell is !Sync but Send:**

`Cell<T>` is `Send` (can be moved to another thread) but `!Sync` (can't be shared between threads via `&Cell<T>`). This is because `Cell::set()` takes `&self` — if two threads had `&Cell<T>` simultaneously, they could race on `set()` without synchronization.

### 9.4 Custom Allocators and the Global Allocator

Rust allows replacing the global memory allocator and using custom allocators for specific collections.

**Replacing the global allocator:**

```rust
// Use jemalloc for better multi-threaded performance:
#[global_allocator]
static GLOBAL: tikv_jemallocator::Jemalloc = tikv_jemallocator::Jemalloc;

// Or mimalloc for general-purpose speed:
// #[global_allocator]
// static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;

// Or a tracking allocator for debugging:
use std::alloc::{GlobalAlloc, Layout, System};
use std::sync::atomic::{AtomicUsize, Ordering};

struct TrackingAllocator;
static ALLOCATED: AtomicUsize = AtomicUsize::new(0);

unsafe impl GlobalAlloc for TrackingAllocator {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        ALLOCATED.fetch_add(layout.size(), Ordering::Relaxed);
        System.alloc(layout)
    }
    
    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) {
        ALLOCATED.fetch_sub(layout.size(), Ordering::Relaxed);
        System.dealloc(ptr, layout)
    }
}

#[global_allocator]
static ALLOC: TrackingAllocator = TrackingAllocator;

fn check_allocations() {
    println!("Currently allocated: {} bytes", ALLOCATED.load(Ordering::Relaxed));
}
```

**The Allocator API (nightly):**

The unstable `Allocator` trait allows per-collection allocators:

```rust
// Nightly only: #![feature(allocator_api)]

// vec.push(1);

// // When arena is dropped, all memory freed at once
```

On stable, use `bumpalo::collections::Vec` for arena-allocated vectors.
