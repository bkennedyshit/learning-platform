## 📚 1. ROS 2 Core Concepts

### Node
A unit of computation. Each node has a name, params, and a process boundary.

### Topic (pub/sub)
Asynchronous many-to-many message stream:
```python
# rclpy publisher
self.pub = self.create_publisher(Twist, '/cmd_vel', 10)
self.pub.publish(Twist(...))
```

### Service (RPC)
Synchronous request/response (e.g., `Trigger`, custom `.srv`).

### Action
Long-running goal with **feedback** + **result** + **cancel** semantics. Used for navigation goals, arm motion plans, behaviors.

### Parameter
Runtime configuration; can be set per-node, namespaced, dynamically reconfigurable.

### Lifecycle node
A node with managed states (unconfigured → inactive → active → deactivated → finalized) — required for safety-critical / multi-node coordinated startup.

## 🌐 2. DDS — The Wire Protocol

ROS 2 sits on **DDS (Data Distribution Service)** — a publish/subscribe middleware standard. Common implementations: **Fast DDS** (default), **Cyclone DDS** (lightweight), **RTI Connext**, **Eclipse Zenoh** (newer 2026 alternative).

### QoS profiles to know

| Policy | Options | Choose by |
|---|---|---|
| Reliability | RELIABLE / BEST_EFFORT | Sensor streams → BEST_EFFORT; commands → RELIABLE |
| Durability | VOLATILE / TRANSIENT_LOCAL | Late-joining subscribers need TRANSIENT_LOCAL |
| History | KEEP_LAST(n) / KEEP_ALL | Buffer depth |
| Deadline | period | Timing contract |
| Liveliness | AUTOMATIC / MANUAL | Stale-detection |

Default profiles cover most cases; mismatches between pub/sub QoS silently break communication — `ros2 topic info -v` shows them.

## 🌳 3. tf2 — The Transform Tree

`tf2` maintains a time-stamped tree of frames. Every transform must have a unique parent, and the tree must be a DAG (single root per chain).

```python
self.tf_buffer = Buffer()
self.tf_listener = TransformListener(self.tf_buffer, self)
T = self.tf_buffer.lookup_transform('map', 'base_link', now)
```

Run `ros2 run tf2_tools view_frames` to dump the tree as a PDF.

## 🛠️ 4. URDF / Xacro

`URDF` describes a robot's kinematic + visual + collision + inertial structure. `xacro` adds macros, parameters, and includes.

```xml
<robot name="my_robot">
  <link name="base_link">
    <visual>...</visual>
    <collision>...</collision>
    <inertial>...</inertial>
  </link>
  <joint name="wheel_joint" type="continuous">
    <parent link="base_link"/>
    <child  link="wheel_left_link"/>
    <axis xyz="0 1 0"/>
    <origin xyz="0.1 0.15 -0.05"/>
  </joint>
</robot>
```

`robot_state_publisher` reads the URDF + listens to `/joint_states` and broadcasts the resulting tf transforms.

## 🚀 5. launch.py — The Composition Layer

```python
from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    return LaunchDescription([
        Node(package='my_robot', executable='driver',
             parameters=[{'serial_port': '/dev/ttyUSB0'}]),
        Node(package='robot_state_publisher', executable='robot_state_publisher',
             parameters=[{'robot_description': open('urdf/my_robot.urdf').read()}]),
    ])
```

Compose multiple `launch_description`s for hierarchical bring-up (sim + real, single + multi-robot).

## 🤖 6. ROS 2 vs Proprietary "Physical AI" Stacks

The 2026 industry split:

| Stack | Strengths | Trade-off |
|---|---|---|
| **ROS 2 + Nav2 + MoveIt 2 + Drake / MuJoCo** | Open, modular, vendor-agnostic | More integration work |
| **NVIDIA Isaac (Sim + Lab + ROS bridge)** | GPU sim + RL + cuRobo | Locked to NVIDIA HW for parts |
| **Skild AI / Helix / Figure 03 internal stack** | End-to-end VLA models (vision-language-action) | Closed, single-vendor |
| **Tesla Optimus internal** | Vertical integration, scale | Closed, proprietary |
| **Eclipse Zenoh** | Lightweight, edge-friendly DDS alternative | Newer, smaller ecosystem |

For most roboticists in 2026: **start with ROS 2 + simulators**, integrate proprietary AI components via topics / services. Don't bet your codebase on one vendor's closed stack.

## 🛠️ 7. Worked Example (skeleton) — Differential-Drive Bring-Up

1. Workspace `~/ros2_ws`, package `bot_bringup`.
2. URDF with two drive wheels + caster.
3. `bot_driver` node (rclcpp): reads `/cmd_vel`, drives motors via serial / micro-ROS.
4. `bot_odom` node: reads encoders, publishes `/odom` + `tf base_link → odom`.
5. `imu_filter_madgwick` node: fuses IMU.
6. `robot_localization` EKF: fuses odom + IMU → `/odometry/filtered`.
7. `launch.py` brings them all up.
8. `ros2 run rviz2 rviz2` or `foxglove-studio` to visualize.

## ⚠️ 9. Common Misconceptions

- **"ROS 1 and ROS 2 are similar."** Different middleware, different lifecycle, different launch format. Don't port; rewrite.
- **"BEST_EFFORT QoS is fine for everything."** It silently drops messages — wrong choice for `/cmd_vel` or any safety-critical command.
- **"Foxglove replaces RViz."** They overlap; Foxglove + rerun.io are *better* for multi-modal logging, RViz is *closer* to the ROS native introspection.
- **"You can ignore the tf tree."** You cannot. Half of ROS 2 bugs are tf misconfigurations.
- **"Proprietary stacks make ROS 2 obsolete."** They specialize on top of (or around) it — ROS 2 fluency remains a force multiplier.
