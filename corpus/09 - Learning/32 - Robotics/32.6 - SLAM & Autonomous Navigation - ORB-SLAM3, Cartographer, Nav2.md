## 📚 1. The SLAM Problem

Given:
- Sequence of control inputs $u_{1:t}$
- Sequence of sensor measurements $z_{1:t}$

Estimate jointly:
- Robot trajectory $x_{1:t}$
- Map $m$

$$
p(x_{1:t}, m \mid u_{1:t}, z_{1:t})
$$

Two big families:
- **Filter-based** (EKF SLAM, particle filter / FastSLAM) — recursive, online.
- **Graph-based / factor-graph** — global optimization, with loop-closure relinearization. Modern dominant approach.

## 🗺️ 2. Modern SLAM Stacks

| Stack | Sensors | Best at |
|---|---|---|
| **slam_toolbox** | 2D LiDAR + odom | Indoor mobile robots; live + offline maps |
| **Cartographer** | 2D / 3D LiDAR + IMU | High-quality 2D maps; 3D in fewer scenarios |
| **ORB-SLAM3** | Mono / stereo / RGB-D + IMU | Visual-inertial, multi-session multi-map ([UZ-SLAMLab/ORB_SLAM3](https://github.com/UZ-SLAMLab/ORB_SLAM3)) |
| **OpenVINS** | Visual-inertial | Drone-grade VIO |
| **LIO-SAM / LIO-Livox / FAST-LIO2** | LiDAR-IMU | Outdoor robotics, drones |
| **VINS-Fusion** | Visual-inertial + GPS | Outdoor multimodal |
| **Kimera** | Visual-inertial + semantic | Research; semantic mapping |
| **NeRF / 3DGS-SLAM (research)** | RGB / RGB-D | Photorealistic reconstructions; not yet real-time on robot |

## 🧭 3. Nav2 — The Navigation Stack

Nav2 is the ROS 2 successor to ROS 1's `move_base`. Architecture:

```mermaid
flowchart LR
  GOAL[Goal pose] --> BT[Behavior Tree]
  BT --> GP[Global Planner]
  GP --> LP[Local Planner / Controller]
  LP --> CMD[/cmd_vel]
  COSTMAP_G[Global Costmap] --> GP
  COSTMAP_L[Local Costmap] --> LP
  SCANS[LiDAR / RGB-D] --> COSTMAP_G
  SCANS --> COSTMAP_L
  TF[tf tree] --> COSTMAP_G
  TF --> COSTMAP_L
```

### Key plugins
- Global planners: **NavFn** (default), **Smac** (state lattice), **Theta***.
- Controllers: **DWB**, **MPPI** (sampling MPC), **Regulated Pure Pursuit**, **Vector Pursuit**.
- Smoothers, recoveries, behavior trees (`xml`).
- Costmap layers: static (map), inflation, voxel/obstacle (live sensors), keepout zones.

### Tuning checklist
1. Robot footprint (polygon).
2. Inflation radius (≥ robot radius + safety).
3. Controller velocities + accelerations match physical limits.
4. Behavior tree: pick "navigate_to_pose" or "navigate_through_poses".
5. Recovery behaviors (clear costmap, spin, backup).

## 🛠️ 4. Worked Example (skeleton) — Indoor Mobile Robot

1. Bring up robot driver + sensors + tf.
2. Run **slam_toolbox** to map the room (drive around, save map).
3. Switch slam_toolbox to **localization mode** OR run **AMCL** on the saved map.
4. Bring up Nav2 with default parameters; adjust footprint + inflation.
5. Send goals from RViz; verify recovery behaviors trigger when needed.
6. Replace global planner with Smac for non-circular footprints (e.g., long+narrow robots).

## ⚠️ 6. Common Misconceptions

- **"SLAM is solved."** It's solved for known sensor configurations and benign environments. Long-term, multi-session, dynamic, semantic, and degenerate scenes are still active research.
- **"More features = better visual SLAM."** Feature density past a point gives diminishing returns and increases compute. Filter aggressively.
- **"AMCL with a 5-year-old map is fine."** Drift in furniture / dynamic objects defeats AMCL. Periodically remap or use SLAM in localization mode.
- **"Nav2 is plug-and-play."** Default parameters are starting points, not production tuning. Costmaps and footprints especially require attention.
