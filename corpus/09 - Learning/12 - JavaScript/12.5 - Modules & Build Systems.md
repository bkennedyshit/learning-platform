# 12.5 — Modules & Build Systems

> *"The lack of a module system is JavaScript's biggest design flaw. We've spent 15 years fixing it."* — **Isaac Z. Schlueter**, creator of npm

> *"Vite is not a bundler. It's a dev server that happens to bundle for production."* — **Evan You**, creator of Vite and Vue.js

For the first 15 years of JavaScript (1995–2010), there was NO module system. Everything was global. Libraries attached themselves to `window`. Dependency management meant ordering `<script>` tags correctly. The Dreamweaver era you remember? That was it.

Today we have **ESM** (ECMAScript Modules) — the official standard — plus a legacy system (**CommonJS**) that Node.js used for a decade. This chapter teaches both, explains the interop challenges, and covers the build tools that transform your source code into optimized production bundles.

---

## 🎯 Learning Objectives

1. **Write and consume ESM modules** — `import`, `export`, `export default`, re-exports.
2. **Understand CommonJS** — `require`, `module.exports`, and why it still exists.
3. **Navigate ESM/CJS interop** — the `"type": "module"` field, `.mjs`/`.cjs` extensions, and dual-package patterns.
4. **Configure Vite** for development and production builds.
5. **Explain tree shaking** — how bundlers eliminate dead code and why ESM enables it.
6. **Implement code splitting** — dynamic `import()` for lazy loading.
7. **Compare bundlers** — Vite, esbuild, Webpack, Rollup, Turbopack — and choose appropriately.

## 📚 1. ECMAScript Modules (ESM) — The Standard

### Definition 12.5.1 — Named Exports

```javascript
// math.js — multiple named exports
export const PI = 3.14159265358979;
export const E = 2.71828182845905;

export function add(a, b) { return a + b; }
export function multiply(a, b) { return a * b; }

export class Vector {
  constructor(x, y) { this.x = x; this.y = y; }
  magnitude() { return Math.hypot(this.x, this.y); }
}
```

```javascript
// consumer.js — importing named exports
import { add, multiply, PI } from "./math.js";
import { Vector } from "./math.js";

// Rename on import
import { add as sum } from "./math.js";

// Import everything as namespace
import * as MathUtils from "./math.js";
MathUtils.add(1, 2); // 3
MathUtils.PI;        // 3.14159...
```

### Definition 12.5.2 — Default Exports

Each module can have ONE default export (plus any number of named exports):

```javascript
// logger.js
export default class Logger {
  log(msg) { console.log(`[${new Date().toISOString()}] ${msg}`); }
}

// Also valid: export default function, export default expression
```

```javascript
// consumer.js — default import (any name works)
import Logger from "./logger.js";
import MyLogger from "./logger.js"; // Same thing, different name

// Combine default + named
import Logger, { formatMessage } from "./logger.js";
```

**Best practice:** Prefer **named exports** over default exports. Named exports enable better tree shaking, IDE auto-imports, and refactoring. Default exports make renaming invisible and harder to grep.

### Definition 12.5.3 — Re-exports (Barrel Files)

```javascript
// utils/index.js — re-export from multiple modules
export { add, multiply } from "./math.js";
export { default as Logger } from "./logger.js";
export { formatDate, parseDate } from "./dates.js";
export * from "./strings.js"; // Re-export all named exports

// Now consumers can import from one path:
import { add, Logger, formatDate } from "./utils/index.js";
```

⚠️ **Barrel file warning:** Large barrel files can hurt tree shaking and increase bundle size if the bundler can't eliminate unused re-exports. Use them for public API boundaries, not internal code.

### Definition 12.5.4 — Dynamic `import()` (Code Splitting)

```javascript
// Static import — loaded at parse time, hoisted
import { heavyFunction } from "./heavy-module.js";

// Dynamic import — loaded at runtime, returns a Promise
const button = document.getElementById("analyze");
button.addEventListener("click", async () => {
  // Module is only downloaded when user clicks
  const { heavyFunction } = await import("./heavy-module.js");
  const result = heavyFunction(data);
  displayResult(result);
});

// Conditional imports
const adapter = await import(
  process.env.DB_TYPE === "postgres"
    ? "./adapters/postgres.js"
    : "./adapters/sqlite.js"
);
```

### ESM Characteristics

| Property | Behavior |
|----------|----------|
| **Parsing** | Static — imports are analyzed at parse time (before execution) |
| **Binding** | Live bindings — importing a variable gives you a live reference |
| **Execution** | Deferred — module code runs after the entire dependency graph is loaded |
| **Scope** | Each module has its own scope (no global pollution) |
| **Strict mode** | Always in strict mode (no `with`, no implicit globals) |
| **`this`** | `this` is `undefined` at module top level (not `window`) |

```javascript
// Live bindings demonstration
// counter.js
export let count = 0;
export function increment() { count++; }

// main.js
import { count, increment } from "./counter.js";
console.log(count); // 0
increment();
console.log(count); // 1 — live binding updated!
```

## 📚 2. CommonJS (CJS) — The Legacy System

### Definition 12.5.5 — CommonJS Syntax

```javascript
// math.cjs (or .js without "type": "module")
const PI = 3.14159;

function add(a, b) { return a + b; }

// Single export object
module.exports = { PI, add };

// Or attach to exports shorthand
exports.multiply = (a, b) => a * b;
```

```javascript
// consumer.cjs
const { PI, add } = require("./math.cjs");
const math = require("./math.cjs"); // Entire module object

// Conditional require (works because require is synchronous)
if (process.env.NODE_ENV === "development") {
  const debug = require("./debug.cjs");
}
```

### CJS vs ESM — Key Differences

| Feature | CommonJS | ESM |
|---------|----------|-----|
| Syntax | `require()` / `module.exports` | `import` / `export` |
| Loading | Synchronous | Asynchronous |
| Parsing | Dynamic (runtime) | Static (parse time) |
| Bindings | Value copy | Live reference |
| Tree shaking | ❌ Not possible | ✅ Enabled by static analysis |
| Top-level await | ❌ No | ✅ Yes |
| Browser support | ❌ Needs bundler | ✅ Native (`<script type="module">`) |
| `this` at top level | `module.exports` | `undefined` |
| Conditional imports | ✅ `if (x) require(y)` | ⚠️ Only via dynamic `import()` |

### Definition 12.5.6 — Interop Between ESM and CJS

```javascript
// ESM importing CJS — generally works
import lodash from "lodash"; // CJS default = module.exports
import { debounce } from "lodash"; // May or may not work (depends on bundler)

// CJS importing ESM — requires dynamic import (async)
// ❌ const { add } = require("./esm-module.mjs"); // Error!
// ✅ 
const { add } = await import("./esm-module.mjs"); // Works in async context
```

### The `"type"` Field in package.json

```json
{
  "type": "module"  // All .js files are ESM
}
```

| `"type"` value | `.js` treated as | Use `.cjs` for | Use `.mjs` for |
|---------------|------------------|----------------|----------------|
| `"module"` | ESM | CJS files | (already ESM) |
| `"commonjs"` (default) | CJS | (already CJS) | ESM files |

**Rule:** Always set `"type": "module"` in new projects. Use `.cjs` extension for the rare CJS file you need (like `postcss.config.cjs`).

## 📚 3. Build Tools & Bundlers

### Definition 12.5.7 — Why Bundle?

Browsers can load ESM natively, so why bundle?

1. **Performance** — Hundreds of HTTP requests for individual modules is slow. Bundling reduces requests.
2. **Tree shaking** — Remove unused code from dependencies.
3. **Code splitting** — Split into chunks loaded on demand.
4. **Transpilation** — Convert TypeScript, JSX, modern syntax to compatible JS.
5. **Asset handling** — Process CSS, images, fonts, SVGs.
6. **Minification** — Reduce file size for production.

### Definition 12.5.8 — Vite (The Modern Default)

**Vite** (2020, Evan You) is a build tool that uses:
- **Dev server:** Native ESM + esbuild for instant HMR (Hot Module Replacement)
- **Production:** Rollup for optimized bundles

```bash
# Create a new Vite project
pnpm create vite my-app --template vanilla-ts
cd my-app
pnpm install
pnpm dev    # Dev server at localhost:5173
pnpm build  # Production build to dist/
```

```javascript
// vite.config.js
import { defineConfig } from "vite";

export default defineConfig({
  build: {
    target: "es2022",        // Modern browsers only
    minify: "esbuild",      // Fastest minifier
    sourcemap: true,        // Debug production issues
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["react", "react-dom"], // Separate vendor chunk
        },
      },
    },
  },
  server: {
    port: 3000,
    open: true,             // Auto-open browser
  },
});
```

**Why Vite wins in 2026:**
- Dev server starts in <100ms (no bundling in dev — serves ESM directly)
- HMR updates in <50ms (only re-processes the changed module)
- Production builds are optimized via Rollup
- First-class TypeScript, JSX, CSS Modules support
- Plugin ecosystem (compatible with Rollup plugins)

### Definition 12.5.9 — esbuild (The Speed Demon)

**esbuild** (2020, Evan Wallace) is a bundler/minifier written in Go. It's 10–100x faster than Webpack:

```bash
# Bundle a file
esbuild src/index.ts --bundle --outfile=dist/bundle.js --format=esm --minify

# Watch mode
esbuild src/index.ts --bundle --outdir=dist --watch --servedir=public
```

```javascript
// build.mjs — programmatic API
import * as esbuild from "esbuild";

await esbuild.build({
  entryPoints: ["src/index.ts"],
  bundle: true,
  outdir: "dist",
  format: "esm",
  splitting: true,     // Code splitting
  minify: true,
  sourcemap: true,
  target: ["es2022"],
  external: ["fsevents"], // Don't bundle native modules
});
```

**Use esbuild when:** You need raw speed for library builds, CI pipelines, or simple applications without complex plugin needs.

### Definition 12.5.10 — Webpack (The Legacy Giant)

**Webpack** (2012) is the most configurable bundler but also the most complex:

```javascript
// webpack.config.js
import path from "path";

export default {
  entry: "./src/index.js",
  output: {
    path: path.resolve("dist"),
    filename: "[name].[contenthash].js",
    clean: true,
  },
  module: {
    rules: [
      { test: /\.tsx?$/, use: "ts-loader" },
      { test: /\.css$/, use: ["style-loader", "css-loader"] },
    ],
  },
  optimization: {
    splitChunks: { chunks: "all" },
  },
};
```

**Use Webpack when:** You're maintaining a legacy project, need specific Webpack plugins, or require advanced code-splitting strategies not yet available in Vite.

### Bundler Comparison (2026)

| Feature | Vite | esbuild | Webpack | Turbopack |
|---------|------|---------|---------|-----------|
| **Dev speed** | ⚡ Instant | ⚡ Instant | 🐌 Slow | ⚡ Instant |
| **Build speed** | Fast | ⚡ Fastest | Slow | Fast |
| **Config complexity** | Low | Minimal | High | Low |
| **Plugin ecosystem** | Large (Rollup) | Small | Largest | Growing |
| **Code splitting** | ✅ | ✅ | ✅ | ✅ |
| **HMR** | ✅ Fast | ⚠️ Basic | ✅ | ✅ Fast |
| **Best for** | Apps | Libraries/CI | Legacy | Next.js |

## 📚 4. Tree Shaking

### Definition 12.5.11 — Tree Shaking

**Tree shaking** is dead code elimination based on static analysis of ESM `import`/`export` statements:

```javascript
// utils.js — exports 10 functions
export function add(a, b) { return a + b; }
export function subtract(a, b) { return a - b; }
export function multiply(a, b) { return a * b; }
// ... 7 more functions

// app.js — only uses one
import { add } from "./utils.js";
console.log(add(1, 2));

// After tree shaking: only `add` is in the bundle.
// subtract, multiply, etc. are eliminated.
```

**Why CJS can't be tree-shaken:**

```javascript
// CJS — dynamic, can't statically analyze
const utils = require("./utils");
// Which properties of `utils` are used? Can't know until runtime.
// Maybe: utils[someVariable]() — impossible to analyze statically.
```

### Ensuring Tree Shaking Works

```json
// package.json of a library
{
  "sideEffects": false,  // Tell bundler: all files are pure (safe to eliminate)
  // Or specify files WITH side effects:
  "sideEffects": ["./src/polyfills.js", "*.css"]
}
```

```javascript
// ❌ Prevents tree shaking (side effect at module level)
export const logger = createLogger(); // Runs on import!

// ✅ Tree-shakeable (pure — no side effects on import)
export function createLogger() { return new Logger(); }
```

## 📚 5. Code Splitting Strategies

### Route-Based Splitting (Most Common)

```javascript
// React with lazy loading
import { lazy, Suspense } from "react";

const Dashboard = lazy(() => import("./pages/Dashboard"));
const Settings = lazy(() => import("./pages/Settings"));
const Analytics = lazy(() => import("./pages/Analytics"));

function App() {
  return (
    <Suspense fallback={<Loading />}>
      <Routes>
        <Route path="/" element={<Dashboard />} />
        <Route path="/settings" element={<Settings />} />
        <Route path="/analytics" element={<Analytics />} />
      </Routes>
    </Suspense>
  );
}
```

### Feature-Based Splitting

```javascript
// Load heavy features on demand
const editorButton = document.getElementById("open-editor");
editorButton.addEventListener("click", async () => {
  const { CodeEditor } = await import("./features/code-editor.js");
  const editor = new CodeEditor("#container");
  editor.init();
});
```

### Vendor Splitting

```javascript
// vite.config.js — separate vendor chunk (cached independently)
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks(id) {
          if (id.includes("node_modules")) {
            if (id.includes("react")) return "react-vendor";
            if (id.includes("lodash")) return "lodash-vendor";
            return "vendor";
          }
        },
      },
    },
  },
});
```

## 🏗️ 8. Extended Worked Examples & Deep Dives

### 8.1 — Dual-Package ESM/CJS Hazard

Publishing a package that works in both ESM (`import`) and CJS (`require()`) is one of the hardest problems in the Node.js ecosystem.

#### The Problem

```js
// Your library exports a singleton:
// lib.js (CJS)
let instance = null;
module.exports.getInstance = () => {
  if (!instance) instance = { id: Math.random() };
  return instance;
};

// If a user imports your package via BOTH systems in the same app:
const { getInstance: cjsGet } = require("your-lib");     // CJS copy
import { getInstance as esmGet } from "your-lib";         // ESM copy

// DIFFERENT instances! The module was loaded TWICE!
cjsGet() !== esmGet(); // true — singleton is broken!
```

#### Why It Happens

```
When Node.js encounters a dual-package:
1. CJS require() → loads the CJS entry point → creates Module A
2. ESM import → loads the ESM entry point → creates Module B

These are SEPARATE module instances with SEPARATE state!
The "dual-package hazard" means stateful modules break.
```

#### Solutions

```json
// package.json — Conditional exports (Node.js 12.7+)
{
  "name": "my-lib",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs",
      "types": "./dist/types/index.d.ts"
    },
    "./utils": {
      "import": "./dist/esm/utils.js",
      "require": "./dist/cjs/utils.cjs"
    }
  },
  "main": "./dist/cjs/index.cjs",
  "module": "./dist/esm/index.js",
  "types": "./dist/types/index.d.ts"
}
```

```js
// Solution 1: ESM wrapper that re-exports CJS (state lives in ONE place)
// dist/esm/index.js
import cjsModule from "../cjs/index.cjs";
export const { getInstance, config, utils } = cjsModule;

// Now both import and require() use the SAME underlying module state

// Solution 2: Stateless design (avoid the problem entirely)
// If your module has no mutable state, dual-loading is harmless
export function add(a, b) { return a + b; } // Pure function — safe!

// Solution 3: ESM-only (the future)
// Just don't support CJS. Set "type": "module" and only provide ESM.
// Users on CJS can use dynamic import():
// const { getInstance } = await import("your-lib");
```

#### Build Configuration for Dual Packages

```js
// tsup.config.ts — Build both formats from single source
import { defineConfig } from "tsup";

export default defineConfig({
  entry: ["src/index.ts"],
  format: ["esm", "cjs"],      // Output both formats
  dts: true,                    // Generate .d.ts
  splitting: false,
  sourcemap: true,
  clean: true,
  outDir: "dist",
  // CJS files get .cjs extension, ESM gets .js
  outExtension({ format }) {
    return { js: format === "cjs" ? ".cjs" : ".js" };
  },
});
```

### 8.2 — Bundler-Specific Tree-Shaking

Tree-shaking eliminates dead code (unused exports) from bundles. But it only works under specific conditions.

#### What Enables Tree-Shaking

```js
// ✅ TREE-SHAKEABLE: Static ESM imports
import { map } from "lodash-es";
// Bundler can prove 'filter', 'reduce', etc. are unused → removed

// ❌ NOT TREE-SHAKEABLE: CJS require
const _ = require("lodash");
// Bundler can't statically analyze what's used from '_'

// ❌ NOT TREE-SHAKEABLE: Namespace import with dynamic access
import * as utils from "./utils";
const fn = utils[dynamicKey]; // Can't determine at build time

// ✅ TREE-SHAKEABLE: Named imports
import { specificFn } from "./utils";

// ⚠️ PARTIALLY TREE-SHAKEABLE: Side effects
import "./polyfill"; // Side-effectful — bundler MUST include it
```

#### The `sideEffects` Field

```json
// package.json — Tell bundlers what's safe to eliminate
{
  "name": "my-lib",
  "sideEffects": false,
  // ↑ "None of my modules have side effects — safe to tree-shake everything"

  // Or be specific:
  "sideEffects": [
    "*.css",
    "./src/polyfills.js",
    "./src/register-globals.js"
  ]
  // ↑ Only these files have side effects; everything else is safe to remove
}
```

#### Bundler Comparison

```js
// Vite (uses Rollup for production builds)
// - Best tree-shaking (Rollup's is the most aggressive)
// - Respects sideEffects field
// - Can eliminate unused class methods (with @__PURE__ annotations)

// esbuild
// - Very fast but less aggressive tree-shaking
// - Doesn't eliminate unused class methods
// - Respects sideEffects field
// - Good enough for most cases

// Webpack 5
// - Good tree-shaking with optimization.usedExports
// - Supports sideEffects field
// - "Module concatenation" (scope hoisting) for better elimination
// - More configuration needed

// Rollup
// - Gold standard for library bundling
// - Most aggressive dead code elimination
// - Understands pure annotations: /*#__PURE__*/
```

#### Verifying Tree-Shaking Works

```bash
# Vite: analyze bundle
npx vite build && npx vite-bundle-visualizer

# Webpack: analyze bundle
npx webpack --profile --json > stats.json
npx webpack-bundle-analyzer stats.json

# esbuild: check metafile
esbuild src/index.ts --bundle --metafile=meta.json
# Then inspect meta.json for included modules

# Quick test: import one function, check bundle size
echo 'import { map } from "lodash-es"; console.log(map);' > test.js
esbuild test.js --bundle --minify | wc -c
# Should be ~2KB, not 70KB (full lodash)
```

#### Writing Tree-Shakeable Libraries

```js
// ❌ BAD: Single barrel export with class instances
// index.js
export class Analytics {
  constructor() {
    this.init(); // Side effect in constructor!
  }
  track(event) { /* ... */ }
  init() { /* sets up global listeners */ }
}
export const analytics = new Analytics(); // Instantiated on import!

// ✅ GOOD: Lazy initialization, pure exports
// index.js
export class Analytics {
  track(event) { /* ... */ }
  init() { /* ... */ }
}
export function createAnalytics(config) {
  const a = new Analytics();
  a.init(config);
  return a;
}
// Nothing happens until createAnalytics() is called
```

### 8.3 — Import Maps (Browser-Native Module Resolution)

Import maps let browsers resolve bare specifiers (like `"react"`) without a bundler.

```html
<!DOCTYPE html>
<html>
<head>
  <!-- Import map must come BEFORE any module scripts -->
  <script type="importmap">
  {
    "imports": {
      "react": "https://esm.sh/react@18.3.1",
      "react-dom/client": "https://esm.sh/react-dom@18.3.1/client",
      "lodash-es": "https://esm.sh/lodash-es@4.17.21",
      "lodash-es/": "https://esm.sh/lodash-es@4.17.21/",
      "@myorg/utils": "/src/utils/index.js",
      "#internal/": "/src/internal/"
    },
    "scopes": {
      "/vendor/": {
        "react": "https://esm.sh/react@17.0.2"
      }
    }
  }
  </script>
</head>
<body>
  <div id="root"></div>
  <script type="module">
    // These bare specifiers now resolve via the import map!
    import React from "react";
    import { createRoot } from "react-dom/client";
    import { debounce } from "lodash-es";
    import { formatDate } from "@myorg/utils";

    const root = createRoot(document.getElementById("root"));
    root.render(React.createElement("h1", null, "No bundler needed!"));
  </script>
</body>
</html>
```

#### Dynamic Import Maps (for Micro-Frontends)

```js
// Dynamically inject import maps before loading micro-frontends
async function loadMicroFrontend(name, version) {
  const mapScript = document.createElement("script");
  mapScript.type = "importmap";
  mapScript.textContent = JSON.stringify({
    imports: {
      [`@mfe/${name}`]: `/mfe/${name}/${version}/index.js`,
      [`@mfe/${name}/`]: `/mfe/${name}/${version}/`,
    },
  });
  document.head.appendChild(mapScript);

  // Now dynamically import the micro-frontend
  const module = await import(`@mfe/${name}`);
  return module;
}
```

### 8.4 — Module Federation Across Micro-Frontends

Module Federation (Webpack 5 / Vite plugin) allows separate builds to share modules at runtime.


### 8.5 — Node.js Conditional Exports Deep Dive

```json
{
  "name": "my-package",
  "exports": {
    ".": {
      "node": {
        "import": "./dist/node-esm.js",
        "require": "./dist/node-cjs.cjs"
      },
      "browser": "./dist/browser.js",
      "deno": "./dist/deno.js",
      "bun": "./dist/bun.js",
      "worker": "./dist/worker.js",
      "default": "./dist/default.js"
    },
    "./lite": {
      "import": "./dist/lite.js",
      "require": "./dist/lite.cjs"
    },
    "./package.json": "./package.json"
  }
}
```

#### Resolution Algorithm

```
Node.js resolves conditional exports in ORDER (first match wins):

1. Check "exports" field exists
2. Match the subpath (e.g., "." or "./lite")
3. Walk conditions top-to-bottom:
   - "node" → matches in Node.js
   - "import" → matches for ESM import
   - "require" → matches for CJS require()
   - "browser" → matches in bundlers targeting browsers
   - "default" → fallback (always matches)

Priority order for conditions:
  "node-addons" > "node" > "import"/"require" > "default"

Custom conditions (--conditions flag):
  node --conditions=development app.js
  → Matches "development" condition in exports
```

```json
    }

}
```

## 📎 9. Appendix: Extended Derivations & Special Cases

### 9.1 — ESM-Only Ecosystem Migration

The JavaScript ecosystem is migrating from CJS to ESM-only. Here's the current state and migration strategy.

#### Why ESM-Only?

```
Benefits of dropping CJS support:
1. Tree-shaking works properly (static analysis)
2. Top-level await available
3. No dual-package hazard
4. Simpler build configuration
5. Native browser compatibility
6. Better tooling support (TypeScript, bundlers)

The cost:
- Breaks require() consumers (they must use dynamic import())
- Some tools still assume CJS (Jest < 29, older webpack configs)
- Node.js < 12 can't use ESM at all
```

#### Notable ESM-Only Packages (Breaking Changes)

| Package | Version | Year | Impact |
|---------|---------|------|--------|
| `chalk` | 12.0 | 2022 | Logging/colors |
| `execa` | 6.0 | 2022 | Child processes |
| `got` | 12.0 | 2022 | HTTP client |
| `globby` | 13.0 | 2022 | File globbing |
| `p-*` (sindresorhus) | Various | 2022+ | Promise utilities |
| `node-fetch` | 3.0 | 2022 | Fetch polyfill |
| `ora` | 6.0 | 2022 | Spinners |
| `nanoid` | 4.0 | 2022 | ID generation |

#### Migration Guide: CJS → ESM

```json
// Step 1: Set type in package.json
{
  "type": "module"
}
// Now ALL .js files are ESM. CJS files must use .cjs extension.
```

```js
// Step 2: Update imports
// Before (CJS):
const path = require("path");
const { readFile } = require("fs/promises");
const myModule = require("./utils");

// After (ESM):
import path from "node:path";
import { readFile } from "node:fs/promises";
import myModule from "./utils.js"; // .js extension REQUIRED in ESM!

// Step 3: Replace __dirname and __filename
// Before (CJS):
const dir = __dirname;
const file = __filename;

// After (ESM):
import { fileURLToPath } from "node:url";
import { dirname } from "node:path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

// Or use import.meta.dirname (Node 21.2+):
const dir = import.meta.dirname;
const file = import.meta.filename;

// Step 4: Replace require.resolve
// Before:
const resolved = require.resolve("some-package");

// After:
const resolved = import.meta.resolve("some-package");

// Step 5: Replace module.exports
// Before:
module.exports = { foo, bar };
module.exports.default = main;

// After:
export { foo, bar };
export default main;
```

#### Consuming ESM-Only Packages from CJS

```js
// If you MUST stay on CJS but need an ESM-only package:

// Option 1: Dynamic import (returns a Promise)
async function main() {
  const { default: chalk } = await import("chalk");
  console.log(chalk.blue("Hello"));
}
main();

// Option 2: Use an older version that still supports CJS
// chalk@4 (CJS) vs chalk@5 (ESM-only)

// Option 3: Use a CJS alternative
// chalk → picocolors (CJS, smaller, faster)
// got → undici (CJS, built into Node)
// node-fetch → native fetch (Node 18+, no package needed)
```

### 9.2 — Node.js Module Resolution Algorithm

Understanding how Node.js finds modules is critical for debugging "module not found" errors.

#### ESM Resolution (import)

```
import "specifier"

1. Is it a URL? (file://, https://, data:)
   → Load directly

2. Is it a bare specifier? (no ./, ../, or /)
   a. Check if it starts with "node:" → built-in module
   b. Check package.json "imports" field (package-internal imports)
   c. Walk up directory tree looking for node_modules/specifier:
      - Check node_modules/specifier/package.json "exports"
      - If no "exports": check "main" field
      - If no "main": try index.js

3. Is it a relative specifier? (starts with ./ or ../)
   → Resolve relative to current file
   → File extension is REQUIRED in ESM!
   → No automatic .js/.json/.node extension resolution
   → No automatic index.js resolution for directories

4. Absolute specifier? (starts with /)
   → Resolve from filesystem root
```

#### CJS Resolution (require)

```
require("specifier")

1. Is it a core module? (fs, path, http...)
   → Return built-in

2. Is it a relative path? (./ or ../ or /)
   → Try: specifier, specifier.js, specifier.json, specifier.node
   → Try: specifier/index.js, specifier/index.json, specifier/index.node
   → Try: specifier/package.json "main" field

3. Is it a bare specifier?
   → Walk up from current directory:
     ./node_modules/specifier
     ../node_modules/specifier
     ../../node_modules/specifier
     ... (up to filesystem root)
   → For each: try same extensions as step 2
   → Check NODE_PATH environment variable
   → Check global folders (~/.node_modules, etc.)

4. Cache: require() caches by resolved filename
   → Same file required twice returns cached exports
   → This is why singletons work in CJS
```

#### Package.json "imports" Field (Subpath Imports)

```json
{
  "name": "my-app",
  "imports": {
    "#utils": "./src/utils/index.js",
    "#utils/*": "./src/utils/*.js",
    "#db": {
      "development": "./src/db/mock.js",
      "production": "./src/db/real.js",
      "default": "./src/db/real.js"
    },
    "#config": "./config/app-config.js"
  }
}
```

```js
// Use # prefix for internal imports (no more ../../../)
import { formatDate } from "#utils";
import { query } from "#db";
import config from "#config";

// Works from ANY file depth — no relative path hell!
// src/deeply/nested/component.js can still use #utils
```

### 9.3 — Bundler Internals: How Tree-Shaking Actually Works

```
STEP 1: Parse all modules into AST (Abstract Syntax Tree)

STEP 2: Build module graph
  entry.js → imports → moduleA.js → imports → moduleB.js
                     → imports → moduleC.js

STEP 3: Mark used exports (starting from entry points)
  - entry.js uses: moduleA.foo, moduleA.bar
  - moduleA.foo uses: moduleB.helper
  - moduleA.bar uses: nothing external
  - moduleC is imported but nothing from it is used

STEP 4: Eliminate unused exports
  - moduleB.otherHelper → REMOVED (not reachable from entry)
  - moduleC (entire module) → REMOVED (nothing used)
  - moduleA.baz → REMOVED (not imported by entry)

STEP 5: Scope hoisting (optional, Rollup/Webpack)
  - Merge modules into single scope where possible
  - Eliminates module wrapper overhead
  - Enables further dead code elimination within merged scope
```

#### Why Some Code Can't Be Tree-Shaken

```js
// Side effects prevent elimination:

// 1. Top-level function calls
console.log("I run on import!"); // Side effect — must keep

// 2. Property access with getters
const x = someObject.property; // Might trigger a getter with side effects

// 3. Class with static initialization
class Foo {
  static instance = new Foo(); // Constructor might have side effects
}

// 4. IIFE (Immediately Invoked Function Expression)
(function() {
  window.myGlobal = "value"; // Side effect
})();

// 5. Prototype modification
Array.prototype.customMethod = function() {}; // Side effect

// Tell bundlers "this is pure" (safe to remove):
const result = /*#__PURE__*/ createSomething();
// If 'result' is unused, bundler can remove the call
```

### 9.4 — Import Attributes (formerly Import Assertions)

```js
// Import JSON (Stage 3, shipping in Node 22+)
import config from "./config.json" with { type: "json" };
console.log(config.database.host);

// Import CSS (bundler-specific, not yet standardized for Node)
import styles from "./component.css" with { type: "css" };
document.adoptedStyleSheets.push(styles);

// Dynamic import with attributes
const data = await import("./data.json", { with: { type: "json" } });

// Why "with" instead of "assert"?
// Original proposal used "assert" — but assertions shouldn't affect behavior.
// "with { type: 'json' }" DOES affect behavior (tells the loader HOW to parse).
// Renamed to "with" (Import Attributes) to reflect this semantic difference.

// Security motivation:
// Without type assertion, a server could serve JavaScript where JSON was expected:
// import data from "https://evil.com/data" ← could execute arbitrary code!
// import data from "https://evil.com/data" with { type: "json" } ← MUST be JSON
```
