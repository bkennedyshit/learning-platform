# 12.1 — Setup, Runtime & Tooling

> *"Node.js is not a framework. It's a runtime. That distinction matters more than people think."* — **Ryan Dahl**, creator of Node.js and Deno (JSConf 2018)

JavaScript is unique among programming languages: it runs in **two fundamentally different environments** — the browser (where it was born in 1995) and server-side runtimes (Node.js since 2009, Deno since 2020, Bun since 2022). Understanding these runtimes isn't optional background — it determines what APIs are available, how modules resolve, and how your code executes.

This chapter gets your development environment production-ready and builds the mental model for *where* JavaScript actually runs.

---

## 🎯 Learning Objectives

1. **Install and verify** Node.js (LTS), Bun, and Deno on your system.
2. **Explain the architectural differences** between V8 (Node/Deno), JavaScriptCore (Bun), and browser JS engines.

4. **Configure VS Code** with essential JS/TS extensions for a professional workflow.
5. **Use the REPL** effectively for rapid prototyping in each runtime.
6. **Understand the relationship** between ECMAScript (the spec), JavaScript (the implementation), and TypeScript (the superset).

## 📚 1. Concepts & Definitions

### Definition 12.1.1 — JavaScript Engine vs Runtime

A **JavaScript engine** is the component that parses and executes JavaScript code. It implements the ECMAScript specification:

| Engine | Creator | Used In |
|--------|---------|---------|
| **V8** | Google | Chrome, Node.js, Deno, Edge |
| **JavaScriptCore (JSC)** | Apple | Safari, Bun |
| **SpiderMonkey** | Mozilla | Firefox |

A **runtime** wraps an engine with additional APIs (file system, networking, timers) that aren't part of the language spec:

```
┌─────────────────────────────────────────────┐
│  Runtime (Node.js / Bun / Deno / Browser)   │
├─────────────────────────────────────────────┤
│  Platform APIs (fs, http, fetch, DOM...)     │
├─────────────────────────────────────────────┤
│  Event Loop (libuv / kqueue / io_uring)     │
├─────────────────────────────────────────────┤
│  JavaScript Engine (V8 / JSC / SpiderMonkey)│
└─────────────────────────────────────────────┘
```

**Key insight:** `console.log`, `setTimeout`, and `fetch` are NOT part of JavaScript the language. They're provided by the runtime. This is why `document.querySelector` works in browsers but not in Node.js — different runtime, different APIs.

### Definition 12.1.2 — ECMAScript vs JavaScript vs TypeScript

```
ECMAScript (ES) ─── The specification (TC39 committee writes it)
     │
     ▼
JavaScript ──────── The implementation (what engines execute)
     │
     ▼
TypeScript ──────── A superset (adds types, compiles to JS)
```

- **ECMAScript** is a *standard* (like a blueprint). Current: ES2024 (ES15).
- **JavaScript** is the *implementation* of that standard in engines.
- **TypeScript** adds a compile-time type system on top. See [[13 - TypeScript]] for the deep dive.

When people say "ES6" they mean ECMAScript 2015 — the massive update that added `let`, `const`, arrow functions, classes, Promises, and modules. Everything since then has been incremental annual releases (ES2016, ES2017, ... ES2024).

### Definition 12.1.3 — Node.js

**Node.js** (2009, Ryan Dahl) is the original server-side JavaScript runtime:

- **Engine:** V8 (same as Chrome)
- **Event loop:** libuv (cross-platform async I/O)
- **Module system:** Originally CommonJS (`require`), now supports ESM (`import`)
- **Package manager:** npm (bundled), compatible with pnpm/yarn
- **Current LTS:** v22.x (as of 2026)

```bash
# Install via nvm (Node Version Manager) — recommended
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.0/install.sh | bash
nvm install --lts
nvm use --lts
node --version  # v22.x.x
```

On Windows, use **nvm-windows** or install directly from [nodejs.org](https://nodejs.org):

```powershell
# Windows: using winget
winget install OpenJS.NodeJS.LTS

# Or use fnm (Fast Node Manager) — cross-platform, Rust-based
winget install Schniz.fnm
fnm install --lts
fnm use lts-latest
```

### Definition 12.1.4 — Bun

**Bun** (2022, Jarred Sumner) is an all-in-one JavaScript runtime designed for speed:

- **Engine:** JavaScriptCore (Safari's engine — faster startup than V8)
- **Built-in:** Package manager, bundler, test runner, TypeScript transpiler
- **Compatibility:** Drop-in Node.js replacement for most code
- **Killer feature:** ~4x faster `install` than npm, native TypeScript execution

```powershell
# Windows install
powershell -c "irm bun.sh/install.ps1 | iex"

# Verify
bun --version

# Run TypeScript directly (no tsc needed!)
bun run server.ts

# Install packages (blazing fast)
bun install express
```

### Definition 12.1.5 — Deno

**Deno** (2020, Ryan Dahl — yes, the Node.js creator) is a "Node.js done right" runtime:

- **Engine:** V8
- **Security:** Permissions-based (no file/network access by default)
- **Built-in:** TypeScript compiler, formatter, linter, test runner
- **Modules:** URL-based imports (no `node_modules` by default), npm compat added in v1.28+
- **Standard library:** Audited, maintained by the Deno team

```powershell
# Windows install
irm https://deno.land/install.ps1 | iex

# Run with explicit permissions
deno run --allow-net --allow-read server.ts

# Or allow all (development only)
deno run -A server.ts
```

### Definition 12.1.6 — The Browser Runtime

The browser is JavaScript's *original* runtime. It provides:

- **DOM API** — `document.querySelector`, `element.addEventListener`
- **Web APIs** — `fetch`, `localStorage`, `WebSocket`, `IntersectionObserver`
- **DevTools** — Console, debugger, network inspector, performance profiler

The browser's JavaScript engine runs in a **sandboxed environment** — no file system access, no raw TCP sockets, no process spawning. This is a security feature, not a limitation.

## 📐 2. Package Managers — npm vs pnpm vs yarn

### The Problem They Solve

JavaScript has the largest package ecosystem in the world (~2.5 million packages on npmjs.com). Package managers handle:
1. **Dependency resolution** — figuring out compatible versions
2. **Installation** — downloading packages to `node_modules/`
3. **Lock files** — ensuring reproducible installs across machines
4. **Scripts** — running project commands (`build`, `test`, `dev`)

### Comparison Matrix

| Feature | npm | pnpm | yarn (v4) |
|---------|-----|------|-----------|
| **Speed** | Baseline | ~2x faster | ~1.5x faster |
| **Disk usage** | Duplicates deps | Content-addressable store (shared) | PnP (no node_modules) |
| **Lock file** | `package-lock.json` | `pnpm-lock.yaml` | `yarn.lock` |
| **Monorepo** | Workspaces | Workspaces (best) | Workspaces |
| **Bundled with** | Node.js | Standalone install | Standalone install |
| **Strictness** | Allows phantom deps | Strict (no hoisting) | Strict (PnP) |

**Recommendation for 2026:** Use **pnpm** for new projects. It's faster, uses less disk space, and prevents "phantom dependency" bugs where you accidentally import a package you didn't explicitly declare.

```bash
# Install pnpm
npm install -g pnpm

# Initialize a project
pnpm init

# Add dependencies
pnpm add express
pnpm add -D typescript vitest  # dev dependencies

# Run scripts
pnpm run dev
pnpm test
```

### The `package.json` Anatomy

```json
{
  "name": "my-project",
  "version": "1.0.0",
  "type": "module",          // ← ESM by default (important!)
  "main": "dist/index.js",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest"
  },
  "dependencies": {
    "hono": "^4.6.0"         // ^ = compatible updates (4.6.x, 4.7.x, not 5.x)
  },
  "devDependencies": {
    "typescript": "^5.6.0",
    "vitest": "^2.1.0"
  },
  "engines": {
    "node": ">=22.0.0"
  }
}
```

**Critical field:** `"type": "module"` tells Node.js to treat `.js` files as ESM (using `import`/`export`). Without it, Node defaults to CommonJS (`require`). Always set this for new projects.

## 🔬 4. REPL Workflows

A **REPL** (Read-Eval-Print Loop) is your scratchpad for testing ideas instantly.

### Node.js REPL

```bash
$ node
Welcome to Node.js v22.x.x.
> const x = [1, 2, 3].map(n => n ** 2)
> x
[ 1, 4, 9 ]
> .exit
```

Useful REPL commands:
- `.help` — show commands
- `.editor` — multi-line mode (Ctrl+D to execute)
- `.load file.js` — load and execute a file

### Bun REPL

```bash
$ bun repl
> Bun.version
"1.1.x"
> await fetch("https://api.github.com").then(r => r.json())
{ ... }  // top-level await works!
```

### Browser Console

Press `F12` → Console tab. The browser console has access to the DOM:

```javascript
// Only works in browser — not Node/Bun/Deno
document.querySelectorAll("h1").forEach(h => console.log(h.textContent));
```

## 🧪 5. Your First Modern JavaScript File

Create a file that demonstrates you're in the modern era:

```javascript
// hello-modern.mjs (or .js with "type": "module" in package.json)

// Top-level await (ES2022+)
const response = await fetch("https://api.github.com/zen");
const wisdom = await response.text();

// Template literals, const, arrow functions
const greet = (name) => `Hello ${name}, GitHub says: "${wisdom}"`;

// Destructuring, optional chaining, nullish coalescing
const config = { port: process.env.PORT ?? 3000 };
const { port } = config;

console.log(greet("Bill"));
console.log(`Server would run on port ${port}`);

// structuredClone (ES2022+) — deep copy without JSON hack
const original = { nested: { value: 42 }, date: new Date() };
const clone = structuredClone(original);
clone.nested.value = 99;
console.log(original.nested.value); // 42 — original untouched
```

Run it:
```bash
node hello-modern.mjs
# or
bun hello-modern.mjs
```

## 📊 6. Runtime Comparison — When to Use What

| Scenario | Best Runtime | Why |
|----------|-------------|-----|
| Production web server | **Node.js** | Largest ecosystem, battle-tested, most hosting support |
| Rapid prototyping | **Bun** | Fastest startup, runs TS directly, built-in tools |
| Security-sensitive scripts | **Deno** | Permission system, no implicit file/network access |
| Frontend development | **Browser** + Vite | Vite uses esbuild/Rollup, serves to browser |
| CLI tools | **Bun** or **Node** | Bun for speed, Node for compatibility |
| Edge functions (Cloudflare/Vercel) | **Workerd** / **Edge Runtime** | V8 isolates, limited APIs, ultra-fast cold start |
| Learning & experimentation | **Bun** | Zero config, TS support, fast feedback loop |

```javascript
// detect-runtime.mjs
function detectRuntime() {
```

### 8.1 — Runtime Benchmark: Bun vs Node vs Deno

Understanding performance differences between runtimes helps you choose the right tool. Here's a systematic benchmark methodology and real-world results.

#### Benchmark Setup

```bash
# Create benchmark directory
mkdir runtime-bench && cd runtime-bench

# Ensure all runtimes are installed
node --version   # v22.x LTS
bun --version    # v1.1.x
deno --version   # v2.x
```

#### Test 1: HTTP Server Throughput

```js
// bench-http.js — Works in all three runtimes
const port = 3000;

// Node.js native
import { createServer } from "node:http";

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "application/json" });
  res.end(JSON.stringify({ message: "Hello", runtime: "node" }));
});

server.listen(port, () => console.log(`Node listening on ${port}`));
```

```js
// bench-http-bun.js — Bun's native server
Bun.serve({
  port: 3000,
  fetch(req) {
    return new Response(JSON.stringify({ message: "Hello", runtime: "bun" }), {
      headers: { "Content-Type": "application/json" },
    });
  },
});
console.log("Bun listening on 3000");
```

```js
// bench-http-deno.js — Deno's native server
Deno.serve({ port: 3000 }, (_req) => {
  return new Response(JSON.stringify({ message: "Hello", runtime: "deno" }), {
    headers: { "Content-Type": "application/json" },
  });
});
```

```bash
# Benchmark with bombardier (or wrk/hey)
bombardier -c 100 -d 10s http://localhost:3000

# Typical results (2024 hardware, Apple M3 Pro):
# Bun:  ~180,000 req/s
# Deno: ~120,000 req/s
# Node: ~80,000 req/s (native http module)
# Node + Fastify: ~65,000 req/s (framework overhead)
```

#### Test 2: File I/O Performance

```js
// bench-file-io.js
import { writeFileSync, readFileSync, unlinkSync } from "node:fs";

const iterations = 10_000;
const data = "x".repeat(1024); // 1KB per write

console.time("write");
for (let i = 0; i < iterations; i++) {
  writeFileSync(`/tmp/bench-${i}.txt`, data);
}
console.timeEnd("write");

console.time("read");
for (let i = 0; i < iterations; i++) {
  readFileSync(`/tmp/bench-${i}.txt`, "utf8");
}
console.timeEnd("read");

// Cleanup
for (let i = 0; i < iterations; i++) {
  unlinkSync(`/tmp/bench-${i}.txt`);
}
```

```bash
# Results (10,000 x 1KB files):
# Bun:  write 320ms, read 180ms  (uses io_uring on Linux)
# Node: write 890ms, read 450ms  (libuv threadpool)
# Deno: write 750ms, read 400ms  (tokio async runtime)
```

#### Test 3: Startup Time (Cold Start)

```bash
# Measure startup + execution of a trivial script
hyperfine --warmup 3 \
  "node -e 'console.log(1)'" \
  "bun -e 'console.log(1)'" \
  "deno eval 'console.log(1)'"

# Typical results:
# Bun:  ~7ms   (JavaScriptCore, no JIT warmup needed for short scripts)
# Deno: ~25ms  (V8 + permission system init)
# Node: ~30ms  (V8 + module system init)
```

#### Test 4: TypeScript Execution (No Pre-Compilation)

```ts
// bench.ts — TypeScript file run directly
interface User {
  id: number;
  name: string;
  email: string;
}

function processUsers(users: User[]): Map<number, string> {
  return new Map(users.map(u => [u.id, u.name.toUpperCase()]));
}

const users: User[] = Array.from({ length: 100_000 }, (_, i) => ({
  id: i,
  name: `User ${i}`,
  email: `user${i}@example.com`,
}));

console.time("process");
const result = processUsers(users);
console.timeEnd("process");
console.log(`Processed ${result.size} users`);
```

```bash
# Run TypeScript directly (no tsc step):
hyperfine \
  "bun bench.ts" \
  "deno run bench.ts" \
  "npx tsx bench.ts"

# Results:
# Bun:  ~12ms  (strips types at parse time, no transpile step)
# Deno: ~35ms  (built-in TS support via swc)
# tsx:  ~120ms (esbuild transpile + Node startup)
```

### 8.2 — Version Manager Comparison: nvm vs Volta vs fnm

#### nvm (Node Version Manager)

```bash
# Install nvm (Unix/macOS)
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash

# Install and use Node versions
nvm install 22        # Install latest Node 22.x
nvm install 20        # Install latest Node 20.x
nvm use 22            # Switch to Node 22
nvm alias default 22  # Set default

# Per-project version pinning (.nvmrc)
echo "22.11.0" > .nvmrc
nvm use  # Reads .nvmrc automatically

# List installed versions
nvm ls
```

**Pros:** Universal standard, huge community, shell integration.
**Cons:** Slow shell startup (~200ms added to shell init), Unix-only (nvm-windows is a separate project), no auto-switching without hooks.

#### Volta (The Hassle-Free JavaScript Tool Manager)

```bash
# Install Volta
curl https://get.volta.sh | bash

# Install and pin Node
volta install node@22    # Install globally
volta pin node@22.11.0   # Pin to project (writes to package.json)
volta pin npm@10          # Pin npm version too

# package.json gets:
# "volta": { "node": "22.11.0", "npm": "10.9.0" }

# Automatic switching — no shell hooks needed!
cd my-project  # Volta reads package.json, switches instantly
node --version # 22.11.0 (even if global is different)
```

**Pros:** Zero-latency switching (shim-based, not shell hooks), pins versions in `package.json`, manages npm/yarn/pnpm versions too, cross-platform (Windows native).
**Cons:** Smaller community than nvm, doesn't manage Deno/Bun.

#### fnm (Fast Node Manager)

```bash
# Install fnm
# Windows (winget):
winget install Schniz.fnm
# macOS (brew):
brew install fnm

# Shell setup (add to profile)
eval "$(fnm env --use-on-cd)"

# Usage (same commands as nvm)
fnm install 22
fnm use 22
fnm default 22

# Auto-switching on cd (reads .nvmrc or .node-version)
echo "22.11.0" > .node-version
cd ../ && cd my-project  # Switches automatically
```

**Pros:** Written in Rust — 40x faster than nvm shell startup, cross-platform, reads `.nvmrc` files (drop-in nvm replacement), auto-switching built-in.
**Cons:** Newer project, slightly smaller ecosystem of plugins.

#### Comparison Table

| Feature | nvm | Volta | fnm |
|---------|-----|-------|-----|
| **Shell startup impact** | ~200ms | ~0ms (shim) | ~5ms |
| **Auto-switch on cd** | Plugin needed | Built-in | Built-in |
| **Windows support** | Separate project | Native | Native |
| **Config file** | `.nvmrc` | `package.json` | `.nvmrc` / `.node-version` |
| **Manages npm/yarn** | ❌ | ✅ | ❌ |
| **Written in** | Shell script | Rust | Rust |
| **Recommendation** | Legacy projects | Teams, CI/CD | Personal dev |

### 8.3 — pnpm Workspaces with Hoisting Strategies

#### Monorepo Setup

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
  - "tools/*"
```

```bash
# Directory structure
my-monorepo/
├── pnpm-workspace.yaml
├── package.json            # Root — shared scripts, devDeps
├── .npmrc                  # Hoisting configuration
├── apps/
│   ├── web/               # Next.js frontend
│   │   └── package.json
│   ├── api/               # Fastify backend
│   │   └── package.json
│   └── mobile/            # React Native
│       └── package.json
├── packages/
│   ├── shared-types/      # TypeScript types
│   │   └── package.json
│   ├── ui/                # Shared component library
│   │   └── package.json
│   └── utils/             # Shared utilities
│       └── package.json
```

```bash
# .npmrc — Controls how pnpm structures node_modules

# Each package only sees its own declared dependencies

# Strategy 2: Semi-strict (recommended for most monorepos)

hoist-pattern[]=*eslint*
hoist-pattern[]=*prettier*
hoist-pattern[]=*jest*
# Everything else stays isolated

# Strategy 3: Shamefully hoisted (npm-compatible flat structure)
# Use when migrating from npm/yarn or when tools don't support symlinks
shamefully-hoist=true
# node_modules structure: flat like npm (loses isolation benefits)

# Strategy 4: Public hoisting (expose specific packages)
public-hoist-pattern[]=@types/*
public-hoist-pattern[]=*eslint*
# These are hoisted to root AND accessible to all packages
```

## 📎 9. Appendix: Extended Derivations & Special Cases

### 9.1 — The V8 Isolate Model

V8 (used by Node.js, Deno, and Chrome) organizes execution around **Isolates** — independent instances of the V8 engine with their own heap, garbage collector, and compilation pipeline.

#### Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                         V8 ISOLATE                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────────┐  │
│  │   HEAP       │  │  COMPILER    │  │  GARBAGE COLLECTOR   │  │
│  │              │  │  PIPELINE    │  │                      │  │
│  │  Young Gen   │  │              │  │  Scavenger (young)   │  │
│  │  (Nursery)   │  │  Ignition    │  │  Mark-Compact (old)  │  │
│  │              │  │  (bytecode)  │  │  Incremental marking │  │
│  │  Old Gen     │  │      ↓       │  │  Concurrent sweeping │  │
│  │  (Tenured)   │  │  Sparkplug   │  │                      │  │
│  │              │  │  (baseline)  │  │  Orinoco (parallel)  │  │
│  │  Large Obj   │  │      ↓       │  │                      │  │
│  │  Space       │  │  Maglev      │  └──────────────────────┘  │
│  │              │  │  (mid-tier)  │                              │
│  │  Code Space  │  │      ↓       │  ┌──────────────────────┐  │
│  │              │  │  TurboFan    │  │  CONTEXTS            │  │
│  └──────────────┘  │  (optimized) │  │  (per-realm globals) │  │
│                     └──────────────┘  └──────────────────────┘  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### Key Concepts

**Isolate:** A single instance of V8. Each isolate has its own heap and cannot share objects with other isolates. In Node.js, each Worker thread gets its own isolate. In Cloudflare Workers, each request handler runs in a lightweight isolate for security isolation.

**Context:** Within an isolate, a Context provides a separate set of global objects. This is how Chrome isolates different iframes — same isolate (for performance), different contexts (for security). Node.js's `vm.createContext()` uses this.

**Compilation Pipeline (2024):**

```
Source Code
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  IGNITION (Interpreter)                                  │
│  - Generates bytecode immediately                        │
│  - Collects type feedback (Inline Caches)               │
│  - Low startup latency, moderate execution speed         │
└────────────────────────┬────────────────────────────────┘
                         │ "warm" functions (called multiple times)
                         ▼
┌─────────────────────────────────────────────────────────┐
│  SPARKPLUG (Baseline Compiler)                           │
│  - Non-optimizing, fast compilation                      │
│  - Translates bytecode → machine code (1:1)            │
│  - No type specialization, but faster than interpreter   │
│  - Added in V8 v9.1 (Node 16+)                         │
└────────────────────────┬────────────────────────────────┘
                         │ "hot" functions (called many times)
                         ▼
┌─────────────────────────────────────────────────────────┐
│  MAGLEV (Mid-Tier Compiler) — Added V8 v11.3            │
│  - Uses type feedback from Ignition's ICs               │
│  - Faster compilation than TurboFan                      │
│  - ~80% of TurboFan's peak performance                  │
│  - Fills the gap: fast to compile, reasonably fast code  │
└────────────────────────┬────────────────────────────────┘
                         │ "very hot" functions
                         ▼
┌─────────────────────────────────────────────────────────┐
│  TURBOFAN (Optimizing Compiler)                          │
│  - Full SSA-based optimization pipeline                  │
│  - Inlining, escape analysis, loop unrolling            │
│  - Type-specialized machine code                         │
│  - Can DEOPTIMIZE back to Ignition if assumptions break │
└─────────────────────────────────────────────────────────┘
```

#### Deoptimization (Bailout)

```js
// TurboFan optimizes based on observed types
function add(a, b) {
  return a + b;
}

// V8 sees: always called with numbers → optimizes for number addition
for (let i = 0; i < 100_000; i++) {
  add(i, i + 1); // TurboFan compiles this as integer addition
}

// Suddenly pass a string → type assumption violated!
add("hello", " world"); // DEOPTIMIZATION! Falls back to Ignition bytecode

// The function may be re-optimized later with polymorphic handling
// But it will never be as fast as the monomorphic (single-type) version
```

**Lesson:** Keep function argument types consistent for maximum V8 optimization. Monomorphic call sites (always same types) are 10-100x faster than megamorphic ones (many different types).

#### Hidden Classes (Maps/Shapes)

```js
// V8 creates "hidden classes" (called Maps internally) for object shapes
function Point(x, y) {
  this.x = x; // Hidden class transition: {} → {x}
  this.y = y; // Hidden class transition: {x} → {x, y}
}

// All Points created this way share the same hidden class
// V8 can use fast property access (known offset, no hash lookup)
const p1 = new Point(1, 2);
const p2 = new Point(3, 4); // Same hidden class as p1 — fast!

// DON'T do this — creates different hidden classes:
const p3 = new Point(5, 6);
p3.z = 7; // Hidden class transition: {x,y} → {x,y,z} — p3 is now different

// DON'T add properties in different orders:
function BadPoint(x, y) {
  if (x > 0) {
    this.x = x;
    this.y = y;
  } else {
    this.y = y; // Different order! Different hidden class!
    this.x = x;
  }
}
```

### 9.3 — JavaScriptCore (Bun's Engine) vs V8

Bun uses Apple's JavaScriptCore (JSC) instead of V8. Key architectural differences:

| Aspect | V8 (Node/Deno) | JavaScriptCore (Bun) |
|--------|----------------|---------------------|
| **Interpreter** | Ignition (bytecode) | LLInt (Low-Level Interpreter) |
| **Baseline JIT** | Sparkplug | Baseline JIT |
| **Mid-tier JIT** | Maglev | DFG (Data Flow Graph) |
| **Top-tier JIT** | TurboFan | FTL (Faster Than Light, via B3/Air) |
| **GC strategy** | Generational, incremental | Generational, concurrent |
| **Startup** | Slower (V8 snapshot helps) | Faster (simpler init) |
| **Peak perf** | Slightly higher (TurboFan is very mature) | Comparable |
| **Memory** | Higher baseline | Lower baseline |
| **Regex engine** | Irregexp (very fast) | YARR (fast) |

**Why Bun is faster for many workloads:**
- JSC's startup is faster (less initialization overhead)
- Bun's I/O layer uses system calls directly (io_uring on Linux, kqueue on macOS) instead of libuv's threadpool
- Bun's module resolver is written in Zig (compiled, not JS)
- Bun bundles its own allocator (mimalloc) optimized for its workload

### 9.4 — Deno's Permission System Deep Dive

```bash
# Deno denies all permissions by default
deno run server.ts
# Error: Requires net access to "0.0.0.0:3000"

# Grant specific permissions
deno run --allow-net=0.0.0.0:3000 server.ts

# --allow-read[=paths]    File system read
# --allow-write[=paths]   File system write
# --allow-net[=hosts]     Network access
# --allow-env[=vars]      Environment variables
# --allow-run[=programs]  Subprocess execution
# --allow-ffi            Foreign function interface
# --allow-sys            System info (hostname, OS, etc.)
# --allow-all / -A       Grant all (development only!)

# Programmatic permission requests (runtime)

}
```

#### Security Model Comparison

```
┌─────────────────────────────────────────────────────────────┐
│  Node.js Security Model                                      │
│  ─────────────────────                                       │
│  • Full system access by default                            │
│  • Trust-based: you trust your dependencies                 │
│  • Experimental --permission flag (Node 20+)                │
│  • Supply chain attacks are a real risk                     │
│  • Mitigation: npm audit, socket.dev, lockfile-lint         │
├─────────────────────────────────────────────────────────────┤
```

### 9.5 — Package Manager Internals: How pnpm's Content-Addressable Store Works

```
Traditional npm (flat node_modules):
project/
└── node_modules/
    ├── express/           ← Full copy
    ├── lodash/            ← Full copy (even if 5 packages need it)
    ├── debug/             ← Full copy
    └── ... (hundreds of flat folders)

pnpm (content-addressable + symlinks):
~/.pnpm-store/            ← Global content-addressable store
└── v3/
    └── files/
        ├── ab/cd1234...  ← Each FILE stored by content hash
        ├── ef/gh5678...  ← Shared across ALL projects on disk
        └── ...

project/
└── node_modules/
    ├── .pnpm/            ← Virtual store (hard links to global store)
    │   ├── express@4.18.2/
    │   │   └── node_modules/
    │   │       ├── express/  ← Hard links to store files
    │   │       ├── debug/    ← Hard links (not copies!)
    │   │       └── ...
    │   └── lodash@4.17.21/
    │       └── node_modules/
    │           └── lodash/   ← Hard links
    ├── express → .pnpm/express@4.18.2/node_modules/express  (symlink)
    └── lodash → .pnpm/lodash@4.17.21/node_modules/lodash    (symlink)
```

**Benefits:**
- **Disk space:** A file is stored ONCE globally, hard-linked everywhere. 10 projects using React share one copy on disk.
- **Install speed:** If a package is already in the store, it's just creating hard links (instant).
- **Correctness:** You can only `require()` packages you explicitly declared. No phantom dependencies.
- **Deterministic:** The `node_modules` structure is fully determined by `pnpm-lock.yaml`.

```bash
# See store stats
pnpm store status
pnpm store prune  # Remove unreferenced packages from store

# Store location
pnpm store path
# Default: ~/.local/share/pnpm/store/v3 (Linux/macOS)
# Default: %LOCALAPPDATA%/pnpm/store/v3 (Windows)
```
