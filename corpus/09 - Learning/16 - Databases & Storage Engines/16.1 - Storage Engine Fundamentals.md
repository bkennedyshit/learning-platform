# 16.1 — Storage Engine Fundamentals

> *"A database management system is, at heart, an elaborate page manager."* — paraphrased from Architecture of a Database System (Hellerstein, Stonebraker, Hamilton 2007)

> *"Understanding that a database is a page manager is the most clarifying single sentence in the entire field."*

Every query you've ever written — `SELECT`, `JOIN`, `UPDATE`, `DELETE` — ultimately compiles down to operations on fixed-size blocks called **pages** moving between disk and a region of RAM called the **buffer pool**. The storage engine is the component responsible for this movement and for ensuring the blocks on disk remain consistent and recoverable.

This chapter is the bedrock. Everything in chapters 16.2 through 16.8 is a specific answer to the question: *"How do we manage pages efficiently for this particular workload?"*

---

## 🎯 Learning Objectives

By the end of this chapter you will be able to:

1. Explain what a **heap file** is and how rows are stored in **pages** within it.
2. Describe the structure of a fixed-size database page (header, slot array, tuples, free space).
3. Explain the **buffer pool manager**: its role, data structures (frame table, page table, dirty bit), and eviction policies.
4. Articulate *why* the OS page cache and the database buffer pool are separate — and when bypassing the OS cache (`O_DIRECT`) makes sense.
5. Distinguish the **B-tree family** (update-in-place) from the **LSM-tree family** (append-only) and name the major databases in each.
6. Reason about the **WA/RA/SA triangle**: write-amplification, read-amplification, space-amplification.

## 📚 1. The Physical Reality: Files, Pages, and the I/O Unit

### 1.1 From Logical to Physical

When you say `SELECT * FROM users WHERE id = 42`, the database does not read the entire table. It reads one or more **pages** — contiguous fixed-size blocks of bytes — from disk into RAM. The page is the atomic I/O unit.

**Why fixed-size pages?**
- OS disk I/O is page-aligned: a read/write to any byte in a 4 KB region loads the entire 4 KB.
- Fixed sizes make free-space management simple: a page is either allocated to a relation or free.
- Buffer pool management (next section) is straightforward with uniform block sizes.

**Typical page sizes:**

| System | Default page size | Note |
|---|---|---|
| PostgreSQL | 8 KB (`BLCKSZ`) | Compile-time constant, 8 KB is most common |
| MySQL InnoDB | 16 KB | Configurable via `innodb_page_size` |
| SQLite | 4 KB | Configurable 512 B – 65536 B |
| Oracle | 8 KB default | Up to 32 KB with `db_block_size` |
| LevelDB / RocksDB SST | 4 KB block within SST | SST files are not fixed-size pages |

### 1.2 Heap Files

A **heap file** is the simplest possible table storage format: an unordered collection of pages, each containing a set of variable-length tuples. "Heap" in this context means *no inherent ordering* — not the data structure heap.

```
Heap file: table "users"
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│   Page 0    │  │   Page 1    │  │   Page 2    │
│ [hdr][t1]   │  │ [hdr][t4]   │  │ [hdr][t7]   │
│ [t2][t3]    │  │ [t5][t6]    │  │ [t8][FREE]  │
└─────────────┘  └─────────────┘  └─────────────┘
        ↑                                  ↑
  first INSERT                         new INSERT goes here (free space)
```

A **page directory** or **free space map** (e.g., PostgreSQL's `pg_freespace`) tracks which pages have free space for new inserts, avoiding a full scan to find a page with room.

### 1.3 Page Layout (PostgreSQL Heap Page Anatomy)

A PostgreSQL heap page is exactly 8192 bytes. Its layout from start to end:

```
Offset   Content
------   -------
0        PageHeaderData (24 bytes)
           pd_lsn:          LSN of last WAL record for this page
           pd_checksum:     page checksum (if enabled)
           pd_flags:        has free lines, has dead tuples, all visible, etc.
           pd_lower:        offset to start of free space
           pd_upper:        offset to end of free space
           pd_special:      offset to start of special space (index use)
           pd_pagesize_version
24       Line pointer array  (ItemId, 4 bytes each)
           ItemId.lp_off:   offset of tuple within page
           ItemId.lp_flags: normal, redirect (HOT update), unused, dead
           ItemId.lp_len:   length of tuple in bytes
pd_lower  ↓ free space starts here
pd_upper  ↑ free space ends here (tuples grow downward from pd_upper)
           HeapTupleHeaderData + user data for each tuple
           tuple header: t_xmin, t_xmax, t_ctid, t_infomask, t_hoff, ...
pd_special Special area (for index pages: high-key, left/right sibling links)
8192     End of page
```

**Key insight:** tuples are inserted at the *top* of the free space area (growing downward from `pd_upper`), while line pointers are appended at the bottom (growing upward from `pd_lower`). When `pd_lower >= pd_upper`, the page is full.

### Definition 16.1.1 — Tuple (Row Version)

A **tuple** in PostgreSQL is a physical row version. A single logical row can have multiple tuple versions if it has been updated (MVCC — see [[16.6 - Concurrency Control & MVCC|chapter 16.6]]). Each tuple has:

- `t_xmin`: transaction ID that inserted this tuple
- `t_xmax`: transaction ID that deleted/updated this tuple (0 if live)
- `t_ctid`: `(page_number, line_pointer_index)` — the physical address of this tuple version; for an updated tuple, `t_ctid` points to the newest version
- `t_infomask`: flags (has null, has var-length, XMIN_COMMITTED, XMAX_COMMITTED, etc.)

## 📚 2. The Buffer Pool Manager

### 2.1 Why Not Just Use the OS Page Cache?

The OS kernel already has a page cache that buffers disk reads. Why does a database need its own buffer pool?

**Because the OS doesn't know about database semantics:**

1. **Dirty page control**: The database must flush dirty pages to disk in a specific order (WAL-before-data — see [[16.5 - Write-Ahead Logging & Recovery|chapter 16.5]]). The OS may flush pages in any order.
2. **Eviction policy**: The database knows which pages are "hot" (e.g., B-tree root nodes), while the OS only sees generic file access patterns.
3. **Pre-fetching**: The database can predict which pages it needs next (e.g., a sequential scan), while the OS cannot.
4. **Double buffering waste**: Without `O_DIRECT`, pages are cached both in the database buffer pool and the OS page cache — two copies of the same data.

**The solution:** Databases typically open data files with `O_DIRECT` (bypass OS cache) and manage their own buffer pool exclusively. PostgreSQL is an exception — it *does* use the OS page cache in addition to its own shared buffer pool (`shared_buffers` setting). This is a known PostgreSQL design trade-off, and `pg_prewarm` exists to work around the cold-start problem.

### 2.2 Buffer Pool Data Structures

The buffer pool is a **fixed-size array of page-sized frames** in shared memory:

```
Buffer Pool (shared_buffers = 128 MB example)
┌──────────────────────────────────────────────────┐
│  Frame 0: [Page data 8192 bytes]                 │
│  Frame 1: [Page data 8192 bytes]                 │
│  Frame 2: [Page data 8192 bytes]                 │
│  ...                                             │
│  Frame N: [Page data 8192 bytes]  N=16383 frames │
└──────────────────────────────────────────────────┘

Page Table (hash map):  (file_id, page_no) → frame_index
Frame Table (metadata per frame):
  frame_id | page_id | dirty_bit | pin_count | usage_count | lsn
```

**Pin count**: a frame with `pin_count > 0` is **pinned** — currently in use by an active query. Pinned frames cannot be evicted. A frame is unpinned after the query releases it.

**Dirty bit**: set when a frame's content differs from disk. A dirty frame must be written back to disk (and WAL flushed first) before it can be evicted.

### 2.3 Eviction Policies

When all frames are pinned or in use and a new page must be loaded, the buffer pool must evict a frame. Classic options:

| Policy | Mechanism | Weakness |
|---|---|---|
| **LRU** (Least Recently Used) | Evict the frame that was least recently unpinned | Sequential scans "flush" the entire buffer pool (cache pollution) |
| **Clock** (LRU approximation) | Circular sweep; if usage bit set, clear it; if already clear, evict | O(1) amortised; doesn't suffer from clock hand being too aggressive |
| **LRU-K** | Evict the frame with the least-recent K-th access (typically K=2) | More precise than LRU; used in PostgreSQL's Clock-Sweep variant |
| **MRU** (Most Recently Used) | Evict the most recently used frame | Correct policy for sequential scans — avoid polluting the pool |

**PostgreSQL uses a Clock-Sweep** variant: each buffer has a `usage_count` (0–5). On each clock tick, if `usage_count > 0` it is decremented; if `usage_count == 0` the frame is a candidate for eviction. This approximates LRU-K without full LRU bookkeeping overhead.

### 2.4 The Buffer Pool in Practice

```sql
-- PostgreSQL: check buffer pool hit rate
SELECT
  sum(heap_blks_read)  AS disk_reads,
  sum(heap_blks_hit)   AS buffer_hits,
  round(100.0 * sum(heap_blks_hit) / nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0), 2) AS hit_rate_pct
FROM pg_statio_user_tables;

-- Typical target: > 99% hit rate for OLTP workloads
-- If consistently below 95%, increase shared_buffers
```

## 📚 3. The Two Great Engine Families

### 3.1 B-Tree Family: Update-In-Place

The B-tree family (specifically B+ trees — see [[16.2 - B-Trees & Page Management|chapter 16.2]]) stores data in sorted, fixed-size pages. Updates modify pages in-place in the buffer pool and eventually flush to disk.

**Characteristics:**
- **Read-optimised**: a point lookup requires only O(log n) I/Os to traverse the tree
- **Random writes are expensive**: inserting a row into a full page requires a **page split**, which is a random write to two new pages
- **Update-in-place requires locking**: modifying a page while another query reads it requires concurrency control

**Databases using B-tree storage:**
PostgreSQL, MySQL InnoDB, Oracle, SQL Server, SQLite, DB2

### 3.2 LSM-Tree Family: Append-Only

The Log-Structured Merge-tree (LSM-tree — see [[16.3 - LSM-Trees & Write-Optimized Storage|chapter 16.3]]) never modifies existing data. All writes are sequential appends — to a WAL, then to an in-memory structure, then flushed as immutable sorted files.

**Characteristics:**
- **Write-optimised**: every write is sequential regardless of where the row logically belongs
- **Reads require checking multiple files**: a point lookup may need to probe multiple sorted files (mitigated by Bloom filters)
- **Compaction reclaims space**: periodic background merges reconcile multiple versions of the same key

**Databases using LSM-tree storage:**
Cassandra, HBase, LevelDB, RocksDB, TiKV (underlying TiDB), Yugabyte DocDB, PebblesDB, BadgerDB

### 3.3 The WA/RA/SA Triangle

Every storage engine sits somewhere in a three-way trade-off:

| Property | What it means | Better for |
|---|---|---|
| **Write Amplification (WA)** | Bytes written to disk / bytes written by application | Lower WA = better for write-heavy workloads |
| **Read Amplification (RA)** | Disk reads to serve one logical read | Lower RA = better for read-heavy workloads |
| **Space Amplification (SA)** | Bytes on disk / bytes of live data | Lower SA = better for storage-constrained environments |

You cannot minimise all three simultaneously:

```
    Low WA (writes are cheap)
    ↑
    │  LSM-tree (tiered compaction)
    │       ●
    │              ● B-tree
    │                    ● B-tree with compression
    └───────────────────────────→ Low RA (reads are cheap)
    Space amplification is the third axis (out of plane)
```

**B-tree**: good RA (point lookup = O(log n)), moderate WA (page splits), moderate SA.
**LSM-tree (leveled)**: higher WA (10–30× write amplification from compaction), excellent RA (Bloom filter reduces probes), good SA.
**LSM-tree (tiered)**: low WA (≈4×), higher RA (must check more levels), moderate SA.

## 📚 4. I/O Access Patterns and Their Cost

### 4.1 Sequential vs Random I/O

The single most important physical constraint in storage engine design is the cost difference between sequential and random I/O:

| I/O type | HDD | NVMe SSD | Note |
|---|---|---|---|
| Sequential read (MB/s) | ~200 MB/s | ~3500 MB/s | Both fast; SSD 17× better |
| Random read (IOPS) | ~200 IOPS | ~500,000 IOPS | HDD catastrophic; NVMe excellent |
| Random read latency | ~10 ms | ~100–200 µs | 100× difference |

**HDDs** have a mechanical seek arm — random access to a new location costs a full rotation + seek (~10 ms). Sequential reads amortise this cost across many sectors in one pass.

**SSDs** (and NVMe) have no mechanical parts — random access costs are much lower. But write amplification in NAND flash (pages must be erased in blocks before rewriting) creates its own WA problem inside the SSD firmware.

**Design implication:** LSM-trees were originally optimised for HDDs (sequential writes replace random writes). On NVMe SSDs, the advantage is reduced but the append-only design still wins for throughput and simplifies crash recovery.

### 4.2 Prefetching and Sequential Scans

A full table scan (`SELECT * FROM users`) reads pages sequentially. Database buffer pools use **prefetching** (read-ahead) to load upcoming pages into the buffer pool before they're requested:

```
Read-ahead in PostgreSQL: controlled by effective_io_concurrency
  - default: 1 (single-threaded, pre-fetch 1 block at a time)
  - NVMe SSDs: set to 200 for parallel prefetch
```

## 📚 5. Worked Example: Tracing an INSERT

Let's trace what happens when you run:

```sql
INSERT INTO orders (customer_id, amount, created_at)
VALUES (9001, 49.99, NOW());
```

**Step 1: Parse and plan.** The query is parsed into a parse tree, analyzed (types checked, table found in `pg_catalog`), and a trivial insertion plan is generated.

**Step 2: Find a page with free space.** The buffer pool manager consults the Free Space Map (`pg_freespace`) to find a page with sufficient free space for the new tuple (roughly `sizeof(HeapTupleHeader) + sizeof(values)` bytes).

**Step 3: Pin the page.** The buffer pool pins the target page into a frame. If the page isn't in memory, it loads it from disk (a read I/O).

**Step 4: WAL first.** Before modifying the page, the storage engine writes a WAL record describing the insertion (see [[16.5 - Write-Ahead Logging & Recovery|chapter 16.5]]). The WAL record includes the new tuple data.

**Step 5: Modify the page in the buffer pool.** The new tuple is written to the free space area of the page. The line pointer array is updated with the new tuple's offset. `pd_lower` advances. The page's LSN is updated to the LSN of the WAL record just written. The frame's dirty bit is set.

**Step 6: Unpin the page.** The buffer pool frame is unpinned. The page will be flushed to disk later (by the background writer or checkpoint process).

**Step 7: Return success.** The transaction is not yet committed — the commit step flushes the WAL record to disk.

This sequence — *WAL write before page modification, buffer pool absorbs the write, background flush later* — is how every write to a B-tree database works.

## ⚠️ 7. Common Misconceptions

- **"The database reads one row at a time from disk."** No — it reads one page (8 KB) at a time. A single page can hold dozens to hundreds of rows. Efficient queries read as few pages as possible.
- **"Postgres has two copies of every page in memory."** Potentially true — PostgreSQL does *not* use `O_DIRECT` by default, so pages can be in both the OS page cache and `shared_buffers`. Setting `shared_buffers` too large wastes RAM that the OS could use for caching.
- **"An index makes every query faster."** Wrong. An index is another set of pages. For queries that touch a large fraction of a table (low selectivity), a sequential heap scan reads fewer pages than an index scan plus random heap fetches.
- **"SSD means we don't need to worry about I/O anymore."** SSDs reduce random I/O costs dramatically but don't eliminate them. Page-level thinking still matters at high throughput. A workload that generates 500,000 random reads/second can saturate a mid-range NVMe.
- **"The buffer pool is the OS page cache."** They are separate. The buffer pool is the database's own in-memory page cache. Many databases bypass the OS page cache entirely (`O_DIRECT`) to avoid double-caching and to maintain precise control over flushing order.
