# 16.5 — Write-Ahead Logging & Recovery

> *"The Write-Ahead Log is the single most important mechanism in database engineering. Without it, there is no durability. Without durability, there is no ACID. Everything else is commentary."*

> *"WAL is the promise that 'committed' means committed — even if the power goes out one millisecond later."*

The Write-Ahead Log (WAL) is the mechanism that makes Durability possible. Without WAL, a database is a glorified in-memory data structure that loses data on crash. With WAL, a database can recover to a consistent, durable state after any failure — crash, power cut, OS panic — and every committed transaction will be present in that recovered state.

This chapter covers the WAL format, the critical write-ahead rule, group commit for throughput, and the **ARIES algorithm** — the definitive recovery algorithm used (in some form) by every major relational database.

## 📚 1. The Write-Ahead Log: Structure and Purpose

### 1.1 The Core Problem

The buffer pool holds dirty pages in memory. Flushing dirty pages to disk on every write would provide durability but is prohibitively slow (100s of random I/Os per second limit). We need a way to make writes durable without writing every modified page to disk immediately.

**Solution: Write-Ahead Log (WAL)**

Instead of flushing dirty pages immediately, we write a *description* of every change to a sequential log file before applying the change to the actual data pages. The log file is sequential (fast), and the data pages are flushed lazily in the background.

### 1.2 The Write-Ahead Rule (Two Sub-Rules)

**Rule 1 (Steal/No-Force):** A modified page can be written to disk at any time — but the log record describing that modification MUST be on disk first.
*(This ensures we can redo the modification after crash.)*

**Rule 2 (Force-Log-at-Commit):** Before returning a COMMIT acknowledgement to the client, ALL log records for that transaction MUST be flushed to disk.
*(This ensures committed transactions are durable.)*

Together, these two rules provide durability without requiring us to flush data pages on every commit. The sequence is:

```
1. Write WAL record (description of change)  ← to sequential log buffer
2. Modify page in buffer pool                ← in RAM only
3. On COMMIT: flush WAL log buffer to disk   ← fsync() on log file
4. Return "COMMIT OK" to client
5. Background: flush dirty data pages to disk ← whenever convenient
```

### 1.3 WAL Record Structure

Each WAL record contains enough information to **redo** the change (for recovery after crash) and **undo** the change (for rollback if the transaction aborts):

```
WAL Record (PostgreSQL XLogRecord):
┌─────────────────────────────────────────────────────────────────┐
│ xl_tot_len: total record length                                 │
│ xl_xid:     transaction ID of the writing transaction          │
│ xl_prev:    LSN (log sequence number) of previous record       │
│ xl_info:    record type (HEAP_INSERT, HEAP_UPDATE, HEAP_DELETE, │
│             HEAP_HOT_UPDATE, XACT_COMMIT, XACT_ABORT, etc.)    │
│ xl_rmid:    resource manager ID (heap, btree, xact, ...)        │
│ data:       redo information (new values, new page state)       │
│             + undo information (old values, old page state)     │
│ (optional) full page image (FPI) if first modification         │
│            after checkpoint                                     │
└─────────────────────────────────────────────────────────────────┘
```

**Log Sequence Number (LSN)**: A monotonically increasing 8-byte integer that uniquely identifies a position in the WAL. Every page in the buffer pool has a `pd_lsn` field recording the LSN of the most recent WAL record that modified it. Recovery uses LSN comparisons to determine whether a page needs to be redone.

### 1.4 WAL in PostgreSQL

```bash
# PostgreSQL WAL files live in the pg_wal directory
ls -la $PGDATA/pg_wal/
# 000000010000000000000001   ← WAL segment file (16 MB default)
# 000000010000000000000002
# ...
# Each file is named: timeline + log segment number

# WAL file size controlled by:
# wal_segment_size = 16MB (default, set at initdb time)

# Current WAL position:
SELECT pg_current_wal_lsn();        -- current write position
SELECT pg_current_wal_insert_lsn(); -- where next record will go
```

## 📚 2. Group Commit: Multiplying Throughput

### 2.1 The Throughput Problem

If every commit requires one `fsync()` call, throughput is bounded by the number of fsyncs per second the storage can handle:

```
HDD:   ~150 fsyncs/sec → 150 TPS ceiling
SSD:   ~5,000 fsyncs/sec → 5,000 TPS ceiling
NVMe:  ~50,000+ fsyncs/sec → 50,000+ TPS ceiling
```

For most applications, HDD means 150 transactions per second — catastrophically slow. Even NVMe isn't enough for high-throughput OLTP.

### 2.2 Group Commit Solution

**Group commit** batches multiple transactions' WAL records into a single `fsync()`:

```
Thread 1 commits → WAL records go to WAL buffer
Thread 2 commits → WAL records go to WAL buffer
Thread 3 commits → WAL records go to WAL buffer
...
[100 ms later OR WAL buffer full]:
  → Single fsync() writes ALL 100 transactions' WAL records
  → All 100 clients get their COMMIT ACK simultaneously

Throughput: 100 commits / 1 fsync = 100× improvement over naive 1-fsync-per-commit
```

PostgreSQL implements group commit via the WAL writer background process:
- `wal_writer_delay` (default 200ms): how long the WAL writer sleeps between flushes
- `commit_delay` (default 0µs): how long a committing session waits to join a group commit
- `commit_siblings` (default 5): minimum active transactions before applying `commit_delay`

### 2.3 Sync Commit Options

PostgreSQL `synchronous_commit` offers a spectrum:

| Setting | Durability | Latency |
|---|---|---|
| `on` (default) | Full — wait for WAL fsync | Highest (fsync latency) |
| `remote_write` | WAL written to replica disk (not fsynced) | Lower |
| `remote_apply` | Replica has applied WAL | Variable |
| `local` | Local WAL fsynced, replica async | Low |
| `off` | No wait for WAL flush | Lowest — risk of losing last 200ms of commits |

`synchronous_commit = off` is appropriate for non-critical, high-throughput inserts where you can tolerate losing the last WAL writer cycle of transactions on crash. Useful for logging tables, analytics ingestion.

## 📚 3. Checkpoints: Bounding Recovery Time

### 3.1 The Problem Without Checkpoints

After a crash, to recover, we must replay WAL from the beginning of time. For a database that's been running for months, that's an unacceptably long recovery time.

**Checkpoint**: a point in the WAL at which all dirty pages known at that time have been flushed to disk. Recovery only needs to start from the last checkpoint.

### 3.2 What a Checkpoint Does

```
PostgreSQL CHECKPOINT process:
1. Note the current WAL LSN as the checkpoint LSN (redo_lsn)
2. Write a CHECKPOINT WAL record containing:
   - Dirty Page Table (DPT): which pages are dirty + their recovery LSN
   - Active Transaction Table (ATT): which transactions are in progress
   - Previous checkpoint LSN
3. Flush ALL dirty pages in the buffer pool to disk
4. Write a checkpoint location record to pg_control file
5. WAL before redo_lsn can be archived/removed (after pg_basebackup etc.)
```

**Cost**: A checkpoint is expensive — it forces all dirty pages to disk. PostgreSQL spreads checkpoint I/O over `checkpoint_completion_target` × `checkpoint_timeout`:
- `checkpoint_timeout = 5min` (default): max time between automatic checkpoints
- `checkpoint_completion_target = 0.9` (recommended): spread checkpoint I/O over 90% of the interval

### 3.3 The Checkpoint Record

```
CHECKPOINT WAL record (simplified):
{
  redo_lsn:          LSN where recovery should start (redo from here)
  TimelineID:        which timeline (for PITR and standbys)
  nextXID:           next transaction ID to allocate
  nextOID:           next OID to allocate
  DirtyPageTable:    {(rel_id, page_no) → recovery_LSN} for all dirty pages
  ActiveTransactions: {xid, type, last_lsn} for active transactions
}
```

## 📚 4. ARIES Recovery Algorithm

### 4.1 Background

**ARIES** (Algorithm for Recovery and Isolation Exploiting Semantics) was published by Mohan et al. at IBM Research in 1992. It is the foundation of recovery algorithms in PostgreSQL, DB2, SQL Server, and Oracle (with variations). Its three key ideas:

1. **Write-ahead logging** (covered above)
2. **Repeating history during redo** (redo ALL operations, including aborted transactions)
3. **Logging undos** (compensation log records make undo idempotent)

### 4.2 Phase 1: Analysis

**Goal**: Determine the dirty page table and active transaction table at the crash point.

```
Start at last CHECKPOINT in pg_control.
Scan forward through WAL from checkpoint_lsn to crash point.
For each record:
  - UPDATE ATT: add new BEGIN records, remove COMMIT/ABORT records
  - UPDATE DPT: for each page_update record:
      if page not already in DPT: add it with this record's LSN
  - Track latest LSN for each active transaction

Result:
  - DPT: which pages were dirty at crash → need redo from minimum(DPT.rec_LSN)
  - ATT: which transactions were active (uncommitted) at crash → need undo
```

### 4.3 Phase 2: Redo

**Goal**: Restore the database buffer pool to the exact state it was in at the moment of crash — including pages modified by transactions that never committed.

```
Start at min(DPT.recLSN) — the earliest point where any dirty page was modified.
Replay EVERY log record forward (even records for aborted transactions).

For each log record L:
  if affected page is in DPT:
    read the page from disk
    if page.LSN < L.LSN:   ← page doesn't already have this change
      apply L's redo action
      set page.LSN = L.LSN
      mark page dirty in buffer pool
  else: skip (page is already up to date)

After redo, the buffer pool state = crash-time state.
```

**Why replay even aborted transactions?** Because those pages might have been flushed to disk as dirty pages before the crash. We need to replay them to get the exact crash-time state, and then undo them in Phase 3.

### 4.4 Phase 3: Undo

**Goal**: Roll back all uncommitted transactions (the ATT survivors from Phase 1).

```
Process ATT transactions in reverse LSN order (newest first).
For each active transaction T in ATT:
  Walk T's log records backward (using xl_prev pointer chain).
  For each record R in T:
    Apply R's undo action to the page.
    Write a COMPENSATION LOG RECORD (CLR) for this undo operation.
    CLR.undoNextLSN = the LSN of the next record to undo in T
    (if ARIES must redo the CLR during a crash-during-recovery, it skips ahead)
```

**Compensation Log Records (CLRs)**: The key to making undo idempotent. A CLR says "I already undid operation at LSN X; don't undo it again". If recovery crashes DURING undo and restarts, the redo phase will redo the CLRs (which describe the undo actions), and the undo phase will see the CLRs and skip already-undone operations. This prevents double-undos.

```
Example CLR: "Undo of LSN 101 (UPDATE row5): reset row5 to old value"
CLR.undoNextLSN = 100 (the previous operation in the same transaction to undo next)
```

### 4.5 Worked Example: Recovery Scenario

```
WAL at crash point:
LSN 100: BEGIN T1
LSN 101: T1 UPDATE row5 (new_val=50, old_val=30)
LSN 102: BEGIN T2
LSN 103: CHECKPOINT (DPT: {page_X: 101}, ATT: {T1: 101, T2: 102})
LSN 104: T2 UPDATE row3 (new_val=20, old_val=15)
LSN 105: T1 COMMIT
--- CRASH --- (T2 still active, uncommitted)

Phase 1 — Analysis:
  Start at LSN 103 (checkpoint).
  Read LSN 104: T2 UPDATE row3 → add row3's page to DPT at LSN 104.
  Read LSN 105: T1 COMMIT → remove T1 from ATT.
  End of WAL.
  Result:
    DPT: {page_X: 101, page_Y: 104}   (page_X from checkpoint, page_Y from analysis)
    ATT: {T2: last_lsn=104}           (T1 committed; T2 never committed)

Phase 2 — Redo:
  Start at min(DPT.recLSN) = 101.
  LSN 101: T1 UPDATE row5 → apply (page_X.LSN < 101? check, if so apply)
  LSN 104: T2 UPDATE row3 → apply (page_Y.LSN < 104? check, if so apply)
  LSN 105: T1 COMMIT → no data change, just record
  Buffer pool now = crash-time state.

Phase 3 — Undo:
  ATT has {T2}: undo T2.
  Find T2's last LSN: 104. Undo LSN 104 (T2 UPDATE row3):
    Set row3 back to old_val=15.
    Write CLR: "Undid LSN 104, undoNextLSN=NIL (T2 is done)"
  T2 is fully rolled back.
  Database is consistent: T1's commit (row5=50) is preserved, T2's update is rolled back.
```

## 📚 5. PostgreSQL WAL Configuration

```sql
-- View current WAL level and settings
SHOW wal_level;             -- minimal, replica, logical
SHOW synchronous_commit;    -- on, remote_write, remote_apply, local, off
SHOW checkpoint_timeout;    -- default: 5min
SHOW max_wal_size;          -- triggers checkpoint when WAL hits this size
SHOW wal_compression;       -- compress WAL records (reduces I/O, costs CPU)

-- Monitor WAL activity
SELECT pg_current_wal_lsn();
SELECT pg_walfile_name(pg_current_wal_lsn());  -- current WAL file name

-- Check checkpoints
SELECT checkpoints_timed, checkpoints_req,
       checkpoint_write_time, checkpoint_sync_time,
       buffers_checkpoint, buffers_clean, buffers_backend
FROM pg_stat_bgwriter;

-- pg_stat_bgwriter.buffers_backend: pages flushed by backends directly
-- (high value = checkpoints too far apart; increase max_wal_size)

-- Monitor replication lag
SELECT client_addr, write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
```

## ⚠️ 7. Common Misconceptions

- **"WAL is just a backup."** WAL is a recovery mechanism — specifically, a redo/undo log. It enables recovery after crash. It can be used for point-in-time recovery (PITR) and replication, but its primary purpose is crash recovery.
- **"Turning off synchronous_commit makes the database unsafe."** `synchronous_commit = off` only risks losing the last ~200ms of commits on crash. If you can tolerate this (logging, analytics), it's a legitimate trade-off. All COMMITTED transactions before that window are still safe.
- **"ARIES redo replays only committed transactions."** ARIES redoes EVERYTHING, including uncommitted transactions. This repeats history exactly. The undo phase then rolls back the uncommitted ones.
- **"CLRs are redundant bookkeeping."** CLRs are critical for crash-during-recovery correctness. Without CLRs, a crash while undoing would leave undo actions half-applied. CLRs make ARIES crash-safe for arbitrary nesting of failures.
- **"A checkpoint makes the database safe."** A checkpoint reduces recovery time. It does NOT replace WAL. After a checkpoint, new WAL records are still needed for durability. The checkpoint merely allows old WAL to be pruned.
