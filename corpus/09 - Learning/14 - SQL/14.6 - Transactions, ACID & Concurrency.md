# 14.6 — Transactions, ACID & Concurrency

> *"A transaction is a unit of work that is either performed in its entirety or not performed at all."* — Jim Gray, *Transaction Processing: Concepts and Techniques* (1992)

Every production database serves multiple users simultaneously. Without transactions, concurrent access leads to corrupted data, lost updates, and phantom reads. This chapter teaches you how databases maintain correctness under concurrency — the ACID guarantees, isolation levels, MVCC (Multi-Version Concurrency Control), and how to reason about concurrent access patterns in your applications.

---

## 🎯 Learning Objectives

By the end of this chapter you will be able to:

1. Explain each ACID property and why it matters for application correctness.
2. Identify and prevent concurrency anomalies (dirty reads, non-repeatable reads, phantoms, write skew).
3. Choose the appropriate isolation level for different workloads.
4. Understand MVCC and how PostgreSQL implements snapshot isolation.
5. Diagnose and prevent deadlocks.
6. Use explicit locking (SELECT FOR UPDATE) when needed.

## 📚 1. ACID Properties

### Atomicity

A transaction is **all-or-nothing**. If any statement fails, all changes are rolled back.

```sql
BEGIN;
    UPDATE accounts SET balance = balance - 500 WHERE account_id = 1;
    UPDATE accounts SET balance = balance + 500 WHERE account_id = 2;
    -- If the second UPDATE fails (e.g., constraint violation),
    -- the first UPDATE is also rolled back.
COMMIT;
```

**Implementation:** Write-Ahead Logging (WAL). Changes are written to a log before being applied. On crash, the log is replayed to undo incomplete transactions.

### Consistency

A transaction moves the database from one **valid state** to another. All constraints (PK, FK, CHECK, UNIQUE) are satisfied after commit.

```sql
-- This transaction will fail at COMMIT if it violates constraints:
BEGIN;
    INSERT INTO orders (order_id, customer_id, amount)
    VALUES (1001, 999, -50.00);  -- CHECK (amount > 0) violated!
ROLLBACK;  -- or the DB auto-rolls-back on constraint violation
```

### Isolation

Concurrent transactions don't interfere with each other. Each transaction sees a consistent snapshot of the database as if it were running alone.

### Durability

Once committed, data survives crashes. Guaranteed by WAL + fsync.

```sql
BEGIN;
    INSERT INTO critical_data VALUES (...);
COMMIT;  -- After this returns, the data is on disk. Power failure won't lose it.
```

## 📚 2. Concurrency Anomalies

### 2.1 Dirty Read

Reading uncommitted data from another transaction.

```
T1: UPDATE accounts SET balance = 0 WHERE id = 1;  (not yet committed)
T2: SELECT balance FROM accounts WHERE id = 1;     → reads 0 (dirty!)
T1: ROLLBACK;                                       → balance is actually still 1000
T2: now has incorrect data
```

**Prevented by:** READ COMMITTED and above.

### 2.2 Non-Repeatable Read

Reading the same row twice yields different values because another transaction committed between reads.

```
T1: SELECT balance FROM accounts WHERE id = 1;  → 1000
T2: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT;
T1: SELECT balance FROM accounts WHERE id = 1;  → 500 (different!)
```

**Prevented by:** REPEATABLE READ and above.

### 2.3 Phantom Read

A query returns different rows on re-execution because another transaction inserted/deleted matching rows.

```
T1: SELECT COUNT(*) FROM orders WHERE status = 'pending';  → 10
T2: INSERT INTO orders (..., 'pending'); COMMIT;
T1: SELECT COUNT(*) FROM orders WHERE status = 'pending';  → 11 (phantom!)
```

**Prevented by:** SERIALIZABLE.

### 2.4 Write Skew

Two transactions read overlapping data, make decisions based on it, then write — creating an inconsistent state that neither would have allowed alone.

```
-- Rule: at least one doctor must be on call
-- Both doctors are currently on call.

T1: SELECT COUNT(*) FROM on_call WHERE hospital = 'A';  → 2
T1: (decides it's safe to go off-call)
T2: SELECT COUNT(*) FROM on_call WHERE hospital = 'A';  → 2
T2: (decides it's safe to go off-call)
T1: DELETE FROM on_call WHERE doctor = 'Alice'; COMMIT;
T2: DELETE FROM on_call WHERE doctor = 'Bob'; COMMIT;
-- Result: 0 doctors on call! Constraint violated.
```

**Prevented by:** SERIALIZABLE (or explicit locking).

## 📚 3. Isolation Levels

### SQL Standard Isolation Levels

| Level | Dirty Read | Non-Repeatable Read | Phantom | Write Skew |
|-------|-----------|-------------------|---------|-----------|
| READ UNCOMMITTED | Possible | Possible | Possible | Possible |
| READ COMMITTED | Prevented | Possible | Possible | Possible |
| REPEATABLE READ | Prevented | Prevented | Possible* | Possible* |
| SERIALIZABLE | Prevented | Prevented | Prevented | Prevented |

*PostgreSQL's REPEATABLE READ actually prevents phantoms (it uses snapshot isolation), but allows write skew.

### 3.1 READ COMMITTED (PostgreSQL Default)

Each statement sees a snapshot as of the statement's start. Different statements within the same transaction may see different committed data.

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

BEGIN;
    -- Statement 1 sees data as of time T1
    SELECT * FROM orders WHERE status = 'pending';

    -- Another transaction commits changes here...

    -- Statement 2 sees data as of time T2 (includes new commits!)
    SELECT * FROM orders WHERE status = 'pending';  -- may differ!
COMMIT;
```

**Use when:** Most OLTP workloads. Simple, good performance, prevents dirty reads.

### 3.2 REPEATABLE READ

The transaction sees a snapshot as of the transaction's start. All statements see the same data regardless of concurrent commits.

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

BEGIN;
    SELECT balance FROM accounts WHERE id = 1;  -- sees 1000
    -- Another transaction changes balance to 500 and commits
    SELECT balance FROM accounts WHERE id = 1;  -- still sees 1000!

    -- But if we try to UPDATE a row modified by another transaction:
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    -- ERROR: could not serialize access due to concurrent update
COMMIT;
```

**Use when:** Reports that need consistent data across multiple queries. Long-running analytics.

### 3.3 SERIALIZABLE

Guarantees that the result is equivalent to some serial (one-at-a-time) execution of the transactions. Detects and prevents all anomalies including write skew.

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

BEGIN;
    -- If this transaction's reads conflict with concurrent writes,
    -- PostgreSQL will abort one transaction with a serialization failure.
    -- Your application MUST retry on serialization failure.
COMMIT;
```

**Use when:** Financial transactions, inventory management, any scenario where write skew would violate business rules.

**Cost:** Higher abort rate (must retry failed transactions). Slightly more overhead for dependency tracking.

## 📚 4. MVCC (Multi-Version Concurrency Control)

### How PostgreSQL Implements MVCC

Instead of locking rows for readers, PostgreSQL keeps **multiple versions** of each row. Each transaction sees the version that was current at its snapshot time.

**Row versioning:**
- Each row has `xmin` (transaction ID that created it) and `xmax` (transaction ID that deleted/updated it, or 0 if live).
- An UPDATE creates a new row version (new `xmin`) and marks the old version dead (`xmax`).
- A transaction sees a row if: `xmin` is committed and before the snapshot, AND (`xmax` is 0 OR `xmax` is not yet committed at snapshot time).

**Key benefit:** Readers never block writers. Writers never block readers. Only writer-writer conflicts on the same row cause blocking.

### VACUUM: Cleaning Dead Rows

Dead row versions accumulate. VACUUM reclaims space:

```sql
-- Manual vacuum:
VACUUM VERBOSE employees;

-- Aggressive vacuum (reclaims space to OS):
VACUUM FULL employees;  -- WARNING: locks table exclusively!

-- Check dead tuple count:
SELECT relname, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC;
```

Autovacuum runs automatically but may need tuning for high-write tables.

## 📚 5. Explicit Locking

### 5.1 Row-Level Locks: SELECT FOR UPDATE

```sql
-- Lock the row to prevent concurrent modification:
BEGIN;
    SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
    -- Row is now locked. Other transactions trying to UPDATE or FOR UPDATE
    -- on this row will WAIT until we commit/rollback.

    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

**Lock modes:**
| Mode | Blocks | Use Case |
|------|--------|----------|
| `FOR UPDATE` | Other FOR UPDATE, UPDATE, DELETE | Modifying the row |
| `FOR NO KEY UPDATE` | Other FOR UPDATE, UPDATE, DELETE | Modifying non-key columns |
| `FOR SHARE` | Other FOR UPDATE, UPDATE, DELETE | Read-only but prevent changes |
| `FOR KEY SHARE` | Other FOR UPDATE, DELETE | Prevent key changes (FK checks) |

### 5.2 Advisory Locks

Application-level locks (not tied to rows):

```sql
-- Acquire an advisory lock (blocks until available):
SELECT pg_advisory_lock(12345);

-- Do exclusive work...

-- Release:
SELECT pg_advisory_unlock(12345);

-- Try without blocking:
SELECT pg_try_advisory_lock(12345);  -- returns true/false
```

**Use case:** Preventing duplicate cron job execution, serializing access to external resources.

### 5.3 Table-Level Locks

```sql
-- Prevent all writes to a table during a migration:
LOCK TABLE employees IN EXCLUSIVE MODE;

-- Prevent all access (including reads):
LOCK TABLE employees IN ACCESS EXCLUSIVE MODE;
```

## 📚 6. Deadlocks

### What Is a Deadlock?

Two transactions each hold a lock the other needs:

```
T1: UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- locks row 1
T2: UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- locks row 2
T1: UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- WAITS for T2
T2: UPDATE accounts SET balance = balance + 50 WHERE id = 1;   -- WAITS for T1
-- DEADLOCK! Neither can proceed.
```

### Detection and Resolution

PostgreSQL detects deadlocks automatically (default check interval: 1 second) and aborts one transaction with:
```
ERROR: deadlock detected
DETAIL: Process 1234 waits for ShareLock on transaction 5678; blocked by process 9012.
```

### Prevention Strategies

1. **Consistent lock ordering:** Always lock resources in the same order (e.g., by ID ascending).

```sql
-- GOOD: always lock lower ID first
BEGIN;
    SELECT * FROM accounts WHERE id = LEAST(1, 2) FOR UPDATE;
    SELECT * FROM accounts WHERE id = GREATEST(1, 2) FOR UPDATE;
    -- Now safe to update both
COMMIT;
```

2. **Short transactions:** Minimize time between acquiring locks and committing.

3. **Lock timeouts:**
```sql
SET lock_timeout = '5s';  -- abort if can't acquire lock within 5 seconds
```

## 📚 7. Transaction Patterns for Applications

### 14.1 Retry Loop (for Serializable)

```python
import psycopg
from psycopg.errors import SerializationFailure

MAX_RETRIES = 3

def transfer_funds(conn, from_id, to_id, amount):
    for attempt in range(MAX_RETRIES):
        try:
            with conn.transaction():
                conn.execute("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
                # Read balances
                row = conn.execute(
                    "SELECT balance FROM accounts WHERE id = %s FOR UPDATE",
                    (from_id,)
                ).fetchone()
                if row[0] < amount:
                    raise ValueError("Insufficient funds")
                conn.execute(
                    "UPDATE accounts SET balance = balance - %s WHERE id = %s",
                    (amount, from_id)
                )
                conn.execute(
                    "UPDATE accounts SET balance = balance + %s WHERE id = %s",
                    (amount, to_id)
                )
            return  # success
        except SerializationFailure:
            if attempt == MAX_RETRIES - 1:
                raise
            continue  # retry
```

### 14.2 Optimistic Concurrency Control (Application-Level)

```sql
-- Add a version column:
ALTER TABLE products ADD COLUMN version INTEGER DEFAULT 1;

-- Read:
SELECT product_id, name, price, version FROM products WHERE product_id = 42;
-- Application stores version = 3

-- Update with version check:
UPDATE products
SET price = 29.99, version = version + 1
WHERE product_id = 42 AND version = 3;
-- If 0 rows affected → someone else modified it → retry or error
```

### 14.3 Idempotent Operations

Design operations that can be safely retried:

```sql
-- Idempotent insert (using ON CONFLICT):
INSERT INTO processed_events (event_id, processed_at)
VALUES ('evt_123', NOW())
ON CONFLICT (event_id) DO NOTHING;

-- Idempotent update (using a deduplication key):
UPDATE orders SET status = 'shipped', shipped_at = NOW()
WHERE order_id = 42 AND status = 'confirmed';  -- only transitions from confirmed
```

## 📚 8. Write-Ahead Logging (WAL)

### How WAL Ensures Durability

1. Before modifying data pages, write the change to the WAL (sequential append — fast).
2. Periodically flush dirty data pages to disk (checkpoint).
3. On crash recovery: replay WAL from last checkpoint to reconstruct committed state.

**Why sequential writes are fast:** Disk seeks are expensive. WAL is append-only (sequential I/O), while data pages are scattered (random I/O). Writing to WAL first and data pages later amortizes the random I/O cost.

### WAL Configuration (PostgreSQL)

```sql
-- Key settings (postgresql.conf):
-- wal_level = replica          -- minimum for replication
-- synchronous_commit = on      -- wait for WAL flush before confirming commit
-- checkpoint_timeout = 5min    -- time between checkpoints
-- max_wal_size = 1GB           -- trigger checkpoint if WAL exceeds this
```

Setting `synchronous_commit = off` improves write performance but risks losing the last few milliseconds of commits on crash.

## 📚 12. Deep Dive — Isolation Levels, MVCC Internals & Serializable Snapshot Isolation

### 12.1 Isolation Level Walkthrough with Anomalies

SQL defines four isolation levels, each permitting different anomalies:

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read | Serialization Anomaly |
|----------------|------------|--------------------|--------------|-----------------------|
| READ UNCOMMITTED | ✅ Possible | ✅ Possible | ✅ Possible | ✅ Possible |
| READ COMMITTED | ❌ Prevented | ✅ Possible | ✅ Possible | ✅ Possible |
| REPEATABLE READ | ❌ Prevented | ❌ Prevented | ✅ Possible* | ✅ Possible* |
| SERIALIZABLE | ❌ Prevented | ❌ Prevented | ❌ Prevented | ❌ Prevented |

*PostgreSQL's REPEATABLE READ actually prevents phantoms too (it uses snapshot isolation), but allows write skew.

**Anomaly 1: Dirty Read**

Transaction T2 reads data written by T1 before T1 commits. If T1 rolls back, T2 has read data that never existed.

```sql
-- T1:                              -- T2 (READ UNCOMMITTED):
BEGIN;
UPDATE accounts SET balance = 0
WHERE id = 1;
                                    -- T2 sees balance = 0 (uncommitted!)
                                    SELECT balance FROM accounts WHERE id = 1;
ROLLBACK;                           -- T2 used a value that was rolled back!
```

**PostgreSQL note:** PostgreSQL never allows dirty reads — even READ UNCOMMITTED behaves as READ COMMITTED.

**Anomaly 2: Non-Repeatable Read**

Transaction T1 reads a row, T2 modifies and commits it, T1 re-reads and gets a different value.

```sql
-- T1 (READ COMMITTED):            -- T2:
BEGIN;
SELECT salary FROM employees
WHERE emp_id = 1;  -- returns 50000
                                    BEGIN;
                                    UPDATE employees SET salary = 60000
                                    WHERE emp_id = 1;
                                    COMMIT;
SELECT salary FROM employees
WHERE emp_id = 1;  -- returns 60000! Different!
COMMIT;
```

**Anomaly 3: Phantom Read**

Transaction T1 reads a set of rows matching a condition, T2 inserts a new row matching that condition, T1 re-reads and sees the new row.

```sql
-- T1 (READ COMMITTED):            -- T2:
BEGIN;
SELECT COUNT(*) FROM employees
WHERE dept_id = 5;  -- returns 10
                                    BEGIN;
                                    INSERT INTO employees (name, dept_id)
                                    VALUES ('New Hire', 5);
                                    COMMIT;
SELECT COUNT(*) FROM employees
WHERE dept_id = 5;  -- returns 11! Phantom row appeared!
COMMIT;
```

**Anomaly 4: Write Skew (Serialization Anomaly)**

Two transactions read overlapping data, make decisions based on what they read, and write non-conflicting rows — but the combined result is inconsistent.

```sql
-- Constraint: at least one doctor must be on call at all times
-- Currently: Alice and Bob are both on call

-- T1:                              -- T2:
BEGIN;                              BEGIN;
SELECT COUNT(*) FROM on_call
WHERE shift = 'night';  -- 2       SELECT COUNT(*) FROM on_call
                                    WHERE shift = 'night';  -- 2
-- "2 doctors on call, safe to
-- remove myself"
UPDATE on_call SET on_call = false
WHERE doctor = 'Alice'
AND shift = 'night';
                                    -- "2 doctors on call, safe to
                                    -- remove myself"
                                    UPDATE on_call SET on_call = false
                                    WHERE doctor = 'Bob'
                                    AND shift = 'night';
COMMIT;                             COMMIT;
-- Result: ZERO doctors on call! Constraint violated!
```

**Fix: Use SERIALIZABLE isolation:**

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM on_call WHERE shift = 'night';
-- If another serializable transaction conflicts, one will be aborted
-- with: ERROR: could not serialize access due to read/write dependencies
UPDATE on_call SET on_call = false WHERE doctor = 'Alice' AND shift = 'night';
COMMIT;
```

### 12.2 MVCC Internals — PostgreSQL

PostgreSQL implements MVCC (Multi-Version Concurrency Control) by keeping multiple physical versions of each row.

**Row header fields:**

| Field | Purpose |
|-------|---------|
| `xmin` | Transaction ID that created this row version |
| `xmax` | Transaction ID that deleted/updated this version (0 if live) |
| `cmin/cmax` | Command ID within the transaction |
| `ctid` | Physical location (page, offset) — points to newer version if updated |

```sql
-- Inspect row versions (requires superuser):
SELECT xmin, xmax, ctid, * FROM employees WHERE emp_id = 1;

-- After an UPDATE, the old version has xmax set, new version has new xmin:
-- Old: xmin=100, xmax=105, ctid=(0,1)  ← "dead" after txn 105
-- New: xmin=105, xmax=0, ctid=(0,5)    ← "live" version
```

**Visibility rules (simplified):**

A row version is visible to transaction T if:
1. `xmin` is committed AND `xmin` < T's snapshot (or `xmin` = T's own txn)
2. `xmax` is either 0 (not deleted) OR `xmax` is not committed OR `xmax` > T's snapshot

**Snapshot in READ COMMITTED:** New snapshot taken at the START of each statement.
**Snapshot in REPEATABLE READ/SERIALIZABLE:** Single snapshot taken at the START of the transaction.

**VACUUM — Cleaning Dead Tuples:**

```sql
-- Dead tuples accumulate from UPDATEs and DELETEs
-- VACUUM reclaims space (but doesn't return it to OS):
VACUUM employees;

-- VACUUM FULL rewrites the entire table (locks it!):
VACUUM FULL employees;  -- use only as last resort

-- Monitor autovacuum:
SELECT relname, n_dead_tup, last_autovacuum, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- Tune autovacuum for high-write tables:
ALTER TABLE events SET (
    autovacuum_vacuum_threshold = 1000,
    autovacuum_vacuum_scale_factor = 0.01,  -- vacuum when 1% dead (default 20%!)
    autovacuum_analyze_threshold = 500
);
```

### 12.3 MVCC Internals — MySQL InnoDB

InnoDB uses a different MVCC approach:

- **Undo logs:** Old row versions are stored in undo tablespace (not in-place like PostgreSQL)
- **Read views:** Each transaction gets a consistent read view (list of active transaction IDs)
- **Purge thread:** Background thread removes undo records no longer needed

**Key differences from PostgreSQL:**

| Aspect | PostgreSQL | MySQL InnoDB |
|--------|-----------|--------------|
| Old versions stored | In-place (heap) | Undo tablespace |
| Cleanup mechanism | VACUUM (explicit) | Purge thread (automatic) |
| Bloat risk | High (if vacuum lags) | Low (undo space is separate) |
| Index maintenance | Dead tuples visible in index | Only live version in index |
| Long transactions | Block vacuum → bloat | Block purge → undo growth |

```sql
-- MySQL: Check undo space usage
SELECT * FROM information_schema.INNODB_METRICS
WHERE NAME LIKE '%undo%' OR NAME LIKE '%purge%';

-- MySQL: Monitor transaction history length (should be low)
SHOW ENGINE INNODB STATUS;  -- look for "History list length"
```

### 12.4 Serializable Snapshot Isolation (SSI)

PostgreSQL's SERIALIZABLE level uses SSI — a technique that detects serialization conflicts without blocking reads.

**How SSI works:**
1. Each transaction runs at snapshot isolation (reads from its snapshot, no blocking)
2. The system tracks **read-write dependencies** between concurrent transactions
3. If a cycle of dependencies is detected (rw-antidependency cycle), one transaction is aborted

**Dependency types:**
- **wr-dependency:** T2 reads a version written by T1 (T1 → T2)
- **ww-dependency:** T2 overwrites a version written by T1 (T1 → T2)
- **rw-antidependency:** T1 reads a version that T2 later overwrites (T2 → T1, "anti")

**A serialization anomaly exists iff there's a cycle containing at least two rw-antidependencies.**

```sql
-- SSI in practice — the system handles it automatically:
BEGIN ISOLATION LEVEL SERIALIZABLE;

-- Your normal queries here...
SELECT ... ;
UPDATE ... ;

COMMIT;
-- If conflict detected: ERROR: could not serialize access
-- Application must RETRY the entire transaction
```

**Retry pattern in Python:**

```python
import psycopg
from psycopg import errors

def run_serializable_transaction(conn_params, operation):
    """Execute operation in a serializable transaction with automatic retry."""
    max_retries = 5
    for attempt in range(max_retries):
        try:
            with psycopg.connect(**conn_params) as conn:
                conn.isolation_level = "SERIALIZABLE"
                with conn.cursor() as cur:
                    result = operation(cur)
                    conn.commit()
                    return result
        except errors.SerializationFailure:
            if attempt == max_retries - 1:
                raise
            # Exponential backoff
            import time
            time.sleep(0.1 * (2 ** attempt))
    raise RuntimeError("Max retries exceeded")

# Usage:
def transfer_funds(cur):
    cur.execute("UPDATE accounts SET balance = balance - 100 WHERE id = 1")
    cur.execute("UPDATE accounts SET balance = balance + 100 WHERE id = 2")

run_serializable_transaction({"dbname": "bank"}, transfer_funds)
```

### 12.5 Locking Strategies

**Row-level locks (PostgreSQL):**

```sql
-- FOR UPDATE: exclusive lock, blocks other FOR UPDATE and modifications
SELECT * FROM inventory WHERE product_id = 42 FOR UPDATE;

-- FOR NO KEY UPDATE: like FOR UPDATE but doesn't block FK checks
SELECT * FROM orders WHERE order_id = 100 FOR NO KEY UPDATE;

-- FOR SHARE: shared lock, blocks modifications but allows other FOR SHARE
SELECT * FROM products WHERE product_id = 42 FOR SHARE;

-- FOR KEY SHARE: weakest, only blocks deletion of the row
SELECT * FROM parent WHERE id = 1 FOR KEY SHARE;

-- SKIP LOCKED: skip rows locked by other transactions (job queue pattern)
SELECT * FROM job_queue
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

**Advisory locks (application-level):**

```sql
-- Session-level advisory lock (released at session end):
SELECT pg_advisory_lock(hashtext('process_customer_42'));
-- ... do work ...
SELECT pg_advisory_unlock(hashtext('process_customer_42'));

-- Transaction-level advisory lock (released at COMMIT/ROLLBACK):
SELECT pg_advisory_xact_lock(12345);

-- Try lock (non-blocking):
SELECT pg_try_advisory_lock(12345);  -- returns true/false
```

## 📚 13. Appendix — 2PC, Saga Patterns & CAP/PACELC Theorems

### 13.1 Two-Phase Commit (2PC)

2PC is a protocol for achieving atomicity across multiple databases/services.

**Phase 1 — Prepare (Voting):**
- Coordinator sends PREPARE to all participants
- Each participant writes changes to durable log, responds VOTE_COMMIT or VOTE_ABORT
- If any participant votes ABORT, the entire transaction aborts

**Phase 2 — Commit (Decision):**
- If all voted COMMIT: coordinator sends COMMIT to all participants
- Each participant makes changes permanent, responds ACK
- Coordinator records completion

```sql
-- PostgreSQL prepared transactions (for 2PC):
-- postgresql.conf: max_prepared_transactions = 10

-- Participant 1:
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
PREPARE TRANSACTION 'transfer_001_db1';

-- Participant 2:
BEGIN;
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
PREPARE TRANSACTION 'transfer_001_db2';

-- Coordinator decides (after both prepared successfully):
COMMIT PREPARED 'transfer_001_db1';
COMMIT PREPARED 'transfer_001_db2';

-- If anything fails:
ROLLBACK PREPARED 'transfer_001_db1';
ROLLBACK PREPARED 'transfer_001_db2';
```

**2PC problems:**
- **Blocking:** If coordinator crashes after PREPARE but before COMMIT, participants are stuck holding locks
- **Latency:** Two round-trips minimum
- **Single point of failure:** Coordinator must be highly available

### 13.2 Saga Pattern (Distributed Transactions Without 2PC)

A Saga is a sequence of local transactions where each step has a **compensating transaction** that undoes its effect if a later step fails.

**Choreography-based Saga (event-driven):**

```python
# Each service publishes events; others react

# Step 1: Order Service creates order
# → publishes OrderCreated event

# Step 2: Payment Service charges customer
# → publishes PaymentCompleted event
# → OR publishes PaymentFailed event → triggers compensation

# Step 3: Inventory Service reserves stock
# → publishes StockReserved event
# → OR publishes StockInsufficient → triggers compensation

# Compensation chain:
# StockInsufficient → Payment Service refunds → Order Service cancels order
```

**Orchestration-based Saga (central coordinator):**

```python
class OrderSaga:
    """Central orchestrator manages the saga steps."""

    steps = [
        SagaStep(
            action=lambda ctx: payment_service.charge(ctx.customer_id, ctx.amount),
            compensation=lambda ctx: payment_service.refund(ctx.payment_id)
        ),
        SagaStep(
            action=lambda ctx: inventory_service.reserve(ctx.product_id, ctx.qty),
            compensation=lambda ctx: inventory_service.release(ctx.reservation_id)
        ),
        SagaStep(
            action=lambda ctx: shipping_service.schedule(ctx.order_id),
            compensation=lambda ctx: shipping_service.cancel(ctx.shipment_id)
        ),
    ]

    def execute(self, context):
        completed = []
        for step in self.steps:
            try:
                step.action(context)
                completed.append(step)
            except Exception:
                # Compensate in reverse order
                for completed_step in reversed(completed):
                    completed_step.compensation(context)
                raise SagaFailed(f"Failed at step {step}, compensated")
```

**Saga vs 2PC comparison:**

| Property | 2PC | Saga |
|----------|-----|------|
| Consistency | Strong (ACID) | Eventual (ACD — no Isolation) |
| Availability | Lower (blocking) | Higher (no global locks) |
| Latency | Higher (2 round-trips) | Lower (async steps) |
| Complexity | Protocol complexity | Compensation logic complexity |
| Isolation | Full | Requires careful design (dirty reads possible between steps) |

### 13.3 The CAP Theorem

**CAP Theorem (Brewer, 2000):** A distributed system can provide at most two of three guarantees simultaneously:

- **C (Consistency):** Every read receives the most recent write (linearizability)
- **A (Availability):** Every request receives a response (not necessarily the latest data)
- **P (Partition Tolerance):** The system continues operating despite network partitions

**Since network partitions are inevitable in distributed systems, the real choice is between C and A during a partition:**

| System Type | During Partition | Examples |
|-------------|-----------------|----------|
| CP | Sacrifices availability (rejects requests) | PostgreSQL, MySQL (single-leader), ZooKeeper, etcd |
| AP | Sacrifices consistency (serves stale data) | Cassandra, DynamoDB, CouchDB |
| CA | Cannot exist in distributed systems | Single-node databases (trivially) |

### 13.4 The PACELC Theorem

PACELC extends CAP: "If there is a Partition, choose between Availability and Consistency; Else (normal operation), choose between Latency and Consistency."

$$
\text{PACELC} = \begin{cases} \text{Partition} \to \text{choose A or C} \\ \text{Else} \to \text{choose L or C} \end{cases}
$$

| System | P: A or C | E: L or C | Classification |
|--------|-----------|-----------|----------------|
| PostgreSQL (single) | C | C | PC/EC |
| Cassandra | A | L | PA/EL |
| MongoDB (default) | C | L | PC/EL |
| DynamoDB | A | L | PA/EL |
| CockroachDB | C | C | PC/EC |
| Spanner | C | C (with TrueTime) | PC/EC |

### 13.5 Consistency Models Spectrum

From strongest to weakest:

1. **Strict Serializability** — Operations appear in real-time order (Spanner with TrueTime)
2. **Linearizability** — Single-object, real-time ordering (etcd, ZooKeeper)
3. **Serializability** — Transactions appear in SOME serial order (PostgreSQL SERIALIZABLE)
4. **Snapshot Isolation** — Each transaction sees a consistent snapshot (PostgreSQL REPEATABLE READ)
5. **Causal Consistency** — Causally-related operations are seen in order (MongoDB sessions)
6. **Read-Your-Writes** — You always see your own writes (most systems with sticky sessions)
7. **Eventual Consistency** — All replicas converge eventually (Cassandra, DynamoDB)

### 13.6 Practical Distributed Transaction Patterns

**Pattern 1: Outbox Pattern (Reliable Event Publishing)**

```sql
-- Instead of: UPDATE table + publish event (not atomic!)
-- Use: UPDATE table + INSERT into outbox (same transaction)

BEGIN;
UPDATE orders SET status = 'confirmed' WHERE order_id = 42;
INSERT INTO outbox (aggregate_id, event_type, payload, created_at)
VALUES (42, 'OrderConfirmed', '{"order_id": 42, "amount": 99.99}', NOW());
COMMIT;

-- A separate process polls the outbox and publishes to message broker:
-- SELECT * FROM outbox WHERE published = false ORDER BY created_at LIMIT 100;
-- After publishing: UPDATE outbox SET published = true WHERE id IN (...);
```

**Pattern 2: Idempotency Keys**

```sql
-- Ensure exactly-once processing even with retries:
CREATE TABLE processed_requests (
    idempotency_key TEXT PRIMARY KEY,
    result JSONB NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Before processing:
INSERT INTO processed_requests (idempotency_key, result)
VALUES ('req_abc123', '{"status": "processing"}')
ON CONFLICT (idempotency_key) DO NOTHING;
-- If INSERT succeeded (1 row affected): process the request
-- If INSERT failed (0 rows): return cached result
```

**Pattern 3: Change Data Capture (CDC)**

```sql
-- PostgreSQL logical replication for CDC:
-- 1. Enable in postgresql.conf:
--    wal_level = logical
--    max_replication_slots = 4

-- 2. Create a publication:
CREATE PUBLICATION my_pub FOR TABLE orders, order_items;

-- 3. Create a logical replication slot:
SELECT pg_create_logical_replication_slot('my_slot', 'pgoutput');

-- 4. Consume changes (via Debezium, pg_recvlogical, or application):
-- Each change includes: operation (INSERT/UPDATE/DELETE), old values, new values
```
