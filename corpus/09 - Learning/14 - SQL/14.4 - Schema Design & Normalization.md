# 14.4 — Schema Design & Normalization

> *"Normalization is not about making the database smaller. It's about making the database correct — eliminating redundancy so that every fact is stored exactly once."* — C.J. Date

Schema design is where engineering meets theory. A well-normalized schema prevents data anomalies and makes your application correct by construction. A well-denormalized schema makes your analytics fast. Knowing when to apply each — and understanding the trade-offs — separates database practitioners from people who just write queries.

---

## 🎯 Learning Objectives

By the end of this chapter you will be able to:

1. Identify functional dependencies in a dataset.
2. Apply normalization rules from 1NF through BCNF systematically.
3. Recognize insertion, update, and deletion anomalies in unnormalized schemas.
4. Design Entity-Relationship (ER) diagrams and translate them to relational schemas.
5. Apply denormalization strategies (star schema, snowflake) for analytics workloads.
6. Design constraint systems (PK, FK, UNIQUE, CHECK, EXCLUDE) for data integrity.

## 📚 1. Functional Dependencies

### Definition 14.4.1 — Functional Dependency (FD)

A **functional dependency** $X \to Y$ holds on relation $R$ if, for every pair of tuples $t_1, t_2 \in R$:

$$
t_1[X] = t_2[X] \implies t_1[Y] = t_2[Y]
$$

In plain English: if two rows agree on $X$, they must agree on $Y$. "$X$ determines $Y$."

**Examples:**
- `emp_id → name, salary, dept_id` (employee ID determines all employee attributes)
- `dept_id → dept_name` (department ID determines department name)
- `(student_id, course_id) → grade` (student + course determines grade)

### Definition 14.4.2 — Trivial vs Non-Trivial FD

- **Trivial:** $X \to Y$ where $Y \subseteq X$ (always holds, uninformative)
- **Non-trivial:** $X \to Y$ where $Y \not\subseteq X$ (carries real information)

### Armstrong's Axioms

The complete set of inference rules for functional dependencies:

1. **Reflexivity:** If $Y \subseteq X$, then $X \to Y$ (trivial)
2. **Augmentation:** If $X \to Y$, then $XZ \to YZ$
3. **Transitivity:** If $X \to Y$ and $Y \to Z$, then $X \to Z$

Derived rules:
- **Union:** If $X \to Y$ and $X \to Z$, then $X \to YZ$
- **Decomposition:** If $X \to YZ$, then $X \to Y$ and $X \to Z$
- **Pseudotransitivity:** If $X \to Y$ and $WY \to Z$, then $WX \to Z$

### Closure of Attributes

The **closure** $X^+$ of attribute set $X$ under FD set $F$ is all attributes functionally determined by $X$:

```
Algorithm: Compute X⁺
1. result = X
2. Repeat until no change:
   For each FD (A → B) in F:
     If A ⊆ result, then result = result ∪ B
3. Return result
```

**Use:** $X$ is a superkey if $X^+ = \text{all attributes of } R$.

## 📚 2. Normal Forms

### 2.1 First Normal Form (1NF)

**Rule:** Every attribute contains only atomic (indivisible) values. No repeating groups, no arrays, no nested tables.

```sql
-- VIOLATES 1NF: multi-valued attribute
CREATE TABLE orders_bad (
    order_id INTEGER,
    customer VARCHAR(100),
    items    VARCHAR(500)  -- "widget, gadget, doohickey" — NOT atomic!
);

-- 1NF COMPLIANT: separate row per item
CREATE TABLE order_items (
    order_id   INTEGER REFERENCES orders(order_id),
    item_id    INTEGER REFERENCES products(product_id),
    quantity   INTEGER,
    PRIMARY KEY (order_id, item_id)
);
```

**Note:** PostgreSQL arrays (`INTEGER[]`) and JSON columns technically violate 1NF but are pragmatically useful. Use them when the array is treated as an opaque value, not when you need to query individual elements relationally.

### 2.2 Second Normal Form (2NF)

**Rule:** 1NF + no **partial dependencies**. Every non-key attribute must depend on the **entire** candidate key, not just part of it.

Only relevant for composite keys.

```sql
-- VIOLATES 2NF: student_name depends only on student_id (partial dependency)
CREATE TABLE enrollments_bad (
    student_id   INTEGER,
    course_id    INTEGER,
    student_name VARCHAR(100),  -- depends only on student_id!
    grade        CHAR(2),
    PRIMARY KEY (student_id, course_id)
);

-- 2NF COMPLIANT: decompose
CREATE TABLE students (
    student_id   INTEGER PRIMARY KEY,
    student_name VARCHAR(100)
);

CREATE TABLE enrollments (
    student_id INTEGER REFERENCES students(student_id),
    course_id  INTEGER REFERENCES courses(course_id),
    grade      CHAR(2),
    PRIMARY KEY (student_id, course_id)
);
```

### 2.3 Third Normal Form (3NF)

**Rule:** 2NF + no **transitive dependencies**. Non-key attributes must not depend on other non-key attributes.

Formally: For every non-trivial FD $X \to A$, either:
- $X$ is a superkey, OR
- $A$ is part of some candidate key (prime attribute)

```sql
-- VIOLATES 3NF: dept_name depends on dept_id (transitive: emp_id → dept_id → dept_name)
CREATE TABLE employees_bad (
    emp_id    INTEGER PRIMARY KEY,
    name      VARCHAR(100),
    dept_id   INTEGER,
    dept_name VARCHAR(50)   -- transitively dependent!
);

-- 3NF COMPLIANT: decompose
CREATE TABLE departments (
    dept_id   INTEGER PRIMARY KEY,
    dept_name VARCHAR(50)
);

CREATE TABLE employees (
    emp_id  INTEGER PRIMARY KEY,
    name    VARCHAR(100),
    dept_id INTEGER REFERENCES departments(dept_id)
);
```

### 2.4 Boyce-Codd Normal Form (BCNF)

**Rule:** For every non-trivial FD $X \to Y$, $X$ must be a superkey.

BCNF is stricter than 3NF — it eliminates the "prime attribute" exception. Most practical schemas that are in 3NF are also in BCNF.

```sql
-- Example where 3NF ≠ BCNF:
-- Relation: StudentAdvisor(student_id, subject, advisor)
-- FDs: (student_id, subject) → advisor
--      advisor → subject
-- 
-- advisor → subject violates BCNF (advisor is not a superkey)
-- but subject is a prime attribute, so 3NF is satisfied.
--
-- BCNF decomposition:
CREATE TABLE advisor_subjects (
    advisor_id INTEGER PRIMARY KEY,
    subject    VARCHAR(50)
);

CREATE TABLE student_advisors (
    student_id INTEGER,
    advisor_id INTEGER REFERENCES advisor_subjects(advisor_id),
    PRIMARY KEY (student_id, advisor_id)
);
```

### 2.5 Normalization Summary

| Normal Form | Eliminates | Rule |
|-------------|-----------|------|
| 1NF | Repeating groups | Atomic values only |
| 2NF | Partial dependencies | Full dependency on entire key |
| 3NF | Transitive dependencies | Non-key → non-key eliminated |
| BCNF | All non-superkey determinants | Every determinant is a superkey |

## 📚 3. Data Anomalies

Why normalize? To prevent these anomalies in unnormalized schemas:

### Insertion Anomaly
Can't insert a new department without also inserting an employee (if dept info is stored in the employee table).

### Update Anomaly
If department name is stored in every employee row, renaming a department requires updating hundreds of rows. Miss one → inconsistency.

### Deletion Anomaly
Deleting the last employee in a department loses all information about that department.

```sql
-- Unnormalized: all three anomalies present
CREATE TABLE emp_dept_bad (
    emp_id    INTEGER PRIMARY KEY,
    emp_name  VARCHAR(100),
    dept_id   INTEGER,
    dept_name VARCHAR(50),    -- redundant!
    dept_loc  VARCHAR(100)    -- redundant!
);

-- Normalized: anomalies eliminated
CREATE TABLE departments (
    dept_id   INTEGER PRIMARY KEY,
    dept_name VARCHAR(50),
    dept_loc  VARCHAR(100)
);

CREATE TABLE employees (
    emp_id   INTEGER PRIMARY KEY,
    emp_name VARCHAR(100),
    dept_id  INTEGER REFERENCES departments(dept_id)
);
```

## 📚 4. Entity-Relationship Modeling

### 4.1 ER Diagram Components

| Component | Meaning | SQL Mapping |
|-----------|---------|-------------|
| Entity | A thing with independent existence | Table |
| Attribute | Property of an entity | Column |
| Relationship | Association between entities | Foreign key or junction table |
| Cardinality | 1:1, 1:N, M:N | Determines FK placement |

### 4.2 Cardinality Patterns

**One-to-Many (1:N):** FK on the "many" side.

```sql
-- One department has many employees
CREATE TABLE employees (
    emp_id  INTEGER PRIMARY KEY,
    dept_id INTEGER REFERENCES departments(dept_id)  -- FK on many side
);
```

**Many-to-Many (M:N):** Junction (bridge) table.

```sql
-- Students enroll in many courses; courses have many students
CREATE TABLE enrollments (
    student_id INTEGER REFERENCES students(student_id),
    course_id  INTEGER REFERENCES courses(course_id),
    enrolled_at TIMESTAMP DEFAULT NOW(),
    PRIMARY KEY (student_id, course_id)
);
```

**One-to-One (1:1):** FK with UNIQUE constraint, or merge into one table.

```sql
-- Each employee has exactly one badge (separate for security reasons)
CREATE TABLE badges (
    badge_id  INTEGER PRIMARY KEY,
    emp_id    INTEGER UNIQUE REFERENCES employees(emp_id),
    rfid_code VARCHAR(50)
);
```

## 📚 5. Constraint Design

### 5.1 Primary Keys

```sql
-- Natural key (meaningful business identifier):
CREATE TABLE countries (
    country_code CHAR(2) PRIMARY KEY,  -- ISO 3166-1 alpha-2
    name VARCHAR(100)
);

-- Surrogate key (system-generated, no business meaning):
CREATE TABLE orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    order_date DATE NOT NULL
);
```

**Surrogate vs Natural keys:**
- Surrogate: stable (never changes), compact (integer), no business coupling
- Natural: self-documenting, no extra column, but may change (email, SSN)
- **Recommendation:** Use surrogate keys for most tables. Add UNIQUE constraints on natural keys.

### 5.2 Foreign Keys

```sql
CREATE TABLE orders (
    order_id    BIGINT PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(customer_id)
        ON DELETE RESTRICT      -- prevent deleting customer with orders
        ON UPDATE CASCADE,      -- if customer_id changes, update here too
    status      VARCHAR(20) DEFAULT 'pending'
);
```

**Referential actions:**
| Action | ON DELETE | ON UPDATE |
|--------|-----------|-----------|
| `RESTRICT` | Block deletion | Block update |
| `CASCADE` | Delete child rows | Update child FKs |
| `SET NULL` | Set FK to NULL | Set FK to NULL |
| `SET DEFAULT` | Set FK to default | Set FK to default |
| `NO ACTION` | Like RESTRICT (deferred check) | Like RESTRICT |

### 5.3 CHECK Constraints

```sql
CREATE TABLE products (
    product_id INTEGER PRIMARY KEY,
    name       VARCHAR(100) NOT NULL,
    price      NUMERIC(10,2) CHECK (price > 0),
    weight_kg  NUMERIC(6,2) CHECK (weight_kg >= 0),
    category   VARCHAR(20) CHECK (category IN ('electronics', 'clothing', 'food'))
);
```

### 5.4 EXCLUDE Constraints (PostgreSQL)

Prevent overlapping ranges:

```sql
-- No overlapping room bookings
CREATE TABLE room_bookings (
    room_id    INTEGER,
    start_time TIMESTAMP,
    end_time   TIMESTAMP,
    EXCLUDE USING gist (
        room_id WITH =,
        tsrange(start_time, end_time) WITH &&
    )
);
```

## 📚 6. Denormalization for Analytics

### 6.1 When to Denormalize

Normalize for **OLTP** (transactional workloads): many small reads/writes, data integrity critical.

Denormalize for **OLAP** (analytical workloads): few large reads, aggregation-heavy, write-once-read-many.

### 6.2 Star Schema

Central **fact table** (events/transactions) surrounded by **dimension tables** (descriptive attributes):

```sql
-- Fact table: one row per sale event
CREATE TABLE fact_sales (
    sale_id      BIGINT PRIMARY KEY,
    date_id      INTEGER REFERENCES dim_date(date_id),
    product_id   INTEGER REFERENCES dim_product(product_id),
    customer_id  INTEGER REFERENCES dim_customer(customer_id),
    store_id     INTEGER REFERENCES dim_store(store_id),
    quantity     INTEGER NOT NULL,
    unit_price   NUMERIC(10,2) NOT NULL,
    total_amount NUMERIC(12,2) NOT NULL
);

-- Dimension table: denormalized (flat) for fast joins
CREATE TABLE dim_product (
    product_id    INTEGER PRIMARY KEY,
    product_name  VARCHAR(200),
    category      VARCHAR(50),
    subcategory   VARCHAR(50),
    brand         VARCHAR(100),
    supplier_name VARCHAR(100)  -- denormalized from supplier table!
);

CREATE TABLE dim_date (
    date_id      INTEGER PRIMARY KEY,
    full_date    DATE,
    year         SMALLINT,
    quarter      SMALLINT,
    month        SMALLINT,
    day_of_week  SMALLINT,
    is_weekend   BOOLEAN,
    fiscal_year  SMALLINT
);
```

### 6.3 Snowflake Schema

Like star schema but dimensions are partially normalized:

```sql
-- dim_product references dim_category (normalized dimension)
CREATE TABLE dim_category (
    category_id INTEGER PRIMARY KEY,
    category_name VARCHAR(50),
    department VARCHAR(50)
);

CREATE TABLE dim_product (
    product_id   INTEGER PRIMARY KEY,
    product_name VARCHAR(200),
    category_id  INTEGER REFERENCES dim_category(category_id),
    brand        VARCHAR(100)
);
```

**Trade-off:** Star is faster (fewer joins) but more redundant. Snowflake saves space but requires more joins.

### 6.4 Materialized Views

Pre-compute expensive aggregations:

```sql
CREATE MATERIALIZED VIEW monthly_sales_summary AS
SELECT
    d.year,
    d.month,
    p.category,
    SUM(f.total_amount) AS total_revenue,
    COUNT(*) AS transaction_count,
    AVG(f.total_amount) AS avg_transaction
FROM fact_sales f
JOIN dim_date d ON f.date_id = d.date_id
JOIN dim_product p ON f.product_id = p.product_id
GROUP BY d.year, d.month, p.category;

-- Refresh when underlying data changes:
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales_summary;
```

## 📚 7. Schema Evolution & Migrations

### 14.1 Non-Breaking Changes

```sql
-- Adding a nullable column (safe, no rewrite):
ALTER TABLE employees ADD COLUMN middle_name VARCHAR(50);

-- Adding a column with a default (PG 11+: no rewrite for non-volatile defaults):
ALTER TABLE employees ADD COLUMN active BOOLEAN DEFAULT true;

-- Creating an index concurrently (no lock):
CREATE INDEX CONCURRENTLY idx_emp_dept ON employees(dept_id);
```

### 14.2 Breaking Changes (Require Migration Strategy)

```sql
-- Renaming a column (breaks existing queries):
ALTER TABLE employees RENAME COLUMN name TO full_name;

-- Changing a type (may require rewrite):
ALTER TABLE employees ALTER COLUMN salary TYPE NUMERIC(12,2);

-- Dropping a column:
ALTER TABLE employees DROP COLUMN middle_name;
```

**Migration strategy:** Use tools like Alembic (Python), Flyway (Java), or golang-migrate. Version your schema changes. Apply forward-only migrations in production.

## 🧪 8. Worked Example — Designing a Schema from Requirements

**Requirements:** "Build a database for an online bookstore. Customers can place orders containing multiple books. Books have authors (many-to-many). Track inventory per warehouse."

**Step 1: Identify entities:** Customer, Order, Book, Author, Warehouse, Inventory

**Step 2: Identify relationships:**
- Customer 1:N Order
- Order M:N Book (via order_items)
- Book M:N Author (via book_authors)
- Warehouse + Book → Inventory (quantity)

**Step 3: Schema:**

```sql
CREATE TABLE customers (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       VARCHAR(255) UNIQUE NOT NULL,
    name        VARCHAR(200) NOT NULL,
    created_at  TIMESTAMP DEFAULT NOW()
);

CREATE TABLE authors (
    author_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name      VARCHAR(200) NOT NULL
);

CREATE TABLE books (
    book_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    isbn       VARCHAR(13) UNIQUE,
    title      VARCHAR(500) NOT NULL,
    price      NUMERIC(8,2) NOT NULL CHECK (price > 0),
    published  DATE
);

CREATE TABLE book_authors (
    book_id   BIGINT REFERENCES books(book_id) ON DELETE CASCADE,
    author_id BIGINT REFERENCES authors(author_id) ON DELETE CASCADE,
    PRIMARY KEY (book_id, author_id)
);

CREATE TABLE orders (
    order_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(customer_id),
    order_date  TIMESTAMP DEFAULT NOW(),
    status      VARCHAR(20) DEFAULT 'pending'
                CHECK (status IN ('pending','confirmed','shipped','delivered','cancelled'))
);

CREATE TABLE order_items (
    order_id BIGINT REFERENCES orders(order_id) ON DELETE CASCADE,
    book_id  BIGINT REFERENCES books(book_id),
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    price_at_purchase NUMERIC(8,2) NOT NULL,  -- snapshot price at order time
    PRIMARY KEY (order_id, book_id)
);

CREATE TABLE warehouses (
    warehouse_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name         VARCHAR(100) NOT NULL,
    location     VARCHAR(200)
);

CREATE TABLE inventory (
    warehouse_id BIGINT REFERENCES warehouses(warehouse_id),
    book_id      BIGINT REFERENCES books(book_id),
    quantity     INTEGER NOT NULL DEFAULT 0 CHECK (quantity >= 0),
    PRIMARY KEY (warehouse_id, book_id)
);
```

## 📚 12. Deep Dive — 1NF Through 6NF, Denormalization Patterns & Temporal Tables

### 12.1 Normal Forms: Complete Hierarchy

**First Normal Form (1NF):** All attributes contain only atomic (indivisible) values. No repeating groups, no arrays-as-values.

```sql
-- VIOLATES 1NF (multi-valued attribute):
CREATE TABLE students_bad (
    student_id INT PRIMARY KEY,
    name TEXT,
    phone_numbers TEXT  -- '555-0101, 555-0102, 555-0103'
);

-- 1NF compliant:
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name TEXT NOT NULL
);
CREATE TABLE student_phones (
    student_id INT REFERENCES students(student_id),
    phone TEXT NOT NULL,
    PRIMARY KEY (student_id, phone)
);
```

**Note:** PostgreSQL's `ARRAY` and `JSONB` types technically violate 1NF but are pragmatically useful. The key question: do you need to query/filter individual elements? If yes, normalize. If the array is always read/written as a unit, arrays are acceptable.

**Second Normal Form (2NF):** 1NF + no partial dependencies. Every non-key attribute depends on the ENTIRE primary key, not just part of it.

```sql
-- VIOLATES 2NF (student_name depends only on student_id, not the full PK):
CREATE TABLE enrollments_bad (
    student_id INT,
    course_id INT,
    student_name TEXT,    -- depends only on student_id (partial dependency)
    grade CHAR(2),
    PRIMARY KEY (student_id, course_id)
);

-- 2NF compliant (decompose):
CREATE TABLE students (student_id INT PRIMARY KEY, student_name TEXT NOT NULL);
CREATE TABLE enrollments (
    student_id INT REFERENCES students(student_id),
    course_id INT REFERENCES courses(course_id),
    grade CHAR(2),
    PRIMARY KEY (student_id, course_id)
);
```

**Third Normal Form (3NF):** 2NF + no transitive dependencies. Non-key attributes don't depend on other non-key attributes.

```sql
-- VIOLATES 3NF (dept_name depends on dept_id, which depends on emp_id):
CREATE TABLE employees_bad (
    emp_id INT PRIMARY KEY,
    name TEXT,
    dept_id INT,
    dept_name TEXT  -- transitively depends on emp_id via dept_id
);

-- 3NF compliant:
CREATE TABLE departments (dept_id INT PRIMARY KEY, dept_name TEXT NOT NULL);
CREATE TABLE employees (
    emp_id INT PRIMARY KEY,
    name TEXT NOT NULL,
    dept_id INT REFERENCES departments(dept_id)
);
```

**Boyce-Codd Normal Form (BCNF):** For every non-trivial FD $X \to Y$, $X$ must be a superkey. Stricter than 3NF — eliminates ALL redundancy from functional dependencies.

```sql
-- VIOLATES BCNF but satisfies 3NF:
-- Relation: CourseSection(student, course, instructor)
-- FDs: {student, course} → instructor, instructor → course
-- instructor → course violates BCNF (instructor is not a superkey)
-- But 'course' is a prime attribute (part of candidate key), so 3NF is satisfied

-- BCNF decomposition:
CREATE TABLE teaches (instructor TEXT PRIMARY KEY, course TEXT NOT NULL);
CREATE TABLE enrollments (
    student TEXT,
    instructor TEXT REFERENCES teaches(instructor),
    PRIMARY KEY (student, instructor)
);
-- Trade-off: we lost the ability to directly enforce {student, course} → instructor
```

**Fourth Normal Form (4NF):** BCNF + no multi-valued dependencies (MVDs). An MVD $X \twoheadrightarrow Y$ means: for a given $X$, the set of $Y$ values is independent of other attributes.

```sql
-- VIOLATES 4NF:
-- Employee(emp_id, skill, language) — skills and languages are independent
-- emp_id ↠ skill and emp_id ↠ language (multi-valued dependencies)
-- This causes redundancy: if emp has 3 skills and 2 languages → 6 rows

-- 4NF compliant (decompose independent MVDs):
CREATE TABLE emp_skills (emp_id INT, skill TEXT, PRIMARY KEY (emp_id, skill));
CREATE TABLE emp_languages (emp_id INT, language TEXT, PRIMARY KEY (emp_id, language));
```

**Fifth Normal Form (5NF / Project-Join Normal Form):** Cannot be further decomposed without losing information. Eliminates join dependencies that aren't implied by candidate keys.

```sql
-- VIOLATES 5NF:
-- Supply(supplier, part, project) — a supplier supplies a part to a project
-- The join dependency *{SP, PJ, SJ} holds but isn't implied by any key
-- Decomposing into SP, PJ, SJ and joining them back gives spurious tuples

-- 5NF: keep the ternary relationship as-is (it's already in 5NF if no JD exists)
CREATE TABLE supply (
    supplier_id INT,
    part_id INT,
    project_id INT,
    PRIMARY KEY (supplier_id, part_id, project_id)
);
```

**Sixth Normal Form (6NF):** A relation is in 6NF if it has no non-trivial join dependencies at all. Every relation is decomposed to its irreducible components — essentially one attribute per table (plus the key).

6NF is primarily used in **temporal databases** where each attribute can change independently over time:

```sql
-- 6NF temporal design:
CREATE TABLE emp_name (emp_id INT, name TEXT, valid_from DATE, valid_to DATE, PRIMARY KEY (emp_id, valid_from));
CREATE TABLE emp_salary (emp_id INT, salary NUMERIC, valid_from DATE, valid_to DATE, PRIMARY KEY (emp_id, valid_from));
CREATE TABLE emp_dept (emp_id INT, dept_id INT, valid_from DATE, valid_to DATE, PRIMARY KEY (emp_id, valid_from));
-- Each attribute has its own timeline — no NULL explosion when one changes
```

### 12.2 Denormalization Patterns for Read-Heavy Workloads

**Pattern 1: Materialized Aggregates**

```sql
-- Instead of computing COUNT(*) on every page load:
ALTER TABLE posts ADD COLUMN comment_count INT DEFAULT 0;

-- Maintain via trigger:
CREATE OR REPLACE FUNCTION update_comment_count()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        UPDATE posts SET comment_count = comment_count + 1 WHERE post_id = NEW.post_id;
    ELSIF TG_OP = 'DELETE' THEN
        UPDATE posts SET comment_count = comment_count - 1 WHERE post_id = OLD.post_id;
    END IF;
    RETURN NULL;
END;
$$;

CREATE TRIGGER trg_comment_count
AFTER INSERT OR DELETE ON comments
FOR EACH ROW EXECUTE FUNCTION update_comment_count();
```

**Pattern 2: Flattened Lookup (Embedding Foreign Data)**

```sql
-- Normalized: orders → customers (requires JOIN for every order display)
-- Denormalized: embed customer_name directly in orders
ALTER TABLE orders ADD COLUMN customer_name TEXT;

-- Trade-off: faster reads, but customer_name can become stale
-- Mitigation: trigger on customers UPDATE to propagate changes
```

**Pattern 3: Pre-computed JSON Documents**

```sql
-- For API responses that always need the same shape:
CREATE TABLE product_documents (
    product_id INT PRIMARY KEY,
    document JSONB NOT NULL,
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Refresh on product change:
CREATE OR REPLACE FUNCTION refresh_product_doc()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO product_documents (product_id, document, updated_at)
    VALUES (
        NEW.product_id,
        jsonb_build_object(
            'id', NEW.product_id,
            'name', NEW.name,
            'price', NEW.price,
            'category', (SELECT name FROM categories WHERE id = NEW.category_id),
            'reviews_count', (SELECT COUNT(*) FROM reviews WHERE product_id = NEW.product_id),
            'avg_rating', (SELECT AVG(rating) FROM reviews WHERE product_id = NEW.product_id)
        ),
        NOW()
    )
    ON CONFLICT (product_id) DO UPDATE SET
        document = EXCLUDED.document,
        updated_at = EXCLUDED.updated_at;
    RETURN NEW;
END;
$$;
```

**Pattern 4: Materialized Views (Best of Both Worlds)**

```sql
-- Keep normalized source of truth, materialize for reads:
CREATE MATERIALIZED VIEW mv_product_catalog AS
SELECT
    p.product_id,
    p.name,
    p.price,
    c.category_name,
    COALESCE(r.avg_rating, 0) AS avg_rating,
    COALESCE(r.review_count, 0) AS review_count,
    i.total_stock
FROM products p
LEFT JOIN categories c ON p.category_id = c.category_id
LEFT JOIN (
    SELECT product_id, AVG(rating) AS avg_rating, COUNT(*) AS review_count
    FROM reviews GROUP BY product_id
) r ON p.product_id = r.product_id
LEFT JOIN (
    SELECT product_id, SUM(quantity) AS total_stock
    FROM inventory GROUP BY product_id
) i ON p.product_id = i.product_id;

CREATE UNIQUE INDEX ON mv_product_catalog(product_id);
-- Refresh periodically or on-demand
```

### 12.3 Temporal Tables (System-Versioned & Application-Time)

**System-versioned temporal tables** automatically track the history of every row change.

```sql
-- PostgreSQL: using temporal_tables extension or manual implementation
CREATE TABLE employees (
    emp_id INT NOT NULL,
    name TEXT NOT NULL,
    salary NUMERIC(10,2),
    dept_id INT,
    -- System-time columns:
    valid_from TIMESTAMP GENERATED ALWAYS AS ROW START,
    valid_to TIMESTAMP GENERATED ALWAYS AS ROW END,
    PERIOD FOR SYSTEM_TIME (valid_from, valid_to),
    PRIMARY KEY (emp_id, valid_from)
);

-- Manual implementation (PostgreSQL doesn't have native system-versioning):
CREATE TABLE employees (
    emp_id INT NOT NULL,
    name TEXT NOT NULL,
    salary NUMERIC(10,2),
    dept_id INT,
    sys_start TIMESTAMP NOT NULL DEFAULT NOW(),
    sys_end TIMESTAMP NOT NULL DEFAULT 'infinity',
    PRIMARY KEY (emp_id, sys_start)
);

CREATE TABLE employees_history (LIKE employees INCLUDING ALL);

-- Trigger to maintain history:
CREATE OR REPLACE FUNCTION employees_versioning()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    IF TG_OP = 'UPDATE' THEN
        -- Close the old version
        INSERT INTO employees_history
        SELECT OLD.emp_id, OLD.name, OLD.salary, OLD.dept_id,
               OLD.sys_start, NOW();
        -- Update sys_start on new version
        NEW.sys_start = NOW();
        NEW.sys_end = 'infinity';
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO employees_history
        SELECT OLD.emp_id, OLD.name, OLD.salary, OLD.dept_id,
               OLD.sys_start, NOW();
        RETURN OLD;
    END IF;
END;
$$;

CREATE TRIGGER employees_version_trigger
BEFORE UPDATE OR DELETE ON employees
FOR EACH ROW EXECUTE FUNCTION employees_versioning();
```

**Querying temporal data:**

```sql
-- Current state:
SELECT * FROM employees WHERE sys_end = 'infinity';

-- State at a specific point in time:
SELECT * FROM employees
WHERE sys_start <= '2025-06-15' AND sys_end > '2025-06-15'
UNION ALL
SELECT * FROM employees_history
WHERE sys_start <= '2025-06-15' AND sys_end > '2025-06-15';

-- Full history of an employee:
SELECT * FROM (
    SELECT *, 'current' AS source FROM employees WHERE emp_id = 42
    UNION ALL
    SELECT *, 'history' AS source FROM employees_history WHERE emp_id = 42
) all_versions
ORDER BY sys_start;
```

**Application-time (business-time) periods:**

```sql
-- Insurance policies with validity periods:
CREATE TABLE policies (
    policy_id INT,
    customer_id INT,
    coverage_type TEXT,
    premium NUMERIC,
    valid_from DATE NOT NULL,
    valid_to DATE NOT NULL,
    CHECK (valid_from < valid_to),
    -- Prevent overlapping periods for same policy:
    EXCLUDE USING gist (
        policy_id WITH =,
        daterange(valid_from, valid_to) WITH &&
    )
);
```

## 📚 13. Appendix — Anchor Modeling, Data Vault & Analytics Schema Patterns

### 13.1 Anchor Modeling

Anchor Modeling is a 6NF-based technique designed for agile data warehousing where the schema evolves frequently without breaking existing queries.

**Core concepts:**
- **Anchor:** An entity (identified by a surrogate key). No attributes.
- **Attribute:** A separate table for each property of an anchor.
- **Tie:** A relationship between anchors (separate table).
- **Knot:** A shared domain/lookup (e.g., country codes).

```sql
-- Anchor: Employee (just the identity)
CREATE TABLE an_employee (
    emp_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Attributes (one table per attribute, historized):
CREATE TABLE at_employee_name (
    emp_id INT REFERENCES an_employee(emp_id),
    name TEXT NOT NULL,
    valid_from TIMESTAMP NOT NULL DEFAULT NOW(),
    PRIMARY KEY (emp_id, valid_from)
);

CREATE TABLE at_employee_salary (
    emp_id INT REFERENCES an_employee(emp_id),
    salary NUMERIC(10,2) NOT NULL,
    valid_from TIMESTAMP NOT NULL DEFAULT NOW(),
    PRIMARY KEY (emp_id, valid_from)
);

-- Tie: Employee works in Department
CREATE TABLE tie_emp_dept (
    emp_id INT REFERENCES an_employee(emp_id),
    dept_id INT REFERENCES an_department(dept_id),
    valid_from TIMESTAMP NOT NULL DEFAULT NOW(),
    PRIMARY KEY (emp_id, valid_from)
);
```

**Advantages:**
- Adding a new attribute = adding a new table (no ALTER TABLE)
- Full history by default (every attribute is temporal)
- No NULLs (if an attribute doesn't apply, the row simply doesn't exist)
- Schema evolution never breaks existing queries

**Disadvantages:**
- Many JOINs required to reconstruct a full entity
- Complex queries for simple lookups
- Tooling support is limited

### 13.2 Data Vault 2.0

Data Vault is a modeling methodology for enterprise data warehouses, designed for auditability, scalability, and parallel loading.

**Core components:**

| Component | Purpose | Key Columns |
|-----------|---------|-------------|
| **Hub** | Business key (unique entity identifier) | hash_key, business_key, load_date, record_source |
| **Link** | Relationship between hubs | hash_key, hub1_hash, hub2_hash, load_date, record_source |
| **Satellite** | Descriptive attributes (historized) | hub_hash, load_date, hash_diff, attributes... |

```sql
-- Hub: Customer (business key = email)
CREATE TABLE hub_customer (
    customer_hash BYTEA PRIMARY KEY,  -- MD5/SHA of business key
    email TEXT NOT NULL UNIQUE,        -- business key
    load_date TIMESTAMP NOT NULL,
    record_source TEXT NOT NULL
);

-- Hub: Product
CREATE TABLE hub_product (
    product_hash BYTEA PRIMARY KEY,
    sku TEXT NOT NULL UNIQUE,
    load_date TIMESTAMP NOT NULL,
    record_source TEXT NOT NULL
);

-- Link: Customer purchases Product
CREATE TABLE link_purchase (
    purchase_hash BYTEA PRIMARY KEY,
    customer_hash BYTEA REFERENCES hub_customer(customer_hash),
    product_hash BYTEA REFERENCES hub_product(product_hash),
    load_date TIMESTAMP NOT NULL,
    record_source TEXT NOT NULL
);

-- Satellite: Customer details (historized)
CREATE TABLE sat_customer_details (
    customer_hash BYTEA REFERENCES hub_customer(customer_hash),
    load_date TIMESTAMP NOT NULL,
    hash_diff BYTEA NOT NULL,  -- hash of all attribute values (change detection)
    name TEXT,
    phone TEXT,
    address TEXT,
    tier TEXT,
    PRIMARY KEY (customer_hash, load_date)
);
```

**Loading pattern:**

```sql
-- Insert new hub records (only if business key is new):
INSERT INTO hub_customer (customer_hash, email, load_date, record_source)
SELECT
    md5(email)::bytea,
    email,
    NOW(),
    'crm_system'
FROM staging_customers s
WHERE NOT EXISTS (
    SELECT 1 FROM hub_customer h WHERE h.email = s.email
);

-- Insert satellite records (only if attributes changed):
INSERT INTO sat_customer_details (customer_hash, load_date, hash_diff, name, phone, address, tier)
SELECT
    md5(s.email)::bytea,
    NOW(),
    md5(s.name || s.phone || s.address || s.tier)::bytea,
    s.name, s.phone, s.address, s.tier
FROM staging_customers s
WHERE NOT EXISTS (
    SELECT 1 FROM sat_customer_details sat
    WHERE sat.customer_hash = md5(s.email)::bytea
      AND sat.hash_diff = md5(s.name || s.phone || s.address || s.tier)::bytea
      AND sat.load_date = (
          SELECT MAX(load_date) FROM sat_customer_details
          WHERE customer_hash = md5(s.email)::bytea
      )
);
```

### 13.3 Star Schema vs Snowflake Schema

**Star Schema:**

```sql
-- Central fact table surrounded by dimension tables (one level)
CREATE TABLE fact_sales (
    sale_id BIGINT PRIMARY KEY,
    date_id INT REFERENCES dim_date(date_id),
    product_id INT REFERENCES dim_product(product_id),
    store_id INT REFERENCES dim_store(store_id),
    customer_id INT REFERENCES dim_customer(customer_id),
    quantity INT NOT NULL,
    unit_price NUMERIC(8,2) NOT NULL,
    total_amount NUMERIC(10,2) NOT NULL,
    discount_pct NUMERIC(4,2) DEFAULT 0
);

-- Dimension: denormalized (all attributes in one table)
CREATE TABLE dim_product (
    product_id INT PRIMARY KEY,
    product_name TEXT NOT NULL,
    brand TEXT,
    category TEXT,          -- denormalized from category table
    subcategory TEXT,       -- denormalized
    supplier_name TEXT,     -- denormalized from supplier table
    unit_cost NUMERIC(8,2)
);
```

**Snowflake Schema:**

```sql
-- Dimensions are normalized (multiple levels)
CREATE TABLE dim_product (
    product_id INT PRIMARY KEY,
    product_name TEXT NOT NULL,
    brand TEXT,
    subcategory_id INT REFERENCES dim_subcategory(subcategory_id),
    supplier_id INT REFERENCES dim_supplier(supplier_id),
    unit_cost NUMERIC(8,2)
);

CREATE TABLE dim_subcategory (
    subcategory_id INT PRIMARY KEY,
    subcategory_name TEXT NOT NULL,
    category_id INT REFERENCES dim_category(category_id)
);

CREATE TABLE dim_category (
    category_id INT PRIMARY KEY,
    category_name TEXT NOT NULL,
    department TEXT
);
```

**Comparison:**

| Aspect | Star | Snowflake |
|--------|------|-----------|
| Query simplicity | Fewer JOINs | More JOINs |
| Query performance | Faster (fewer joins, bitmap indexes) | Slower |
| Storage | More redundant | Less redundant |
| ETL complexity | Simpler (flatten during load) | More complex |
| Dimension updates | Must update all denormalized copies | Update once |
| BI tool compatibility | Excellent (most tools expect star) | Good |
| Best for | Analytics, dashboards, OLAP | Storage-constrained, frequently-changing dims |

### 13.4 Slowly Changing Dimensions (SCD)

| Type | Strategy | History | Example |
|------|----------|---------|---------|
| SCD-0 | Never change | No | Original signup date |
| SCD-1 | Overwrite | No | Fix a typo in customer name |
| SCD-2 | Add new row with validity dates | Full | Track address changes over time |
| SCD-3 | Add "previous" column | Limited (1 change) | Store previous + current value |
| SCD-4 | Separate history table | Full | Current in main, history in archive |
| SCD-6 | Hybrid (1+2+3) | Full + current flag | Combines approaches |

```sql
-- SCD Type 2 implementation:
CREATE TABLE dim_customer (
    customer_sk BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- surrogate key
    customer_id INT NOT NULL,       -- natural/business key
    name TEXT NOT NULL,
    address TEXT,
    tier TEXT,
    valid_from DATE NOT NULL,
    valid_to DATE NOT NULL DEFAULT '9999-12-31',
    is_current BOOLEAN NOT NULL DEFAULT true
);

-- When customer changes address:
-- Step 1: Close current record
UPDATE dim_customer
SET valid_to = CURRENT_DATE - 1, is_current = false
WHERE customer_id = 42 AND is_current = true;

-- Step 2: Insert new version
INSERT INTO dim_customer (customer_id, name, address, tier, valid_from, is_current)
VALUES (42, 'Alice Smith', '456 New St', 'Gold', CURRENT_DATE, true);
```

### 13.5 Fact Table Grain Patterns

```sql
-- Transaction grain (one row per event):
CREATE TABLE fact_orders (
    order_id BIGINT PRIMARY KEY,
    date_id INT, customer_id INT, product_id INT,
    quantity INT, amount NUMERIC
);

-- Periodic snapshot (one row per entity per period):
CREATE TABLE fact_inventory_daily (
    date_id INT,
    product_id INT,
    warehouse_id INT,
    quantity_on_hand INT,
    quantity_reserved INT,
    PRIMARY KEY (date_id, product_id, warehouse_id)
);

-- Accumulating snapshot (one row per process, updated as milestones occur):
CREATE TABLE fact_order_fulfillment (
    order_id BIGINT PRIMARY KEY,
    order_date_id INT,
    ship_date_id INT,        -- NULL until shipped
    delivery_date_id INT,    -- NULL until delivered
    return_date_id INT,      -- NULL unless returned
    order_amount NUMERIC,
    days_to_ship INT,        -- computed when shipped
    days_to_deliver INT      -- computed when delivered
);
```
